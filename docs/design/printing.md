# USB printing on Windows 98 SE (printer class 07)

Status: design draft, 2026-10-20. No code yet.

## 1. Purpose and devices served

Windows 98 SE has no USB printer class driver. A USB printer, or a USB to
parallel printer cable, gets no driver and no printer port, so 98 SE cannot
print to it. ME, 2000 and XP have one (section 2). This design fills the 98
SE gap with two pieces:

- **`USBPRN.SYS`**, a WDM function driver for the printer class interface
  (USB Device Class Definition for Printing Devices 1.1). It sends job data
  on the bulk OUT pipe and reads the optional bulk IN pipe. It answers the
  three class requests `GET_DEVICE_ID`, `GET_PORT_STATUS` and `SOFT_RESET`.
- **`USBPRNMN.DLL`**, a port monitor for 98's spooler. It exposes one
  printer port per device (`USB001`, `USB002`, ...) and moves each job's
  bytes to the driver with `WriteFile`.

The devices people would use it with:

- **USB to parallel printer cables.** These present printer class `07/01/01`
  or `07/01/02`. They are the usual way to drive a parallel laser,
  dot-matrix or label printer from a machine without an LPT port, and 98 SE
  has drivers for many of those printers in the box (`msprint*.inf`).
- **USB printers that speak a language 98 knows**: PCL 5, PCL 6 or
  PostScript lasers. 98 SE's in-box drivers cover many of them, and a
  generic PCL or PostScript driver covers most of the rest.
- **The printer function of a multi-function device (MFP)**, where the
  printer interface is one of several (section 9).

What it does not do, and the user documentation must say so plainly:

- **It is a port, not a printer driver.** Most current inkjets and
  host-based ("GDI") lasers have no Windows 98 printer driver from anyone,
  so a working port does not help them.
- **It does not drive a pure IEEE 1284.4 interface** (`07/01/03` with no
  `01` or `02` alternate). Those need a 1284.4 channel stack, which XP
  provides with `dot4` and 98 SE does not have (section 2, section 5.1).
- **It gives MS-DOS programs no LPT port** (section 4.4).

Vendor 98 packages for USB printers, where they exist, usually ship their
own USB port driver and bind by VID/PID. A VID/PID match outranks this
package's class match, so it does not displace them.

## 3. Target systems and the plumbing on 98 SE

```
 application -> GDI -> printer driver (msprint INF, e.g. HPPCL5MS.DRV)
             -> spooler (SPOOLSS.DLL, spool32) -> language monitor (PJLMON.DLL, optional)
             -> port monitor USBPRNMN.DLL  "USB001"
                   | CreateFile("\\.\USBPRN1"), WriteFile, ReadFile, DeviceIoControl
             -> NTKERN -> USBPRN.SYS (FDO on the printer interface devnode)
                   | URBs (bulk OUT, bulk IN, class requests on EP0)
             -> usbhub / USBD -> host controller driver (UHCI, OHCI, NUSB EHCI, xHCI98)

 USBPRN.SYS also reports one child PDO  USBPRN\<NameModel><CRC>   (section 6)
             -> Class Printer, installed by msprint*.inf or a vendor INF,
                which creates the spooler printer on port USB001
```

### 3.1 The spooler side: a port monitor, not an LPT-port VxD

Two ways for 98's spooler to reach a WDM device were weighed.

**Route A: a port monitor DLL (chosen).** The 98 DDK documents the Windows
95/98 print monitor interface completely:

- `HELP_OTHER.CHM`, printer section:
  - "Port Monitors" (`printer_0r91.htm`)
  - "Local Port Monitor Design and Implementation Notes" (`printer_0r93.htm`)
  - "Required Functions" (`printer_0r94.htm`)
  - "Sample Port Monitor" (`printer_0r95.htm`, the documentation page only)
  - the reference pages `AddPort` ... `WritePort` (`printer_0rap.htm` to
    `printer_0rcj.htm`)
  - "Language Monitors" (`printer_0rck.htm`), "Language Monitor and Port
    Monitor Relationships" (`printer_0rcn.htm`) and the `MONITOR` structure
    (`printer_5kqb.htm`)
- `incs\INC_WIN98_WINSPLP.H`: the `MONITOR` structure (lines 390-494) and
  `InitializeMonitorEx` (lines 496-501).

A monitor DLL exports `InitializeMonitorEx` and its entry point, and nothing
else ("Sample Port Monitor": "Only two APIs have to be exported"). It fills in
the `MONITOR` table:

- port management: `EnumPorts`, `AddPort`, `ConfigurePort`, `DeletePort`;
- job I/O: `OpenPort`, `StartDocPort`, `WritePort`, `ReadPort`,
  `EndDocPort`, `ClosePort`;
- bidirectional and timeouts: `GetPrinterDataFromPort`,
  `SetPortTimeOuts`.

`pfnOpenPortEx` is left NULL: it belongs to language monitors.

The DDK states the case for this route directly: a printer vendor "needs to
develop a port monitor if their printer connects to a different type of I/O
port" ("Port Monitors"). Microsoft took the same route for USB on ME:
`usbmon.dll` is registered as a print monitor by ME's `subase.inf`.

**Route B: a VCOMM port driver VxD that presents an `LPTn` port.** The
in-box local monitor in `SPOOLSS.DLL` already prints to `LPTn` through
VCOMM ("Spooler Components and IHV Development Opportunities",
`printer_0qya.htm`: the port monitor "typically communicates with VCOMM").
VCOMM even defines the escape `GETDEVICEID` for the 1284 id
(`INC_WIN98_VCOMM.H` line 591). A VxD of the `serial.md` 5.1.2 kind could
present the USB printer as `LPT2`.

Route A is chosen for these reasons:

1. **What Route B would buy does not materialise.** The one thing an `LPTn`
   name would add is MS-DOS printing. DOS programs print through INT 17h or
   the port registers, not through VCOMM (section 4.4), so they would still
   not reach the printer. Win32 and Win16 programs that print through GDI go
   through the spooler either way.
2. **Route B costs much more.** It inherits every hard problem `serial.md`
   lists for `USBCOM.VXD`:
   - VCOMM's rule that `PortWrite` and others be callable at interrupt time,
     which forces a direct-call table into the WDM driver (`serial.md`
     5.1.2);
   - the resource-less `PortName` problem (`serial.md` 5.1.4), here
     colliding with BIOS-numbered real LPT ports;
   - LPT contention (`comm_0sqh.htm`), which `LPT.VXD` and `LPTENUM.VXD`
     also take part in.
3. **Route A is user mode.** The spooler calls `WritePort` on its own thread
   and waits, which maps directly onto a blocking `WriteFile`. A fault in the
   monitor kills the spooler, not the system, and the monitor can be
   debugged with ordinary tools.
4. **Every interface Route A uses is documented**, apart from the
   `GetPrinterDataFromPort` control codes (section 7.3). Route B rests on
   VCOMM's LPT behaviour, which the DDK documents more thinly than the COM
   side.
5. **It matches ME, 2000 and XP**, where USB printers appear as `USBnnn`
   ports of a USB monitor. Users and printer software meet the same shape on
   every system.

The user-mode DLL is in scope (Owner, 2026-10-20: user-mode code is allowed
when it exists only to make a driver here work; `AGENTS.md`, "Sources").
Owner, 2026-10-20: a VCOMM shim presenting `LPTn` comes later, and only if
asked for; this design does not need it.

### 3.2 How the monitor reaches the driver

`USBPRN.SYS` names each printer's device object `\Device\UsbPrn<n>` and links
it as `\DosDevices\USBPRN<n>`. The monitor opens `\\.\USBPRN<n>` with
`CreateFile`.

Win32 `CreateFile` on a WDM `\DosDevices` link works on 98 SE and ME. xHCI98
does exactly this for its query device (`xhci98\src\cm\cm_qryos.c`, header
comment and the `IRP_MJ_CREATE` case near line 1049, "98 SE and ME are not
held to it"). Its user-mode tools open `\\.\XHCICM<n>` on 98 SE. Device
interfaces and SetupDi are not used: they would add nothing on 98 SE, and
whether they work there was not checked.

## 4. The monitor, `USBPRNMN.DLL`

### 4.1 Installation and registration

- `USBPRN.INF` copies `USBPRNMN.DLL` to the system directory and writes
  `HKLM,"System\CurrentControlSet\Control\Print\Monitors\USB Printer
  Port",Driver,,USBPRNMN.DLL`. This is the same registration ME's
  `subase.inf` makes for `usbmon`. `msprint.inf` `[Environment_Reg]` creates
  the `...\Control\Print\Monitors` key on 98 SE.
- The spooler loads monitors when it starts. A monitor registered only in
  the registry is active after the next restart. To avoid a reboot,
  `USBPRN.INF` also adds a `RunOnce` entry,
  `RUNDLL32.EXE USBPRNMN.DLL,InstallMonitor`. That entry point calls the
  Win32 `AddMonitor` ("Installing Printer Support", `printer_0r04.htm`:
  "Use Win32 APIs such as AddPrintProcessor and AddMonitor"). Whether 98's
  `AddMonitor` accepts a monitor whose registry key already exists, and
  whether `RunOnce` runs before the user's first print, are **unverified**
  (M1).
- `InitializeMonitorEx(pRegisterRoot, pMonitor)` keeps `pRegisterRoot`. The
  monitor's own state lives under it: the port list and per-port settings.
  The spooler deletes that key if the monitor is deleted
  (`printer_0raw.htm`).

### 4.2 Ports

- **Names.** `USB001`, `USB002`, ...: the names `usbmon.dll` uses on ME,
  2000 and XP (Owner, 2026-10-20: named like Microsoft's). Port `USB00n`
  maps to `\\.\USBPRN<n>`.
- **The number `n`** is chosen by `USBPRN.SYS` when the device starts. It is
  the lowest number not already held, remembered per device identity in the
  driver's own registry key (`IoOpenDeviceRegistryKey`,
  `PLUGPLAY_REGKEY_DRIVER`):
  - The identity is VID, PID and the `iSerialNumber` string when the device
    has one.
  - Without a serial number, it is VID, PID and the 1284 id string with its
    volatile fields (`VSTATUS`, `SERN`) removed. Two identical printers
    without serial numbers can then swap numbers between boots. That is
    documented as a limit (section 9).
  - The driver also writes the chosen port name into the device's hardware
    key as `PortName` (section 6.3).
- **`EnumPorts`** (levels 1 and 2, `printer_0rau.htm`) returns every port in
  its registry list. A port stays listed while its printer is unplugged, so
  a printer object keeps its port. On each call, `EnumPorts` also probes
  `\\.\USBPRN1` to `\\.\USBPRN<max>`, where `<max>` is a bound kept in the
  registry, and adds any number not yet listed. So a newly plugged printer's
  port appears without user action.
- **`AddPort`** shows a message that USB ports appear by themselves when a
  printer is connected, and returns FALSE. `DeletePort` removes a port from
  the list. The spooler never calls it on an open port (`printer_0ras.htm`).
  The number stays reserved for the device in the driver's key.
- **`ConfigurePort`** shows a small dialog with the device's 1284
  description, its status (section 7) and one option, "Reset the printer
  when a job is cancelled", off by default (section 8).

### 4.3 Job flow

| Monitor entry | What it does |
|---|---|
| `OpenPort(name)` | Allocates the port context and opens no device. The spooler calls it at startup for every port with a printer (`printer_0r93.htm`), and the printer may not be connected. |
| `SetPortTimeOuts(cto)` | Stores the `COMMTIMEOUTS`. `WriteTotalTimeoutConstant` (the printer's "Transmission retry" setting) becomes the write timeout sent to the driver. |
| `StartDocPort` | Opens `\\.\USBPRN<n>` and sends `IOCTL_USBPRN_SET_TIMEOUTS` (private, section 5.4). Fails with `ERROR_NOT_READY` if the device is absent. The spooler then reports the error. |
| `WritePort(buf, cb)` | One `WriteFile`. On a timeout, it returns FALSE with the bytes accepted in `*pcbWritten` and `SetLastError` from the status (section 7.1). The spooler shows its retry dialog (`printer_0rcj.htm`). |
| `ReadPort` | `ReadFile` on the bulk IN pipe, with the read timeouts (section 7.2). |
| `GetPrinterDataFromPort` | Section 7.3. |
| `EndDocPort` | Closes the handle. If the job was deleted mid-stream and the port's reset option is on, it first sends `IOCTL_USBPRINT_SOFT_RESET` (section 8). It calls `SetJob` to delete the finished job, as `printer_0rat.htm` requires of a port monitor. |
| `ClosePort` | Frees the context. |

The device is open only between `StartDocPort` and `EndDocPort`, plus brief
opens for status. So an idle printer can be unplugged without a handle
holding its device object.

### 4.4 MS-DOS programs

98 SE's DOS printing goes to LPT through the BIOS INT 17h interface or the
port registers. Neither passes through the spooler or VCOMM, so no Windows
port, from this design or from Route B, reaches them. A workaround needs
98's own networking: share the printer, then use "Capture Printer Port" to
map `LPT2` to the share. Whether 98 SE captures to a share on the same
machine is **unverified** (M3 records it). Nothing in this package depends
on it.

## 5. The WDM driver, `USBPRN.SYS`

### 5.1 USB side

Descriptors are parsed per the printer class specification 1.1
(`usbprint11a021811.pdf` from usb.org, read on 2026-10-20, SHA-256
`d7c52da77bebf66c6f7888b5f3b5f297d631e399cab3f032e7c300e1d2eeb13f`). The relevant sections are 3.2, 4.2 and 5.

**Interface.** Class `07`, subclass `01`. Protocol `01` is unidirectional
(bulk OUT only), `02` is bidirectional (bulk OUT and bulk IN), and `03` is
1284.4 (spec 5.3, Table 6). "If multiple printer interfaces are supported,
they shall be implemented as alternate interfaces" (spec 3.2).

**Alternate setting choice**, as Linux `usblp_select_alts()` does it
(`drivers/usb/class/usblp.c`, v6.12):

1. Collect the alternates of the bound interface whose class/subclass is
   07/01. Linux's `USBLP_QUIRK_BAD_CLASS` lets a listed device skip that
   check.
2. Keep only those with the endpoints their protocol needs.
3. Prefer `02`, then `01`, then `03`.
4. Under `USBLP_QUIRK_BIDIR` (the listed HP DeskJets, Kyocera FS-820,
   Brother HL-1440 and others), drop the IN endpoint.

**Protocol `03` is accepted only when no `01` or `02` exists.** Even then,
the driver starts but refuses data (Code 10 with a logged reason). A raw
byte stream to a 1284.4 interface is not a print job, and 98 SE has no
1284.4 stack. Owner, 2026-10-20: 1284.4-only devices are out of scope.

**Selecting the alternate.** `SELECT_CONFIGURATION` (whole device) or
`SELECT_INTERFACE` (function PDO, section 9) picks the chosen alternate. The
bulk OUT pipe's `MaximumTransferSize` is set to 64 KiB. The default is
`USBD_DEFAULT_MAXIMUM_TRANSFER_SIZE = PAGE_SIZE` (`INC_WIN98_USBDI.H` line
324). Writes are split at whatever the stack hands back in the pipe
information. Whether 98 SE's `uhcd`/`openhci` honour 64 KiB is
**unverified**, and the split makes it harmless either way.

**Class requests** (spec 4.2, Table 1):

| Request | `bmRequestType` | `bRequest` | `wValue` | `wIndex` | Data |
|---|---|---|---|---|---|
| `GET_DEVICE_ID` | `A1h` | 0 | configuration index (0-based) | interface in the high byte, alternate in the low byte | up to 1024 bytes: 2-byte big-endian length (counting itself), then the 1284 id |
| `GET_PORT_STATUS` | `A1h` | 1 | 0 | interface | 1 byte |
| `SOFT_RESET` | `21h` | 2 | 0 | interface | none |

Three details:

- **`SOFT_RESET`.** Spec 4.2.3 notes that version 1.0 wrongly gave
  `bmRequestType` `23h` (recipient Other). It says hosts "should be prepared
  for USB printers that expect this request code". Linux sends `23h`
  (`usblp_reset()`, `USB_RECIP_OTHER`). The driver sends `21h` and, if the
  device stalls it, sends `23h`. It records which one worked, per device,
  for next time.
- **`GET_DEVICE_ID`'s `wIndex`.** Linux uses the spec's layout
  (`usblp_ctrl_msg()`: "High byte has the interface index. Low byte has the
  alternate setting"). Interface 0, alternate 0, the common case, is 0
  either way. For a non-zero interface (an MFP), if the request stalls or
  returns a length under 2, the driver retries with the plain interface
  number in the low byte. That retry is defensive. Whether any device needs
  it is **unverified**.
- **Clamping and retries.** The length field is clamped to 2 to 1023, as
  Linux does (`usblp_cache_device_id_string()`). The id is read at start and
  again on each `IOCTL_USBPRINT_GET_1284_ID`, because `VSTATUS`-style fields
  change.

**Bulk OUT.** Each `WriteFile` becomes one or more bulk OUT URBs of at most
`MaximumTransferSize`, issued in sequence. No zero-length packet is sent;
Linux `usblp_write()` sends none either. A write completes when all URBs
complete, when the write timeout expires, or when the device is removed. On
a timeout, the in-flight URB is cancelled (abort pipe) and the IRP completes
with `STATUS_TIMEOUT`. `Information` holds the bytes the completed URBs
moved, and the partial URB's `TransferBufferLength` is counted too, so the
spooler's byte count stays exact.

**While a write is pending**, the driver reads `GET_PORT_STATUS` every 1.5
s. Linux does this in `usblp_wwait()` ("Prod the printer, Gentoo#251237"),
and the latest status byte also feeds section 7.1.

**Bulk IN.** It is read only on demand: one URB per `ReadFile`, with the
read timeout. No read is kept posted between requests. A printer that
streams unsolicited status therefore holds it until the next `ReadPort`, as
a parallel port in nibble mode does. Linux posts a read at open
(`handle_bidir()`); whether any printer stalls its OUT pipe while IN data
waits is **unverified** (M3, with the bidirectional test printer).

### 5.2 Device objects and PnP

- **FDO** on the printer interface's devnode (section 9 says which devnode
  that is). It is named `\Device\UsbPrn<n>`, with the
  `\DosDevices\USBPRN<n>` link.
- **One child PDO** for the printer itself (section 6). This makes
  `USBPRN.SYS` a bus driver for one child, as `serial.md` 5.1.2 does for
  its port child.
- **Power.** No selective suspend, no remote wakeup. On system suspend,
  outstanding URBs are cancelled and pending writes complete with
  `STATUS_CANCELLED`. The spooler sees a failed `WritePort` and offers a
  retry. On resume, the driver selects the alternate again; if the device
  re-enumerated, that is removal plus arrival.

### 5.3 Device I/O controls

The public controls are the codes Microsoft's `usbprint.sys` answers, taken
as interface values from the WDK 7.1 header `inc\ddk\usbprint.h`. They are
all `FILE_DEVICE_UNKNOWN`, `METHOD_BUFFERED`, `FILE_ANY_ACCESS`, with
function numbers 12 to 16. Using the same codes lets tools written for
2000/XP's device work against ours on 98. The header is not copied: the
package's own `usbprn.h` defines the five values.

| Code | Function | Behaviour |
|---|---|---|
| `IOCTL_USBPRINT_GET_LPT_STATUS` | 12 | `GET_PORT_STATUS`, 1 byte out |
| `IOCTL_USBPRINT_GET_1284_ID` | 13 | `GET_DEVICE_ID`, length bytes included |
| `IOCTL_USBPRINT_VENDOR_SET_COMMAND` | 14 | Vendor OUT request to the interface. The input layout is unverified: the header gives no structure. Answered `STATUS_NOT_SUPPORTED` until a client needs it. |
| `IOCTL_USBPRINT_VENDOR_GET_COMMAND` | 15 | The same, IN |
| `IOCTL_USBPRINT_SOFT_RESET` | 16 | `SOFT_RESET` (section 5.1) |

### 5.4 Private controls

- `IOCTL_USBPRN_SET_TIMEOUTS`: read and write timeouts in ms (0 = none).
- `IOCTL_USBPRN_GET_INFO`: protocol in use, whether bidirectional, VID/PID,
  port number, and whether the device is present. The monitor's
  `ConfigurePort` dialog and the M1 test tool use it.

## 6. Plug and Play printer install from the 1284 id

### 6.1 How 98 SE matches a printer to its INF

The 98 DDK documents this for parallel printers (`HELP_OTHER.CHM`,
device-installation section):

- **"Generating Unique Plug and Play Device IDs"** (`devinst_1c51.htm`):
  - `LPTENUM` concatenates the 1284 `MFG` and `MDL` values and computes "a
    4-digit checksum" over the string.
  - It truncates the string to 20 characters and appends the checksum, giving
    "a device ID string of not more than 24 characters".
  - Its example: `MFG` `Hewlett-Packard` and `MDL` `HP LaserJet 4P` give
    `LPTENUM\Hewlett-PackardHP_La7EE2`.
  - "The algorithm used to calculate the checksum is beyond the scope of this
    documentation."
- **"Using CID Values"** (`devinst_1c52.htm`): a printer's 1284 `CID` key
  lists compatible ids, either enumerator-qualified (`LPTENUM\...`) or bare
  (`HP_LaserJet_4L`).
- **"Ordering of Device ID and Compatible Device ID Values"**
  (`devinst_1c6o.htm`): each match gets a device rank (0 for the MFG/MDL id,
  then 1, 2, ... for the CIDs in order) plus an INF rank (the id's position
  after the install section name). A sum of 0 installs silently; otherwise
  the user is asked.
- **"Printer Plug and Play Installation Requirements"** (`devinst_1c4x.htm`)
  defines `MFG`, `MDL`, `CLS` (`PRINTER`), `DES` and `CID`.

98 SE's in-box printer INFs follow this pattern: the first id is
`LPTENUM\<id>`, the second is the bare `<id>`, and further bare
compatibles follow. For example, `msprint3.inf`:

```
"HP LaserJet 4P" = HPPCL5MS.DRV.BIDI,LPTENUM\Hewlett-PackardHP_La7EE2,Hewlett-PackardHP_La7EE2,HP_LaserJet_4P
```

There are 147 lines with `LPTENUM\` ids across `msprint.inf` to
`msprint4.inf`, and no `USBPRINT\` ids. 2000's `ntprint.inf` keeps the
`LPTENUM\` form. XP's mostly lists bare ids. Its 27
`USBPRINT\` entries take the form `USBPRINT\BrotherMFC-8303E01`. Microsoft's
"Identifiers Generated by USBPRINT.SYS" (learn.microsoft.com) confirms that
`usbprint.sys` builds `USBPRINT\NameModel(20)Checksum(4)` the same way, with
spaces replaced by underscores, and gives the example
`USBPRINT\Hewlett-PackardHP_Co3115`.

### 6.2 The child PDO

`USBPRN.SYS` reports one child PDO with the following ids. `<id>` is
`<MFG><MDL>` with spaces replaced by `_`, truncated to 20 characters, plus
the 4-hex-digit checksum.

| Query | Value |
|---|---|
| `BusQueryDeviceID` | `USBPRN\<id>` (our own enumerator name, so the `Enum` path is ours) |
| `BusQueryInstanceID` | the port number `n` (unique per parent and stable) |
| `BusQueryHardwareIDs` | `LPTENUM\<id>`, `USBPRINT\<id>`, `<id>` |
| `BusQueryCompatibleIDs` | each `CID` value as the device gives it, in order |
| `DeviceTextDescription` | the 1284 `DES` value, or `MFG MDL` |

`LPTENUM\<id>` comes first so that an in-box 98 SE entry or a vendor's
parallel-port INF matches at device rank 0 and INF rank 0, and installs
silently, exactly as the same printer would on a parallel port.
`USBPRINT\<id>` lets the few 9x-era vendor INFs written for USB match.
Whether 98 SE's device installer accepts, on a devnode under another
enumerator, a hardware id carrying the `LPTENUM\` prefix, and ranks it as
`devinst_1c6o.htm` describes, is **unverified**. M2's first test settles it.
If it fails, the bare `<id>` (rank 1 in every in-box entry) still matches,
and the user confirms the driver once.

Only `MFG` and `MDL` (long or short key names, `MANUFACTURER`/`MODEL`) are
needed. A device that reports neither gets no child PDO. Its port still
works, and the user adds the printer by hand (section 6.4).

### 6.3 The checksum

The DDK withholds the algorithm, and the DDK sample sources are not read
(Owner, 2026-10-20; `AGENTS.md`, "Sources"). What was established from
published data only:

- **The candidate.** CRC-16/ARC: polynomial `8005h` reflected (`A001h`),
  initial value 0, no final XOR, over the bytes of `<MFG><MDL>`. A PWG
  mailing-list post (Jim Sommer, 2001-10-04,
  `pwg.org/hypermail/upd/0514.html`) describes the algorithm "used to
  generate the LPTENUM checksum" as a table-driven 16-bit CRC with seed 0.
  Its code carries no licence and is not used. CRC-16/ARC is a standard
  algorithm and is written from its definition.
- **The test.** Over the 114 untruncated ids (prefix shorter than 20
  characters) in 98 SE `msprint*.inf` and XP `ntprint.inf`, CRC-16/ARC of
  the prefix reproduces 42. One is `CanonBJC-2105D67`. The DDK's own HP
  example (`7EE2`) and Microsoft's `3115` example do not reproduce from the
  strings as written.
- **The misses** are consistent with the true `MDL` values differing from
  what the INF's truncated prefix shows: trailing spaces or a different
  model string. Many missed prefixes end in underscores
  (`MINOLTAPAGEPRO___6`). The 72 misses also leave open that the algorithm
  differs. Microsoft's page warns: "The CRC that is generated by the
  operating system may not match the CRC that is calculated as described
  ... or by any other CRC algorithm."

So the checksum is **unverified**, and the design does not rest on it alone:

1. **M2 compares, where an XP SP3 machine is at hand.** For every test
   printer, the id `USBPRN.SYS` builds is compared with the `USBPRINT\`
   hardware id XP SP3's `usbprint.sys` reports for the same printer
   (Device Manager, Details). XP is outside this package's range, so the
   comparison is a reference reading, not a release blocker; until it is
   made, the release notes list the checksum as unverified and the 98 SE
   fallbacks below stand. That is observed output,
   not a reading of the binary. Each difference is recorded with the raw
   1284 string.
2. **The bare compatibles do not depend on it.** The `CID` values (for
   example `HP_LaserJet_4L`) and the model-name ids such as `HP_LaserJet_4P`
   in the INFs can be matched without the checksum. The child's compatible
   list also gets a generated `<MFG>_<MDL>`-style model id only if M2 shows
   that in-box entries match it. **Unverified**; not added on speculation.
3. **Manual install always works** (section 6.4).

### 6.4 Port assignment and the fallbacks

When the child installs, `MSPRINT.DLL` (the Printer class installer) creates
the spooler printer. For an `LPTENUM` printer it must pick the parent port's
name. How it finds that name is undocumented in the DDK; the
`HKLM\Enum\...\PortName` of the parent devnode is the likely source. So
`USBPRN.SYS` writes `PortName=USB00n` into its own devnode's hardware key
(`IoOpenDeviceRegistryKey`, `PLUGPLAY_REGKEY_DEVICE`). It also writes the
same value into the child's key. **Unverified**; M2 tests it. In order:

1. The printer is created on `USB00n`: done.
2. The printer is created on another port (`LPT1:` or `FILE:`). The user
   changes it under Properties, Details, "Print to the following port". This
   is the step the manual says to check. Owner, 2026-10-20: this is the
   final answer; no helper program moves the printer automatically.

**Manual install, no PnP needed** (M1): Control Panel, Printers, Add
Printer, Local printer, pick the model or Have Disk, port `USB001`. This is
what users of printers without a 98 INF entry do in any case.

## 7. Bidirectional status

### 7.1 Port status

`GET_PORT_STATUS` returns the parallel status byte (spec 4.2.2, Table 3):
bit 5 Paper Empty, bit 4 Select, bit 3 Not Error, the rest reserved. Linux
maps it the same way (`usblp_check_status()`: `LP_POUTPA`, `LP_PSELECD`,
`LP_PERRORP`). The spec notes that a printer that cannot tell should return
the benign value.

When a write times out, `WritePort` returns FALSE and sets the last error
from the latest status:

| Status | Error | What 98's spooler shows |
|---|---|---|
| Paper Empty | `ERROR_OUT_OF_PAPER` | its retry dialog |
| not Select | `ERROR_NOT_READY` | the same |
| not Not-Error | `ERROR_GEN_FAILURE` | the same |
| benign | `ERROR_TIMEOUT` | the same |

The DDK says the spooler "displays a dialog box" when `WritePort` fails
(`printer_0rcj.htm`) and that monitors may `SetLastError` so the spooler can
"prompt the user" (`printer_0rao.htm`). Which of these codes give distinct
text on 98 SE is **unverified** (M3).

### 7.2 `ReadPort`

`ReadPort` reads the bulk IN pipe and passes the data unaltered
(`printer_0rcg.htm`: "must not alter the data stream"). If the interface is
unidirectional, or the `BIDIR` quirk applies, `ReadPort` fails at once.
Language monitors such as 98's `PJLMON.DLL` call `ReadPort` from a
background thread "every few seconds" (`printer_0rcn.htm`). Every 98 SE
`.BIDI` install section attaches `PJLMON.DLL`: `msprint3.inf`
`[HPPCL5MS.DRV.BIDI]` has `LanguageMonitor=%PJL_MONITOR%`. So a PJL laser on
USB can show real status in 98, as it does on a bidirectional parallel port.

### 7.3 `GetPrinterDataFromPort`

The DDK says it "can be used to make any IEEE 1284 specification IOCTL
call" (`printer_0rav.htm`) but documents no `ControlID` values. The 98 DDK
headers define none either: `INC_WIN98_WINSPLP.H` has only the prototype.
So in M1 the monitor logs every `ControlID` it receives and fails it with
`ERROR_INVALID_FUNCTION`. The language monitor then falls back to
`ReadPort`, as `printer_0rcn.htm` describes for printers without IEEE 1284
support.

M3 runs `PJLMON.DLL` against the port with that log on and records the codes
it sends. It then maps the ones that turn out to mean "device id" or "port
status" onto `IOCTL_USBPRINT_GET_1284_ID` and `..._GET_LPT_STATUS`. This is
black-box observation of our own DLL's input.

## 8. Removal while a job is printing

98 has no `IRP_MN_SURPRISE_REMOVAL` (a 2000-and-later minor code, 2000 DDK
`wdm.h`; `serial.md` 7.9). NTKERN sends `IRP_MN_REMOVE_DEVICE`. Whether it
sends `IRP_MN_STOP_DEVICE` first on a yank is unverified, and M3 logs it.

**Driver:**

1. Mark the device gone and delete the `\DosDevices\USBPRN<n>` link, so new
   opens fail.
2. Abort both pipes. The pending write completes with
   `STATUS_DEVICE_NOT_CONNECTED` and the bytes moved so far. New I/O fails
   the same way.
3. Report the child PDO gone (`BusRelations` without it). Its devnode and
   the spooler printer stay. The printer is not deleted, as with an
   unplugged parallel printer.
4. Keep the FDO's extension alive until the last handle's `IRP_MJ_CLOSE`.
   A reference count taken at `IRP_MJ_CREATE` and dropped at `CLOSE` does
   this. Then call `IoDeleteDevice`. This ordering is the main crash risk,
   and M3 tests it with a job in flight.

**Monitor:**

1. `WritePort` returns FALSE with `ERROR_DEVICE_NOT_CONNECTED`, closes the
   handle, and marks the port absent. The spooler shows its retry dialog,
   and the job stays queued.
2. On Retry, `WritePort` reopens `\\.\USBPRN<n>`. The replugged printer gets
   the same `n` (section 4.2), so printing resumes. The printer lost what
   was in flight, and the page in progress is likely garbled. The manual
   says to cancel and reprint.
3. On Cancel, the spooler deletes the job, and `EndDocPort` closes. If the
   device is still present, the job was cancelled mid-stream, and the
   port's reset option is set, `EndDocPort` first sends `SOFT_RESET` so the
   printer drops the partial job. The default is off (Owner, 2026-10-20):
   Linux never resets on its own, and how printers react is unverified
   (M3).

Unplugging an idle printer leaves no handle open (section 4.3), so it is the
ordinary removal case.

## 9. Multiple printers, and MFPs

**Multiple printers.** Each printer interface gets its own FDO, number `n`,
link `\\.\USBPRN<n>` and port `USB00n`. The monitor holds one context per
port and the spooler serialises jobs per port. Two printers print at once,
each on its own thread. The driver allows one writer per device at a time:
a second write-access open fails with `STATUS_SHARING_VIOLATION`.
Status-only opens are allowed alongside. Identical printers without serial
numbers may swap numbers between boots (section 4.2). The manual says to
tell them apart by Properties, Details.

**MFPs.** The printer is one interface among others: scanner (vendor class
or `06`), card reader (`08`), fax or storage. Owner, 2026-10-20: INFs here
match interface-level ids only, and never bind a whole device generically:

- **`USBPRN.INF` matches interface-level class ids only**:
  `USB\Class_07&SubClass_01&Prot_01`, `...&Prot_02` and `...&Prot_03` (for
  devices whose alternate 0 is `03` but which offer `02` elsewhere, section
  5.1). It never matches a whole device generically. These ids exist where
  the stack has made the printer interface a devnode of its own:
  - **A single-interface printer.** The device's devnode carries the
    interface class ids, which is how 2000's `usbprint.inf` matches
    `USB\Class_07`. That the 98 SE hub generates them for a device whose
    `bDeviceClass` is 0 is **unverified**; M0 reads the ids of a real
    printer under 98 SE.
  - **A composite split by 98 SE's `usbhub`** (`usb.inf` line 91,
    `USB\COMPOSITE` on the hub), by ME's `usbccgp`, or by xHCI98. The
    printer function devnode is `USB\VID_vvvv&PID_pppp&MI_nn` with the
    interface class ids as compatible ids. xHCI98 splits per interface and
    per IAD (xHCI98 `docs/contributing/design/13-superspeed-hcd.md` 10.7 and
    10.8, as cited in `serial.md` 5.2). A printer function is one interface,
    so IAD handling does not matter here.
- **Bound to a function devnode**, `USBPRN.SYS` reads the configuration
  descriptor the parent supplies, finds its interface, and uses
  `SELECT_INTERFACE` for the alternate. It never selects the configuration.
  The scanner and storage functions stay with their own drivers. On 98 SE
  the scanner has `usbscan.sys` with a vendor INF, if one exists.
- **An unsplit composite** (a stack that does not split it, or a device
  whose device-level class hides the interfaces) is served under xHCI98,
  which splits it. Otherwise it is added by VID/PID on request (Owner,
  2026-10-20), with the loss of its other functions documented.
- **`GET_DEVICE_ID`'s `wIndex`** carries the MFP's actual interface number.
  This is where the retry of section 5.1 matters.

Under MFPs whose printer interface is `03`-only (HP's 1284.4 OfficeJets),
this package does nothing useful; such devices are out of scope (Owner,
2026-10-20).

## 14. Test plan

No QEMU printer model exists (`candidates.md`). Development uses real
printers passed into a 98 SE guest with `usb-host`. Acceptance is on real
hardware.

**Real devices** (Owner, 2026-10-20: one or two mainstream devices per
class; the three below are the minimum the cases need):

1. **A USB to parallel printer cable** (class `07/01/01` or `/02`) with a
   parallel PCL laser or an ESC/P dot-matrix printer that 98 SE's in-box
   INFs list. This is the main use case and the M1 device.
2. **A USB PCL or PostScript laser with a bidirectional interface** (`07/01/02`
   with a bulk IN pipe) that has an in-box 98 SE or vendor 98 driver. It is
   used for PnP install, `PJLMON` status and paper-out.
3. **An MFP** whose printer is one interface among scanner and storage
   functions (`07/01/02` plus others). It tests the interface-level binding
   and the `wIndex` retry.

**Host stacks, each device on each** (NUSB's EHCI stack is fully
supported, Owner, 2026-10-20):

- Microsoft's 98 SE UHCI and OHCI stack;
- NUSB's EHCI stack on 98 SE;
- xHCI98.

98 SE is the one tested system (Owner, 2026-10-20; `README.md`, "Tested
by the author"). The NUSB leg is an EHCI leg only when EHCI carries the
traffic: a High Speed printer, or a Full Speed printer or cable behind a
High Speed (USB 2.0) hub. Most printers and parallel cables are Full
Speed; on an EHCI root port, real or in QEMU, they are handed to the
companion UHCI/OHCI controller and count as that leg. The EHCI leg is
real hardware, with a High Speed hub, and the record shows which path
carried the job.

If M0 makes ME a target, the `w98se-me` folder is "Built, not tested" on
ME, and its release notes list what stays unverified there: printing,
Plug and Play install and status on ME, and every case below.

No Pentium-class PC is assumed. Throughput is measured on the bench
machines and recorded as such.

**Cases:**

- Manual install on `USB001`; print a test page, a 50-page PCL job and a
  20 MB PostScript job; record throughput per stack.
- PnP: the child's ids against XP SP3's `usbprint.sys` ids for the same
  printer (section 6.3); silent install versus a prompt; the port the
  printer object gets (section 6.4).

  available, across reboots: port numbers stay stable or the documented

- MFP: the printer prints while the scanner's devnode keeps its own driver;
  no whole-device binding occurs.
- Standby and resume with a job queued.
- **ME (M0):** does the in-box `usbprint.sys` bind and print? This decides
