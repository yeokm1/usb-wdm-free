# AX88179 physical router traffic, 2026-10-21

The user's router-connected physical 0B95:1790 now passes an original
**host-side** USB Ethernet test. Two bounded runs obtained DHCP offer/ACK,
resolved the advertised router by ARP and received an exact-nonce ICMP
echo reply with verified IP/ICMP checksums. The second run additionally
validates and strips every delivered Ethernet FCS in the actual C receive
core. This is real physical traffic, not a synthetic frame test or guest
NDIS result. It does not establish a Windows kernel network driver.

The user's autonomous physical-network-test request authorized the necessary
volatile initialization/reset/link RX/TX controls. It satisfied the control
header's separate authorization gate; the planner alone does not confer
permission. No EEPROM/eFuse write, MAC rewrite, host driver rebinding,
host OS IP configuration, general traffic generator or VM was used.

## Source and execution boundary

New `src/net/ax88179/axnet.py` is an original bounded ctypes/libusb executor
and DHCP/ARP/ICMP test. Its volatile reset/register/link facts are adapted
from the already pinned Linux v6.12 `drivers/net/usb/ax88179_178a.c`, commit
`adc218676eef25575469234709c2d87185ca223a`, SHA-256
`1c851bd414cb0251723cc50ae5c652032870ddcdd7ceef60b3d7e96f25e68e05`.
ASIX copyright and GPL-2.0-or-later are retained and the file has its own
NOTICE row. No Microsoft/vendor binary code or sample sources were read.
See [control provenance](../../../src/net/ax88179/CONTROL.md) and
[framing provenance](2026-10-21-ax88179-framing.md).

`host.ps1` now compiles the existing actual `axctrl.c` and `axframe.c` into
the host ABI. The executor uses the C descriptor validator, power prefix,
observed-speed/link planner, TX encoder and RX aggregate parser, rather
than a Python-only wire model. It claims only interface0 of the already
configured exact device; no configuration switch or host driver change.

Volatile operations follow the source's PHY power/reset and clock delays,
read EEPROM word43 and conditionally set only the corresponding volatile
auto-detach bits, retain the hardware MAC, set pause watermarks, disable
checksum offloads for software checksum testing, select physical/broadcast
receive traffic with alignment/CRC-error filtering, restart PHY autoneg,
bound link/FIFO polling, then apply the C-derived queue/negotiated medium.
LED, EEPROM/eFuse, EEE, WoL, jumbo and vendor-private persistent operations
are not performed. Omitting them does not prove a complete Linux-equivalent
initialization or generic hardware support.

An explicit write allowlist accepts only the required volatile MAC
registers and standard PHY BMCR write. It cannot write NODE_ID, EEPROM,
eFuse or unrelated PHY registers. All control return lengths are checked.
The power prefix's EEPROM-dependent branch is observed, not skipped or
assumed. MAC mismatch after reset stops the test.

Traffic is five packets per run: DHCP DISCOVER, DHCP REQUEST, router ARP,
one router ICMP echo and DHCP RELEASE. DHCP identity uses the preserved
MAC and a fresh transaction ID; replies must match both. ACK must agree
with offered address/server. ARP must match router/client protocol and
hardware identities. Echo must match source/destination, ID/sequence,
random payload and IP/ICMP checksums. DHCP RELEASE is sent after the test;
UDP has no release acknowledgement, so server-side lease removal is not
asserted. Incoming unrelated LAN broadcasts can appear in the raw log.

Finally the tool stops RX, restores the captured MAC-register values,
checks the node MAC again, releases interface0 and closes libusb handles.
This is not a promise to restore every PHY-internal/autoneg transient;
the saved clock/power/RX state is restored and the post-test PHY observation
is down, as before. Failed restore/release forces final failure.

## Measured result

Initial `axread.py` returned all three exact-length diagnostic reads.
Observed libusb speed4 maps explicitly to this core's SuperSpeed enum3;
USB-status register04 agrees. Hardware MAC was valid and preserved. Initial
PHY was down. Both initialized runs negotiated **1000 Mb/s full duplex**,
medium013B, queue074F0012FF and 20480-byte receive-buffer plan.

Run1 exposed a physical representation detail: every received record had
a trailing four-byte FCS. Independently recalculated Ethernet CRC32 matched
all seven. Its protocol parser bounded IPv4 by the IP total length and
thus did not misinterpret the FCS, but the old C receive API's omit-FCS
precondition was not satisfied. Run1 remains useful network evidence;
it is not counted as validation of the new FCS mode.

The original `AxFrameReceive` API is retained. New `AxFrameReceiveFcs`
explicitly validates IEEE Ethernet CRC32, drops bad-FCS records and strips
four bytes before the callback; it never guesses the mode. Run2 uses it
with maximum1514 Ethernet bytes excluding FCS. This avoids inventing an
undocumented hardware register bit to change FCS forwarding.

Host tests: 66542 control/descriptor/link checks, 62861 existing framing,
guard/boundary checks, plus six Python packet/executor tests. The latter
include every one-bit payload/FCS corruption of an independently zlib-CRC
fixture through the **actual C** FCS API, DHCP identity/option/truncation
checks, IP checksums/fragments and persistent-write refusal before I/O.
WDK7.1 x64 host DLL compile/link `/W3 /WX` passed. These are host tests,
not kernel builds or device/USB certification.
