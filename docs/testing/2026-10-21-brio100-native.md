# Physical Brio 100 native Windows 7 reference, 2026-10-21

The connected Logitech Brio 100, **046D:094C**, delivered camera frames through
Windows 7 x86's **in-box usbvideo driver** and the project's CAMCHECK utility.
This is a native-driver/reference-tool run, not a project USB camera driver
test. The preview was gray/noisy; the cause was not established and no clear
scene/image-quality claim is made. The user authorized the WinUSB rebind and
camera preview. No video recording or microphone capture was performed.

## Configuration and identity

Before attachment, the host's present device reported service `WinUSB`.
QEMU 11.1.0 attached only this physical VID/PID to `usb-ehci`; HMP reported
480 Mb/s, product Brio 100. A fresh
`E:\usb-wdm-free\wave2\w7brio.qcow2` overlay of `vm/w786.qcow2` used:

- `-machine pc -accel whpx,kernel-irqchip=off -cpu pentium3 -smp 2 -m 1024`;
- standard VGA, `-display none`, no NIC;
- `usb-host,bus=ehci.0,vendorid=0x046d,productid=0x094c,id=brio`;
- localhost HMP 44338, exchange `E:\usb-wdm-free\wave2\w7brio-a`;
- scratch, trace, TEMP/TMP and vvfat temporary backing on E:.

No other physical device was assigned to this guest. The guest installed its
native camera support automatically. No project INF, catalog, kernel binary,
trust-policy change or signature-enforcement override was used.

Read-only `PNPSTAT.EXE 046D:094C` reported:

| Function | Native service | Configuration Manager result |
|---|---|---|
| USB composite parent | usbccgp | CM=0, problem=0 |
| Video interface MI_00 | usbvideo | CM=0, problem=0 |
| Audio interface MI_02 | usbaudio | CM=0, problem=0 |

The audio function merely enumerated; no audio stream was opened. The generic
PnP metadata helper gained an explicit, strictly parsed four-hex-digit
`VID:PID` option. Its no-argument synthetic VID FFFF default remains. It records
hardware IDs/services/status, without device instance IDs or serial strings.
Its malformed target `046D094C` returned exit 4. The VC6 build passed.

After stopping preview, `HUBDESC.EXE 046D:094C` captured standard device and
configuration descriptors through the guest's hub, without strings or vendor
requests. The guest's 18-byte device and 2453-byte configuration are identical
to the earlier host [descriptor fixture](../../src/video/uvc98/testdata/brio100/README.md):
USB 2.0, UVC 1.0, VC0/VS1, video EP81 and eleven nonzero isochronous alternates.
This confirms the descriptor identity seen through EHCI in this run.

## Preview, format and reopen observations

CAMCHECK enumerated `Microsoft WDM Image Capture (Win32)` version
6.1.7601.17514. The initial connection briefly displayed Not Responding, then
returned with Preview on. Its initial 640x480, 16-bit YUY2 mode eventually
reported 5 then 6 frame callbacks, each with a 614400-byte buffer.

The native Format dialog accepted **160x120 YUY2**, reporting size 38400.
CAMCHECK then showed advancing frame callbacks, including **94 to 332**, with
last-buffer size **38400 bytes**. This counter is updated by the actual AVICap
frame callback; it is not a timer-generated success counter. The scaled
preview remained gray/noisy. No target frame rate, sustained performance,
decoded-image correctness or clear scene was independently established.

Stop reported `Preview stopped; camera disconnected.` A subsequent Preview
connection retained 160x120 YUY2 and reached **131 frame callbacks**, again
38400 bytes. Stop disconnected successfully a second time. The native control
dialog and CAMCHECK were used only for video preview/format selection.

## USB trace and limits

`w7brio.trace` records USB control setup/status and ISO start/stop metadata,
without image payload bytes. It includes VS PROBE selector 0100 and COMMIT
selector 0200 on interface 1, and video alternate transitions including 0/11.
The trace does **not** retain their negotiated data blocks, so it does not
independently prove their decoded values or exact probe length.

Per-completion tracing was disabled during preview after sufficient evidence
to bound log growth. Before disabling, the metadata had 419052 status-0
completions and six status -3 completions. Those six followed a standard
descriptor query or optional class-control queries during enumeration; no
claim that every control succeeded is made. The log showed ISO EP1 activity
and nonzero transfer lengths. Callback counters provide separate application
evidence of delivered video buffers.

QEMU stderr repeatedly reported `libusb_kernel_driver_active: -12
[NOT_SUPPORTED]` on the host's WinUSB path. Native installation and preview
nevertheless proceeded. No `libusb_submit_transfer[iso] INVALID_PARAM` failure
was observed in this run. This result is specific to this camera's IN path;
it does not resolve the separate X4 ISO OUT boundary.
