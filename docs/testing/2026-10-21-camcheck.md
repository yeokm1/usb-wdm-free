# CamCheck preview utility, 2026-10-21

The owner requested a utility to display a webcam feed and accepted a name
independent of xHCI98. The resulting utility is `CAMCHECK.EXE`, window
title **CamCheck**, in `src/video/uvc98/`. It supports camera selection,
live preview, stop/disconnect, refresh, driver format/source dialogs, and
format/frame-buffer diagnostics. No recording operation is implemented.

## Build and review

`cmd /c src\video\uvc98\preview.cmd` passes MSVC6 `/W3 /WX`, x86 ANSI,
Windows subsystem 4.0, `/MD`. Output:
`out/video/uvc98/preview/CAMCHECK.EXE`.

SHA-256 of the initial Windows 2000 tested build:
`22a5978850dbe21a8db3292513b09c5c24d68e9f202ee91085e43c2661f85028`.
Source `camcheck.c`:
`69f022b9f66e3ed6a7cd4af0c7a9213e47feccc39b32d9dac0e9689b5e097d7b`.

An independent source review checked format allocation/length bounds,
callback storage, callback-to-UI communication and capture-window teardown.
The review found a recovery issue where preview-rate failure prevented
preview startup and left no retry while connected. The fixed build calls
preview independently and allows retry while connected; format/source
dialogs also restart preview. Camera errors persist until a manual retry.

Only our executable's import table was inspected. Imports are from
AVICAP32, USER32, KERNEL32 and MSVCRT. The utility requires those system
components; it does not package replacement DLLs or redistribute runtime
binaries. Microsoft API documentation and published headers were used,
not driver-kit sample sources. API links are in the package README.

## Windows 98 SE and smaller displays

The initial executable loaded on 98 SE, but its 800x680 window extended
outside a 640x480 desktop. The native AVICap also sent error ID0 during
setup; that is a new-operation/clear notification, according to
[Microsoft's callback documentation](https://learn.microsoft.com/en-us/previous-versions/ms707184(v=vs.85)),
and must not be displayed as a camera failure.

The revised utility sizes its initial window to the work area, resizes
the selector and buttons, and ignores ID0 as an error. Revised executable
SHA-256: `2b4cc420aa4a2035a813a67f1f735a97b9a3790bf5d89fee02f1f3802b61f690`;
source: `ad8ce259cb9a1b9bc8a9de8417b0e1deeedaef04a861bb688c0d1b5fd196e5a4`.

(base `vm/w98se.qcow2`), headless QEMU i386 pc/Pentium III, 256 MiB,
standard VGA, no NIC or USB device. The entire window and all controls fit
the 640x480 desktop. The no-device message, Refresh and close were checked.
The guest shut down and its QEMU process exited. Evidence:
`w98cam2-fixed.png`, `w98cam2-refresh.png` and shutdown screenshot on E:.
An earlier throwaway `w98cam.qcow2` used Cirrus and triggered a
new-display-driver CD prompt; it was closed and replaced with standard VGA,

This is a utility load/UI check, not a camera driver or live-frame pass.

The revised build was then loaded again on the Windows 2000 overlay:

## Native Windows 7 UVC simulator preview

The same revised CamCheck binary displayed original moving color bars
from `uvcemu.py` through QEMU usbredir and Windows 7 x86's in-box USB video
driver. This tests the utility and simulator, not our future USB minidriver.

The successful run uses a fresh `E:\usb-wdm-free\wave2\w7cam3.qcow2`
overlay of the closed `w7midi.qcow2` overlay, ultimately `vm/w786.qcow2`.
QEMU x86_64 uses WHPX, Pentium III, two CPUs, 1024 MiB, standard VGA,
headless display, no NIC, UHCI, and an explicit simulated FFFF:0002
full-speed bulk UVC 1.1 camera. TEMP/TMP and the exchange disk are on E:.
No real camera was attached. Monitor 44338, model port 44420, evidence
prefix `E:\usb-wdm-free\wave2\w7cam8-`.

The source dialog and preview negotiated 160x120, 16-bit YUY2. Two
screenshots (`connect2.png`, `moving.png`) show different positions of
the moving bars. The latter reports 143 observed preview callbacks and
38,400 bytes in the last buffer, the exact uncompressed frame size.
`stopfocus.png` subsequently reports 186 callbacks. Stop released the
camera, restored selection/Refresh, and displayed the disconnected status.
The model trace records 220 complete frames before the first stop, with
no rejected COMMIT or unsupported read-size events. Model frame counts
and utility callbacks count different stages and are not a frame-rate
or loss-free guarantee.

Reopening after Stop displayed the native source chooser but then error418
before any new USB class controls. Closing and relaunching the utility also
returned to that source chooser. Reconnect remains unresolved; no reconnect
pass is claimed. The chooser was cancelled, the utility closed normally,
and the guest shut down through ACPI powerdown. QEMU PID34532 and model
PID36532 exited; monitor44338 and model port44420 are closed.

Model SHA-256: `9031ec4f20c11a947c2c544f759d5e5000668a51eb9379ddf9e4cd4a52a09451`;
integration-test SHA-256: `cdbf8e3011372ff5873e6dfeea97a7e94656aa325e371bd87aa710ba4cec143e`.
Seven integration tests pass, including exact final-short-packet reads.

Earlier attempts are retained separately. `w7cam4` reached COMMIT but
rejected Windows' 62-byte tail requests; hot replacement did not recover
that stream. `w7cam7` enumerated usbccgp and usbvideo with CM problem zero
but VfW returned error418 before class controls. A fresh overlay was used
for the successful run rather than reporting those attempts as passes.
`w7cam6` failed to launch because its requested TEMP directory was absent;
the directory was created before the next launch. Windows activation
notifications were dismissed normally; no licensing or guest policy was
changed. No physical-camera, project-USB-driver or old-OS live-feed claim
