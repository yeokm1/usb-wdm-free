# CDCNET QEMU/Windows 2000 and XP experiments, 2026-10-21

This is an original, test-only implementation. `CDCTEST.INF` matches the
dedicated QEMU `0525:A4A2` model, not a generic device class. Nothing is
released and no physical-device, 98 SE, ME or EHCI claim follows. The
initial experiments target 2000; an additional XP x86 baseline is
recorded at the end, without implying full XP support.

## Inputs and sources

- Repository-local MSVC 6.0 and Windows 2000 DDK; source under
  `src/net/cdcnet/`. No DDK sample sources were read or copied.
- NDIS/WDM ABI declarations in `ndis.h`, `wdm.h`, `usbdi.h`, `usb100.h`
  and `usbioctl.h`. The private NDIS and USB source files are separate.
- The existing [Ethernet design](../design/ethernet.md), especially the
  M0 gates, ECM framing and separate payload/ZLP ownership contract.
- [QEMU 11.1.0 USB network model](https://gitlab.com/qemu-project/qemu/-/blob/v11.1.0/hw/usb/dev-network.c)
  for model facts: RNDIS configuration 2, ECM configuration 1, alternate
  1 on data interface 1, a 64-byte bulk pair and an interrupt pipe. No
  QEMU implementation code was copied. Synthetic host-test descriptors
  were constructed from the documented USB/CDC field layout.
- Microsoft's [NDIS 5 send completion](https://learn.microsoft.com/en-us/previous-versions/windows/hardware/network/ff553613(v=vs.85))
  and [receive indication](https://learn.microsoft.com/en-us/previous-versions/windows/hardware/network/ff553533(v=vs.85))
  contracts. The M1 spike uses copied `NDIS_STATUS_RESOURCES` receives;
  protocols never retain its one receive packet after indication returns.
- WDK 7.1 `ipexport.h` and `icmpapi.h` for the user-mode ICMP ABI facts
  used by the original `NETTEST.EXE` helper. Windows' own `icmp.dll` is
  dynamically called through its public API, never inspected.

## Build and host checks

```
src\net\cdcnet\build.cmd ndis5 free
src\net\cdcnet\build.cmd ndis5 checked
src\net\cdcnet\test.cmd
src\net\cdcnet\nettest.cmd
```

Free and checked builds pass the PE/import gate. The package-local gate
is copied from the repository's hardened UAC2 gate and fails on empty,
malformed, ordinal or delay-import reports. Import-list membership alone
does not establish availability on another target.

The descriptor host test passes 107 assertions and 80 single-byte
mutations. Every truncated synthetic input ends at an inaccessible page
boundary. This is parser evidence, not a USB or NDIS run.

## Guest setup

QEMU 11.1.0, fresh overlays backed by this repository's `vm/w2k.qcow2`:
Windows 2000 SP4, `-machine pc,acpi=off -cpu pentium3,-apic -m 256
-vga cirrus -rtc base=localtime -display none -nic none -usb`, with
`-netdev user,id=usbnet -device usb-net,netdev=usbnet,id=cdcnet`.
An Ethernet `filter-dump` on `usbnet` records the isolated user network.
There is no emulated PCI NIC. The USB path is Microsoft's emulated UHCI,
not an EHCI or physical-controller leg.

Scratch overlays and immutable per-run floppy staging directories are in
`E:\usb-wdm-free\wave2\`. Monitor `127.0.0.1:44340` is driven with
`src/generic/usbprobe/monitor.py`; screenshots are under
`out/net/cdcnet/`. The guest keyboard is Dvorak, so text fields use
`--layout dvorak`. Newer runs set QEMU's `TEMP` and `TMP` to the `E:`
scratch folder as well, including vvfat's temporary write overlay.

Installation: Found New Hardware, search suitable driver, floppy `A:`,
`CDCTEST.INF`, accept the unsigned-driver warning. Guest windows are not
shown on the host. Each completed run shuts Windows down to its safe-to-
power-off screen, then exits QEMU through the monitor.

## M0 configuration and OUT termination

`w2kecm.qcow2`, binary version `0.0.0.1`, SHA-256:

```
0609619c11073e59647d283250102d35e31122132b4178760a4386bb72525774
```

The miniport gets the USB PDO/FDO/lower objects through
`NdisMGetDeviceProperty`, reads both configurations, decodes the MAC
string, selects ECM configuration 1 and data alternate 1, validates the
returned pipe handles and limits, then submits 64-byte payload, separate
zero-length OUT transfer, and 60-byte payload, synchronously in order.
All USB transfer buffers are resident nonpaged storage.

Windows finishes installation and Device Manager reports working properly
(`out/net/cdcnet/ecm-start.png`). The PCAP contains distinct ordered
64-byte and 60-byte ARP requests, with different target IPs and trailing
markers. `testcap.py` checks exact lengths, markers, targets and source
MAC consistency. The zero-length transfer is not an Ethernet frame in the
capture; the next payload remains a separate frame.

Idle `device_del cdcnet` gives Windows' unsafe-removal warning. After its
acknowledgement and `device_add usb-net,netdev=usbnet,id=cdcnet`, Windows
asks for unsigned-driver acceptance again, creates adapter instance `#2`,
and reports working properly (`ecm-replug.png`). There are eight captured
frames: two request/reply pairs per arrival. No crash or restart occurs.
The guest was shut down cleanly and QEMU exited.

PCAP `E:\usb-wdm-free\wave2\w2kecm.pcap`, SHA-256:

```
539c692fa221013ec3ca4d1eaa15b3d42e24c4693f3f2cfd990002dcea63bf7a
```

This is QEMU endpoint/stack termination evidence, not proof on real
controllers or a working NDIS network interface. The M0 miniport reported
disconnected and rejected NDIS sends.

## M0 IN and cancellation

Fresh `w2krx.qcow2`, version `0.0.0.2`, SHA-256:

```
0122f9f0c82fd5df270c4d4a376f818c0f435a66487a8e049a96ebc657bfd886
```

Initialize now also sends `SET_ETHERNET_PACKET_FILTER` for directed and
broadcast traffic, reads the two ARP replies through bulk IN, validates
reply lengths, destination MAC, operation and source/target IPs, and
issues a third IN with no expected frame. After two seconds it calls
`IoCancelIrp` on its caller-owned IRP. Passing requires cancellation to
return true and the final IRP status to be `STATUS_CANCELLED`; completion
is drained before the IRP, URB or buffer can be freed. A timeout never
authorizes freeing lower-owned memory.

Device Manager reports working properly (`rx-start.png`), so all these
mandatory Initialize checks passed. The PCAP has the four ARP frames and
an additional multicast IPv6 router advertisement generated by QEMU;
the directed/broadcast filter keeps that unrelated frame out of the
pending-IN test. Windows shut down cleanly and QEMU exited.

PCAP `E:\usb-wdm-free\wave2\w2krx.pcap`, SHA-256:

```
1862e90ba88c0679e6392220fbd6b092322fac901551d64140a375aee1a58d85
```

## M1 bounded worker spike

Version `0.0.0.3` is an explicit QEMU/Windows-2000-only experiment. It
keeps a 32-packet send queue, rejects frames outside 14-1514 bytes before
admission, serializes USB work in one passive system thread, and polls
one timed bulk IN at a time. A payload and its required ZLP finish before
the next send. Halt closes admission, fails queued sends and waits for
the referenced thread object to terminate before freeing state. The
single copied receive packet is always indicated with saved
`NDIS_STATUS_RESOURCES` semantics; there is no retained receive ownership.

The M0 ARP and cancellation prerequisites still run before M1 starts.
This is a low-throughput feasibility spike, not the final asynchronous
multi-pipe implementation. Reset/power recovery, notification processing,
cross-OS imports, NCM, RNDIS data and real hardware remain unimplemented
or unverified. The INF now has an NT-only signature and an explicit
QEMU/2000 experiment description.

### M1 actual guest results

The free version 0.0.0.3 staged binary SHA256 was
`2c58226ec83cb5d39dd4c3e4ef442b912aac6bdd202e4200c0bb51197edfd421`.
Windows 2000 SP4 installed it and Device Manager reported "This device
is working properly" (`out/net/cdcnet/m1-start.png`). It obtained address
10.0.2.15 by DHCP through the guest TCP/IP and NDIS stacks.

The original GUI `NETTEST.EXE` then received three matching ICMP replies
from 10.0.2.2 and verified all 32768 deterministic TCP bytes supplied by
`netserve.py`, bound only to host 127.0.0.1:44342. The test used Explorer
to launch the file, opened no guest console and sent no Internet request.
`out/net/cdcnet/m1-nettest.png` records the PASS dialog;
`out/net/cdcnet/NETTEST.TXT` records all three successful replies, source
address and verified byte count. The host peer also recorded SENT 32768.

After `device_del cdcnet`, Windows displayed its normal unsafe-removal
warning and remained responsive (`m1-remove.png`). Recreating the same
QEMU device required unsigned-driver acceptance again. A second GUI
test after replug passed the same three ICMP replies and 32768-byte TCP
verification (`out/net/cdcnet/NETTEST2.TXT`, host `netserve2.log`).

The final capture `E:\usb-wdm-free\wave2\w2km1.pcap` has 231 Ethernet
frames and SHA256
`c5b95dbb0c94dadf403c8e24af294f2c3b70e748919d9956ee966b26b67f06a0`.
Running `python src/net/cdcnet/testcap.py --m1 <capture>` verifies the
ordered finite 64/60-byte probes, DHCP discover/offer/request/ACK, six
ICMP echo requests and six replies with the test payload, and two TCP
sessions each reassembled to exactly the expected 32768 bytes. This is
actual NDIS data-path evidence, not just installation success.

The guest completed an orderly shutdown with the "safe to turn off"
screen (`out/net/cdcnet/m1-poweroff.png`), followed by monitor `quit`.
QEMU PID40120 and localhost peer PIDs752/37168 no longer existed after
cleanup. Its overlay and capture remain under E:. The two earlier M0
guests were also shut down and quit; no guest owned by this package
remains running.

The initial run exercised the bounded transfer timeout/cancel/drain gate
and idle removal/replug. The follow-up below adds active removal and
bounded traffic pressure. Systematic fault injection, suspend/resume,
reset recovery and soak testing remain unverified. M1 is a QEMU/Windows
2000 feasibility prototype only.

## M1 active removal, load and repeated recovery follow-up

An additional headless guest used `E:\usb-wdm-free\wave2\w2kload.qcow2`,
backed by the successful M1 overlay above, with a new immutable vvfat
stage and PCAP in the same E: directory. TEMP/TMP remained on E:. The
installed driver remained exactly the version 0.0.0.3 binary hashed above;
no transport change was made to obtain these results.

The original `NETLOAD.EXE` helper and localhost-only `netstress.py` peer
were added. The GUI helper starts a patterned TCP download, then 64 UDP
threads attempting at most 512 nonblocking 1400-byte sends each. It logs
progress for 30 seconds, signals stop and joins every worker before
closing Winsock. The TCP receive has a 3-second timeout. The peer validates
the UDP datagrams and supplies a paced deterministic TCP stream. The
helper reads interface counters through the public Windows `GetIfTable`
API, using Platform SDK header declarations; no system binary is read.

`nettest.cmd` builds both GUI helpers with warnings as errors. The
tested staged NETLOAD binary SHA256 is
`538b564aa38893ce28033e0627b0197a7c2c2f7837a90a897e5f93ad847b2964`.

### Removal during established traffic

The monitor removed `cdcnet` after the peer had reported continuous TCP
sends and UDP traffic was active. The guest had verified 267160 TCP bytes
with no mismatches. It then reported Winsock 10054 (connection reset),
which is expected for the intentional removal. UDP returned 1303 accepted
sends and 31465 errors; the host sink received and validated 1238 datagrams.
Every one of the 65 worker threads joined successfully. The guest showed
the normal unsafe-removal warning and remained responsive.

Evidence: `out/net/cdcnet/NETREMOV.TXT`, `load-active-remove.png`,
`load-removal-warning.png`, `load-finished.png`, and E: `stress1.log`.
The capture has 284680 patterned bytes emitted by the netdev for that
TCP session; capture includes data the removed guest never received, so
the guest's verified count is the reception evidence.

### Bounded transmit pressure with the link intact

After replug, the same load test ran without removing the adapter.
The guest reported 2004 accepted UDP sends, 30764 errors and 265720
verified TCP bytes with zero mismatches. The TCP receive timed out with
Winsock 10060 during the flood. Windows interface counters rose from zero
transmit errors to 30041; the peer received and validated 2004 complete
UDP datagrams. All 65 workers joined. This exercises failure completion
under heavy pressure; it is not a lossless-load or fairness pass. Queue
occupancy was not instrumented, so these counters do not establish a
measured queue high-water mark. The source admission bound remains 32.

Evidence: `out/net/cdcnet/NETPRESS.TXT`, `pressure-result.png`, and E:
`stress2.log`. The capture contains a valid 283240-byte prefix for the
second load TCP session. The passive worker prioritizes queued sends;
fair scheduling and sustained throughput remain work for a later design.

### Recovery

Ordinary `NETTEST.EXE` networking immediately after the pressure test
passed all three ICMP replies and 32768 verified TCP bytes without
restarting/reinstalling the driver. Two more remove/replug cycles each
passed the same baseline test. This follow-up therefore exercised three
reconnects total, including the first removal during load. Evidence:
`out/net/cdcnet/RECOVER1.TXT` through `RECOVER3.TXT`, corresponding
`recover1-pass.png` through `recover3-pass.png`, and E: host
`recover1.log` through `recover3.log`.

The capture checker gained `--load` and byte-consistent TCP overlap
handling: retransmission may use a different segment length. A separate
host check accepted out-of-order segments and shorter retransmissions,
and rejected contradictory bytes, gaps and contradictory overlaps.
The existing baseline capture still passes `--m1`; descriptor host tests
still pass 107 assertions/80 mutations. This follow-up changed helpers
and their build script, not driver logic or INF. Earlier free/checked
driver-build evidence remains the matching binary evidence.

The final `E:\usb-wdm-free\wave2\w2kload.pcap` has 4857 frames and SHA256
`49a51781d10f623bf66a3bb5703a24727fad6a95c4493401732d5d5cb4606122`.
`testcap.py --m1 --load <capture>` passes: DHCP D/O/R/ACK, nine ICMP
requests/replies, three complete 32768-byte baseline TCP streams, 3242
intact UDP load payloads and the two valid interrupted TCP prefixes.

The guest reached the safe-to-power-off screen
(`out/net/cdcnet/load-poweroff.png`) and monitor `quit` closed QEMU.
PID21048 and helper peer PIDs30800/37060/8764/41140/38152 were all absent
afterward. TCP monitor/peer listeners were also absent. No owned guest
remains running; overlays, peer logs and captures remain on E:.

## XP x86 baseline with the unchanged NDIS 5 binary

A fresh `E:\usb-wdm-free\wave2\wxpcdc.qcow2` overlay of repository
`vm/wxp.qcow2` booted Windows XP Professional SP3 x86. QEMU used
`-display none -machine pc -cpu pentium3 -m 512 -vga std -usb`, the same
dedicated `usb-net` model/user netdev and local monitor 44340. No physical
USB device or alternate guest NIC was attached. TEMP/TMP, the vvfat
stage, overlay, monitor log and PCAP remained under E:.

### Default device description and local search

The virtual driver floppy was ejected before the USB network wizard ran.
XP described the unbound device as "RNDIS/QEMU USB Network Device". With
Windows Update declined, automatic local search found no suitable driver
and reached "Cannot Install this Hardware" because necessary software
could not be found. Evidence: `out/net/cdcnet/xp-rndis-name.png`,
`xp-native-result.png` and `xp-native-failed.png`.

This is a negative automatic-binding result for this XP image, not proof
that XP cannot operate RNDIS with another INF. The RNDIS product/location
description also does not prove that a native RNDIS data path ran.

### Package installation and ECM traffic

After reinserting the staged floppy, Back and advanced search of removable
media found `CDCTEST.INF`. XP displayed its normal unsigned-package
warning; Continue Anyway permitted this specific test installation. No
signature-enforcement or other system policy was disabled.

The driver was exactly the already tested free 0.0.0.3 binary, SHA256
`2c58226ec83cb5d39dd4c3e4ef442b912aac6bdd202e4200c0bb51197edfd421`.
No INF or source change was required. Its historical description still
says "QEMU/2000 ECM experiment". Device Manager reported "This device is
working properly", provider usb-wdm-free, version 0.0.0.3, unsigned
(`out/net/cdcnet/xp-start.png`, `xp-driver.png`). The location string still
said RNDIS/QEMU; the running driver explicitly discovers both descriptor
candidates and selects ECM configuration 1/data alternate 1. All finite
ECM ARP receive/cancellation initialization gates had to pass for this
successful miniport start.

XP obtained 10.0.2.15 by DHCP. Launching `NETTEST.EXE` through Explorer
passed three matching gateway ICMP replies and 32768 deterministic bytes
from the localhost-only TCP peer. `out/net/cdcnet/xp-nettest.png` and
`XPTEST.TXT` record the guest result; E: `xppeer.log` records the peer's
32768-byte send. No guest console was used and the test helper addressed
only QEMU's gateway and the localhost peer. The capture also contains
one separate guest background UDP/123 time-service packet to
52.148.114.188; this was not a driver download or helper test endpoint.

This establishes one XP x86 install/start/data baseline on Microsoft's
UHCI stack. XP removal under load, reset/power recovery, EHCI, x64 and
physical devices were not tested in this leg. The earlier 2000 stress
results are not promoted into XP claims.

The final `E:\usb-wdm-free\wave2\wxpcdc.pcap` has 90 frames and SHA256
`2483926673c9e94c8f95e3dfa1d272520961247f31ed3b583374262e9c4d2bca`.
`testcap.py --m1 <capture>` passes the ordered finite probes, DHCP
discover/offer/request/ACK, three ICMP requests/replies and one exactly
verified 32768-byte TCP stream.

Turn off computer initiated an orderly Windows shutdown
(`out/net/cdcnet/xp-shutdown.png`, `xp-poweroff.png`). QEMU exited on
guest poweroff; PID39228 and localhost peer PID32672 were absent afterward,
as were listeners 44340/44342. No owned guest or peer remains running.
The E: overlay, stage, logs and capture are retained.
