## Priority finding: Windows event-dispatch cadence

host-libusb.c 259-277 schedules libusb event polling on QEMU's virtual clock.
It selects 10 ms when request_count is nonzero, **one second otherwise**.
Only ordinary USBHostRequest allocation/free updates request_count
(392-401). ISO ring allocation/submission (547-778) does not use that
allocator or increment the counter. Therefore ISO-only traffic can retain
a one-second callback-dispatch cadence despite outstanding ISO requests.
This is a strong source-level candidate for periodic host callback bursts,
buffer exhaustion and a 200 ms feedback watchdog. It is not yet measured
in this exact installed fork. A regular control/bulk/interrupt request can
temporarily change the cadence, so incidental device traffic may change
observed behavior. Do not change the guest watchdog to conceal the issue.

## Packet sizing and callback semantics

host-libusb.c 551 explicitly leaves interval handling unresolved. Default
properties are four buffers of 32 packets (1770-1771). At HS interval 1,
32 packets span 4 ms; interval-4 feedback spans 32 ms. OUT startup waits
until two full buffers already precede the next packet before submission
(733-752), about 8.125 ms for uninterrupted interval-1 traffic.

Allocation sets transfer.length=MPS*32 (577). Each copied OUT packet changes
its descriptor length to guest size (659), but submit (760) retains the
original aggregate length. Endpoint 01 MPS112 with 32*24-byte payloads thus
has length3584, sum(packet lengths)768. libusb's KISO branch constructs
cumulative packet offsets (windows_winusb.c3565-3569) and passes the original
length to IsoWritePipe (3576). The last offset would be744 with a2840-byte
remaining tail. Whether the kernel treats that tail as last-packet data is
unverified; record those lengths rather than assume legal host scheduling.

QEMU also calls libusb_get_iso_packet_buffer_simple (652), whose contract
requires equal packet sizes; libusb.h2192 computes offset using packet0's
length times index. Mixed24/28-byte OUT packets can therefore select a
different offset from KISO's cumulative offsets. Uniform24 avoids that
specific stride mismatch, but not the aggregate-length discrepancy.

Guest ISO completion is distinct from host callback. QEMU's ISO dispatch
returns immediately after copy and emits usb_host_req_complete
(host-libusb.c1602-1610). EHCI usb_handle_packet (1469) is followed by IOC
raising and ACTIVE clearing (1512-1515). Host callback arrives separately
at usb_host_req_complete_iso (523), which returns OUT buffers to unused.
It does not emit ordinary req_complete and does not inspect aggregate or
per-packet status. For IN, a missing completed host buffer yields immediate
guest length0; received packets use actual_length without checking packet
status (684-692,661). A guest feedback ZLP can therefore reflect QEMU's
empty ring rather than a physical unchanged-value report.

Consequently host callback delay alone cannot explain zero completions for
guest iTDs already processed by EHCI. Trace the guest scheduling/IOC/URB
path independently from the host callbacks and client/audio-engine state.
Reported physical counters (data and feedback completions with a later
watchdog failure) already disprove a blanket absence of host activity.

## Concrete bounded trace plan

The installed executable's `-trace help` confirms these events exist:
`usb_host_req_data`, `usb_host_req_complete`, `usb_host_iso_start`,
`usb_host_iso_stop`, `usb_host_iso_out_of_bufs`, `usb_ehci_itd`,
`usb_ehci_periodic_state_advance`, `usb_ehci_irq`, `usb_ehci_usbsts`,
`usb_ehci_state`. Capture a short quiet interval before RUN and a bounded
RUN/STOP interval, with wall/virtual timestamps and QEMU/libusb identities.

1. **Guest scheduling:** EHCI periodic frame/list progress, iTD endpoint,
   MPS/mult, active transaction lengths and IOC; guest URB submitted,
   completed/cancelled counts and first completion status. Existing iTD
   trace does not expose all transaction words, so a source trace addition
   would be needed for exact per-microframe active/IOC values.
2. **QEMU copy:** req_data endpoint/size and immediate req_complete length;
   distinguish endpoint1 OUT from endpoint3 IN. These are guest transactions,
   not proof of host completion or physical audibility.
3. **Host submission:** enable usb-host `loglevel=4` for libusb diagnostics;
   record endpoint, transfer identity, aggregate length, packet count,
   min/max/sum lengths, final offset, submit result and monotonic timestamp.
   Existing QEMU ISO start/stop shows transitions only, not every submit.
4. **Host callback:** timestamp transfer status, all packet-status counts,
   actual lengths, inflight/unused/copy counts, and windows event-poll entry
   with request_count/next delay. One-second callback batches while ISO
   requests are inflight and request_count=0 would directly support the
   timer hypothesis. This requires explicit source-level diagnostics;
   ordinary req_complete must not substitute for it.
5. **KISO boundary:** selected backend/interface/alt/endpoint, NumberOfPackets,
   StartFrame/Flags, BufferLength, offsets and returned UrbHdrStatus,
   ErrorCount/per-packet status. libusb reports requested OUT lengths as
   actual lengths (windows_winusb.c3910-3914), so byte counts alone cannot
   establish successful physical OUT packets.

No tracing changes, QEMU rebuild, host driver changes or physical operations
were performed as part of this review. The owners of the active X4 and UVC
guests retain exclusive access to their devices and monitor ports.

## Independent candidate review

The separately owned candidate source at
`E:\usb-wdm-free\host-qemu\qemu-11.1.0\hw\usb\host-libusb.c`
was reviewed at SHA-256
`44bdad839d4093e1c0390930d7f9ec87d626043040ce31f7d2f3573c3fbd5765`.
This is an experimental QEMU host change, not a guest-driver change or
validation of the exact installed distributor fork.

The reviewed revision introduces a shared ISO submit helper. It increments
the Windows ISO count only after successful libusb submission, then
anticipates a 1ms event-poll deadline. Completion decrements the count
before checking whether its ring was already destroyed, preserving orphan
callback accounting. Ring destruction deliberately does not decrement or
free the still-libusb-owned transfer/buffer; the null-user-data completion
does the final free. Submit failure does not increment. Under the existing
main-loop serialization, timer scheduling cannot execute a callback between
counting and the subsequent inflight-list insertion.

Cumulative packet offsets and the summed OUT length are consistent with
the original MPS-sized allocation: each written length is capped at MPS.
Reset restores all descriptor lengths before reuse, and every completed
OUT buffer recomputes its aggregate length before submission. Separate IN
endpoint rings retain their original MPS*packet-count length. No new
blocking lifetime/offset defect was found in that revision. Required
regression cases were communicated to the owner: submit failure, mixed
24/28-byte payloads, reuse, fixed-size IN, orphan callbacks/count-to-zero
and preserving an earlier timer deadline. All-zero OUT/backend behavior
remains a separate edge case; it is not exercised by the X4 48kHz packets.

An earlier candidate also switched to QEMU_CLOCK_REALTIME. The independent
review flagged the upstream `include/qemu/timer.h` contract that this clock
should be used for work that does not change VM state; USB callbacks do
change device state. The owner removed that broader clock change before
runtime testing. The reviewed candidate retains QEMU_CLOCK_VIRTUAL while
adding the narrow ISO accounting/deadline changes. Source review and a
stubbed regression harness do not establish physical audio improvement.
