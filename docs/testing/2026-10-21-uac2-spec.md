## Explicit feedback and PCM packetization

UAC2 section 3.16.2.2 delegates explicit feedback encoding to USB 2.0
section 5.12.4.2. The base specification's printed pages 74–75 correspond
to PDF pages 102–103. Both pages were rendered for visual inspection;
text extraction was also used for searching. The checked facts are:

| Requirement | Implementation / result |
|---|---|
| Full-speed feedback is three-byte 10.14; high-speed is four-byte 16.16, expressed per frame or microframe respectively. | `uacrate.c` decodes these explicitly and scales by the data service interval. There is no guessed three-byte high-speed quirk. |
| A successful zero-length feedback payload may indicate an unchanged value. | Audit found transport rejected these and only refreshed its timeout for newly decoded values. The fix retains the last validated value and refreshes packet freshness for an unchanged packet only after initial valid feedback. Final runtime results must identify the tested build. |
| Type I packets contain whole audio slots; fractional slots accumulate until another complete slot is available. | Audio Data Formats 2.0 sections 2.3.1.1 and 2.3.1.5, printed/PDF pages 13–15. `uacrate.c` uses integer remainder/phase accumulation and emits multiples of the complete frame size. |
| Type I PCM uses signed two's-complement samples; subslot and resolution describe their representation. | Audio Data Formats 2.0 sections 2.3.1.3–2.3.1.7.1, pages 15–16. This M1 path admits stereo, two-byte subslots, sixteen significant bits at 48 kHz only. |

`rtest.cmd` passed 46,067 host checks covering rational 44.1/48 kHz
packet counts, interval scaling, feedback decoding and rejection, endpoint
capacity, phase continuity, and legal zero-frame low-rate intervals.
The PCM subslot and format tables on PDF pages 15–16 were also rendered
and visually checked. The planner's acceptance window of nominal rate ±12.5% is an experimental
driver policy, not a tolerance mandated by the USB specification.

These checks are a scoped implementation review, not USB certification.
Descriptor and class-control findings are recorded separately in the
[controls audit](2026-10-21-uac2-controls-spec.md); VM reports establish
which binaries actually ran.

## Windows transfer contract cross-check

Microsoft's [URB contract guidance](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/usb-client-driver-contract-in-windows-8)
requires high-speed packet counts to be multiples of the packets per
1 ms frame, calculated as eight divided by the polling period. The X4
data endpoint uses interval 1 (period 1): 32 packets satisfy the multiple
of eight and cover 4 ms. Feedback interval 4 gives period 8: eight packets
satisfy the multiple of one and cover 8 ms. Both periods are supported
by the documented Windows contract. This arithmetic does not establish
that every older target stack behaves identically under load.

The [URB isochronous structure documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/usb/ns-usb-_urb_isoch_transfer)
defines returned packet length for IN transfers. The transport therefore
uses its scheduled OUT byte counts for cyclic position, while separately
counting packet failures. A progressing cursor alone cannot establish
successful sound delivery.
