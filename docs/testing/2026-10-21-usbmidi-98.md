# USB MIDI Windows 98 readiness, 2026-10-21

No project MIDI driver has passed Windows 98 SE in this work. The physical
UM-ONE mk2 startup/open/close evidence on Windows 7 is separate. The tested
NT v4 SYS is unchanged:
`B34E751044FA14DCBB54077CC2001484D63E2BAC52CC40C14819006FF67BEDF3`.
No SYS was staged, installed, or renamed by this investigation, and no VM or
physical USB device was operated by this agent.

## Concrete blockers and evidence

| Boundary | Evidence and status |
|---|---|
| Cleanup API imports | The current SYS imports `IoAllocateWorkItem`, `IoQueueWorkItem`, and `IoFreeWorkItem`. Win98 WDM.H declares none of these. Microsoft explicitly states that [IoAllocateWorkItem is unavailable in Windows 98](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-ioallocateworkitem). An INF edit alone cannot make this NT binary load on 98. |
| Device and image lifetime | Replacing the calls with `ExQueueWorkItem` loses the device-associated lifetime guarantee described by [Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/nf-wdm-exqueueworkitem). Final Stream and Mini release must execute passive teardown, including USB cancellation and a thread join. Elevated Release cannot directly run that teardown. |
| INF installation | Current `usbmidi.inf` supplies `[UM.NT]`, `.NT.Services`, and `.NT.Interfaces`, without a Win9x `[UM]`/loader registration. Separate `um98.inf` records the proposed undecorated sections, `*NTKERN` DevLoader, `NTMPDriver`, WDMAud MIDI registration and interfaces. It deliberately names **unbuilt `usbm98.sys`**, not the NT binary. It is an installation-contract draft, not an installable package. Its own-source precedent is `src/audio/uac2/uac2wdm.inf`; no kit sample INF was used. |
| Lifecycle diagnostics | Current NT diagnostic code uses `OBJ_KERNEL_HANDLE`, absent in the Win98 NTDEF header. A future 98 profile must omit the NT service-key diagnostics or establish a supported equivalent. `IoOpenDeviceRegistryKey`/`ZwSetValueKey` declarations alone do not validate equivalent registry paths. |
| PortCls imports | All six current MIDI imports appear in the recorded [Win98 PortCls export table](exports/w98port.txt): `PcInitializeAdapterDriver`, `PcAddAdapterDevice`, `PcNewPort`, `PcRegisterSubdevice`, `PcNewServiceGroup`, and `PcRegisterAdapterPowerManagement`. Export presence does not prove ABI/lifetime behavior or device startup. |
| Other kernel imports | [Existing export audit](2026-10-21-exports.md) did not inspect NTKERN/VMM32 exports. The pristine offline raw file listing contains `WINDOWS/SYSTEM/VMM32.VXD` and no separate NTKERN.VXD or NTOSKRNL.EXE. Only directory metadata was listed in this follow-up; no VMM32 body, code, embedded modules or dump was inspected. Actual export availability remains unverified. |
| User helper and OS exposure | WinMM MIDI APIs exist in the intended target contract, but current installer/CM reporting paths and runtime dependencies require independent 98 testing. No Win7 helper result is a 98 WinMM exposure test. Actual parent/child binding, MIDI enumeration, open/close, traffic and safe reconnect remain untested. |

## Bounded cleanup research

New original `umclean.c`/`.h` uses one dedicated cleanup thread, a protected
FIFO, event wakeup, one device reference per work item, and a saved PortCls
unload wrapper. Callbacks may free their own item/context; all callback
arguments are copied before invocation. The unload wrapper drains the queue
and waits on the actual referenced thread object, rather than trusting a
pre-exit event. Microsoft requires [driver-created threads to terminate before
unload](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/releasing-driver-allocated-resources).

**This prototype is not a safe replacement yet and is not integrated into
the MIDI driver.** If the I/O manager invokes DriverUnload synchronously on
the cleanup worker's last FDO dereference, the unload routine would join its
own thread. Published documentation guarantees a system-thread context, not
a different system thread. As a compatible-source counterexample to assuming
all unloads are asynchronous, ReactOS
[`device.c`](https://github.com/reactos/reactos/blob/master/ntoskrnl/io/iomgr/device.c)
`IopDereferenceDeviceObject` (lines 429–446 at inspection) calls
`IopUnloadDevice`, whose automatic unload path invokes `DriverUnload` directly
(line 422). This concerns ReactOS's device-I/O reference accounting; it does
**not** establish how Windows 98 NTKERN handles this specific object-manager
reference. No ReactOS implementation was copied or adapted into the prototype.

The source requires explicit `UM_CLEAN_RESEARCH` to compile. Neither existing
driver build nor release/stage script includes it. A future integration needs
a proven callback/image lifetime mechanism, potentially a separate resident
compatibility component, or a documented target guarantee that rules out the
self-unload case. Merely deleting the thread join, leaking a device reference,
or assuming Release is always PASSIVE would not resolve it.

## Checks actually run

`powershell -NoProfile -File src/audio/usbmidi/um98chk.ps1` passed:

- **807 host contract checks**, using the actual dispatcher source and real
  Win32 threads with mocked WDM lock/event/object primitives. This includes
  258 self-freeing callbacks, a blocked callback with 257 queued at unload,
  true thread termination before chaining the saved unload, allocation/thread
  creation failures, duplicate initialization refusal and device references.
- A separate child-process negative case invokes unload from the callback.
  The mock wait detects the self-join and exits with expected code 77. This
  proves the prototype's missing lifetime assumption, not a target OS defect.
- The production C source compiled `/W3 /WX` against the **actual Win98 WDM
  declarations**, with MSVC 6. Only explicitly named primary headers are copied
  from `tools/win98ddk-extracted/all/INCS_DDK`: WDM, NTDEF, NTSTATUS, BUGCODES,
  NTIOLOGC and BASETSD. CRT/packing headers come from named installed toolchains.
  No kit sample tree is searched or read.
- The old header compile exposed two real source differences and they were
  removed from the research code: `RemoveHeadList` is a statement macro, and
  `InterlockedCompareExchange` has a pointer signature. The prototype uses
  `RemoveEntryList` and the declared LONG `InterlockedExchange` instead.
- Its own object symbol listing contains no `Io*WorkItem`, `ExQueueWorkItem`,
  or `OBJ_KERNEL_HANDLE` dependency. This is a compile/symbol check, **not** a
  target kernel export or runtime gate.

The Win98 header declares `PsCreateSystemThread`/`PsTerminateSystemThread`
(WDM.H lines 7063/7075), events, spinlocks, pool allocation, current thread,
object references and `ZwClose`. Declarations make the research source
compile; the test does not claim these calls have been exercised in NTKERN.
Ignored reports and objects are under `out/audio/usbmidi/98check/`.
