# 98 SE legs of uvc98 and uac2, and the first xHCI98 legs of usbmidi and uvc98, 2026-10-22

Owner rule, 2026-10-22: every driver works on Windows 98 SE at minimum,
`uvc98` and `uac2` above all, under NUSB's EHCI and under xHCI98
(`AGENTS.md`). This record has the first 98 SE legs of `uvc98` and `uac2`
and the first xHCI98 legs of `usbmidi` (2000 SP4 and 98 SE) and `uvc98`
(2000 SP4). Development legs in QEMU, not a release and not "Tested".

## Rig

## Making uvc98 and uac2 load on 98 SE

Neither had run on 98 SE. Linking their objects against the 98 SE DDK's
`wdm.lib`, `stream.lib`, `portcls.lib` and `ks.lib` (as `usbmidi`'s
`probe98` does) named the NTKERN gaps:

- uvc98 M2: `IoAllocateWorkItem`, `IoQueueWorkItem`, `IoFreeWorkItem`,
  `ZwWaitForSingleObject`, `MmMapLockedPagesSpecifyCache`.
- uac2: `IoAllocateWorkItem`, `IoQueueWorkItem`, `IoFreeWorkItem`.

Fixed in `8de91b2` and `c2f5cee` (executive work items, an Exited-event
thread join that waits the thread object only on WDM 1.10 systems,
`MmMapLockedPages`); both link probes then resolve every import. uvc98
also gained `UVCM298.INF`, the 98 SE / ME INF, and both camera INFs list
the `MI_00` child, because xHCI98 splits the composite Brio 100 itself
(IAD) on 98 SE and on 2000. Host tests after the change: uac2 `test`,
`ctest`, `mtest`, `rtest`, `streamtest` PASS, all four builds PASS;
uvc98 `test`, `worktest`, M1 and M2 builds and gates PASS.

`M1CAP` also needed a 98 SE fix: 98 SE's `SetupDiGetDeviceRegistryProperty`
returns `SPDRP_HARDWAREID` as one `REG_SZ` and reports the buffer size as
the length, and its hardware ID list holds only the `&REV_xxxx` form, so
the 98 SE runs name `USB\VID_046D&PID_094C&REV_9915&MI_00`.

## uvc98 on 98 SE, xHCI98 3.1.0.0, Brio 100 (real device via VM)

Overlay `m98a` (xHCI98 installed). Install: the Add New Hardware wizard
found `UVCM298.INF` for the `MI_00` child; the KS and capture files that
`Needs=KS.Registration,KSCAPTUR.Registration` pulls were looked for on the
INF's own disk and skipped (the `LayoutFile` line that should send them to
the Windows CD was added after this install and is not yet tried).
Trace: `M1_DRIVER_ENTRY`, `USB_OPEN 0`, 9 formats from the descriptors,
INITIALIZE and stream info complete.

| Run | Size | Result | Readings |
|---|---|---|---|
| 1 | 160x120 | **PASS**: three complete changing frames, STOP and close return | 3 frames, 25 dropped (19 with the error bit), error-bit payloads 406; stop: `UVU_JOINED` (Exited join), `UVU_ALT0 0` |
| 2, 3, and one on a later boot | 320x240 | **FAIL** (3 of 3): READ returns error 1784, no frame | alternate 4 (640 B); 74-76 frames all dropped, each carrying the camera's error bit (675-679 error-bit payloads); resubmission gaps 28, 29, then 1 |
| 4 (new boot) | 160x120 | **PASS** | 3 frames, 22 dropped |
| 5 (after unplug and replug) | 160x120 | **PASS** | driver reloaded; 3 frames, 19 dropped |
| unplug, idle | - | **PASS** | SURPRISE_REMOVAL, UNINITIALIZE, `USB_CLOSED`, guest alive |

Frames: `frame3.png` shows a plain wall, as the 2000 runs did. The
320x240 failure is not explained: gaps fell to 1 in the last run, yet the
camera flagged every payload as an error. On 2000 SP4 under Windows'
EHCI the same size passed (`2026-10-22-uvc-m2.md`). Whether this is
xHCI98's isochronous IN scheduling, QEMU's xHCI with `usb-host`, or the
host load is open.

**Guest freeze at plug (not this driver):** on three boots after the
first, plugging the Brio 100 froze 98 SE (CPU looping in VMM code, EIP
C000xxxx; xHCI98 kept polling its controller). It froze the same way with
`uvcm2.sys` renamed away (the driver never loaded), and did not freeze
with 98 SE's own `USBAUDIO.SYS` renamed away. So the Brio 100's
microphone function under 98 SE's in-box `usbaudio.sys`, on xHCI98
3.1.0.0, freezes the guest; the later uvc98 runs above were taken with
`USBAUDIO.SYS` renamed (`.BAK`) in that overlay. After the first session
a Windows restart also wedged QEMU in real mode at the boot logo (the
known 98 warm-reset hang in QEMU).

## uac2 on 98 SE, xHCI98 3.1.0.0, X4-layout simulator (emulated)

`uacemu.py` over `usb-redir`, the captured X4 configuration. xHCI98
split the composite; the `MI_03` function first matched the stock
`wdma_usb.inf` (`USB\CLASS_01`), so `uac2wdm.inf` was chosen with Have
Disk (it is listed as compatible). KS/WDM audio file copies skipped as
above. Results:

- **Start: PASS.** Device Manager: "This device is working properly".
  The driver's registry record: `Uac2M0Stage` 12 (every PortCls step,
  through `PcRegisterAdapterPowerManagement`), `Uac2M0Status` 0, the full
  configuration descriptor and parse recorded. So PortCls over xHCI98's
  function PDO works on 98 SE (design section 14's M0 question).
- **Playback: FAIL, not reached.** `UACPLAY` lists `waveOut devices=0`,
  also after a restart, although the class key carries the `wdmaud.drv`
  wave and mixer entries and `AssociatedFilters=wdmaud`. Why WDMAud does
  not expose the filter is open (next: whether sysaudio sees the wave
  filter's interfaces and accepts its data range on 98 SE).
- **Idle unplug: PASS** (guest alive).
- The other X4 functions (HID, CDC) raised wizards that were cancelled.

## usbmidi under xHCI98 3.1.0.0 (emulated: the MIDI simulator)

**2000 SP4** (overlay `m2k1`): install from the staged INF, then:

- `multi` profile, Full Speed: WinMM lists IN/OUT "MIDI 2x2 SIM Port A"
  and "Port B"; `MIDITEST 0 0` and `1 1` 355/355 PASS, cleanup complete;
  `0 1` receives nothing (cable isolation); stress 5 s 17398/17398.
- Unplug with both ports streaming (two stress helpers): the helpers ran
  on and closed with cleanup complete; trace REMOVE, shutdown, release
  and DriverUnload (`s1`..`s5`, `>unload`). **PASS** (the 2000 rerun of
  the stop path owed by `e4fd9e4`).
- Same-port replug: loads again, both loopbacks PASS, no restart.
- New port: "restart your computer" asked, as under UHCI; after the
  restart both loopbacks PASS.
- `multi` profile at **High Speed** (`midiemu.py --speed high`, 512-byte
  bulk): loopbacks PASS, stress 5 s 14232/14232.
- Shutdown with the device attached: safe-off.

**98 SE** (overlay `m98a`): `MIDITEST stage` staged the INF as `oem0.inf`;
the plug asked for `ks.cat`, `ksproxy.ax` and the other KS files (skipped)
and `usbmidi.sys` was copied by hand, as under UHCI. Then:

- `multi`, Full Speed: ports listed; `0 0` and `1 1` 355/355 PASS; `0 1`
  nothing (isolation); stress 5 s on port B 3554/3554. **PASS.**
- Unplug after use: REMOVE, release and DriverUnload, no fault.
  **PASS** (the 0E fault under UHCI before `e4fd9e4` does not recur).
- Same-port replug: the driver loads and starts, but every
  `midiInOpen`/open fails with `WinMM failure=4` (MMSYSERR_ALLOCATED) on
  both ports. **FAIL** - the input-after-replug defect of the UHCI leg,
  here on the same port.
- Second unplug: clean unload.

## uvc98 on 2000 SP4, xHCI98 3.1.0.0, Brio 100 (real device via VM)

Overlay `m2k1`; the wizard installed `UVCM2.INF` for the `MI_00` child
(unsigned-driver prompt answered Yes). `USB_OPEN 0`, 9 formats; the pin
connects at 160x120. **FAIL** twice: no frame (READ error 1784);
9672 and 21424 packets of which 9464 and 21040 empty, two FID flips,
58 error-bit payloads; the stop's alternate-0 select failed
(`UVU_SELECT_USBD C0000004`, `UVU_ALT0 C0000001`). Unplug: SURPRISE_REMOVAL,
UNINITIALIZE, `USB_CLOSED`; Windows then reached safe-off (the WDM 1.10
thread-object join ran). The same camera and build passed 160x120 on 98
SE under xHCI98 minutes earlier, and 2000 under Windows' EHCI passed
before (`2026-10-22-uvc-m2.md`), so this points at xHCI98 on 2000 (an
isochronous IN stream that stays empty, and a refused alternate-0 select)
- for xHCI98 to read, not fixed here.
