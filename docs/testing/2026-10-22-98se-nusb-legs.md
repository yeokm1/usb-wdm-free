## Below the drivers: how NUSB presents a composite device

Two facts decide how each driver binds under NUSB; both were read from the
guest's `HKLM\Enum\USB` export.

- **A class 00 composite** (the MIDI simulator, `FFFF:0002`, AC + MS
  interfaces) gets `USB\COMPOSITE` among its compatible ids, and 98 SE
  binds its own composite parent from `USB.INF`, which is `USBHUB.SYS`.
  The NUSB image has no `USBHUB.SYS`: 98 SE Setup places it only when it
  finds a USB controller it knows, and this image was installed on a
  machine with none (the same cause xHCI98 found in its task 13-E.1). The
  devnode installed, nothing ran, and the device was never configured
  (the simulator saw only descriptor reads). With `USBHUB.SYS` copied from
  the 98 SE CD (`BASE4.CAB`, SHA-256 `e898b75f...fc31`) into
  `SYSTEM32\DRIVERS` and a restart, the parent split the device and
  `USB\VID_FFFF&PID_0002&MI_00` appeared. A real 98 SE PC with a USB
  controller has the file; the image does not. The earlier NUSB leg of
  `usbmidi` (`2026-10-22-usbmidi-m1.md`) ran on an image that had it.
- **A class EF/02/01 device** (IAD: the X4 and the Brio 100) is not split
  at all. NUSB's hub gives the whole device the compatible ids of its first
  interface only - for the X4 `USB\CLASS_03&SUBCLASS_00&PROT_00`,
  `USB\CLASS_03&SUBCLASS_00`, `USB\CLASS_03` (HID) - and no
  `USB\COMPOSITE`, so no composite parent loads and no `MI_xx` function
  exists. A driver for such a device under NUSB must bind the whole device
  (`uvc98`'s INF already lists `USB\VID_046D&PID_094C`; `uac2` does from
  `1344887`). The device's other functions (the Brio's microphone, the
  X4's HID and CDC) stay unbound, so 98 SE's `usbaudio.sys` never meets
  the Brio's microphone under NUSB.

### Whose failure: the driver's or the vehicle's (build 6 diagnostics)

Build 6 (`aa00947`; wdmx86 free `uac2wdm.sys` SHA-256 `0e318514...6467`
for the xHCI98 runs, `46f669fd...d166` for the NUSB runs, same source)
adds schedule diagnostics to `Uac2UsbStats`: the bus driver's current
frame at stream start (`URB_FUNCTION_GET_CURRENT_FRAME_NUMBER`), the
`StartFrame` the bus gave the first and last feedback URB and the first
data URB, and how every feedback packet came back (4 bytes, zero length,
failed, with the failure codes).

The driver's feedback request is the same on every stack: two URBs of 8
packets of 4 bytes, `USBD_START_ISO_TRANSFER_ASAP`, IN with short
transfers allowed, on the pipe of endpoint 0x83 (`wMaxPacketSize` 4,
`bInterval` 4, so one transaction per 8 microframes); the data pipe has
four URBs of 32 packets. What differs is how each bus driver maps a
packet to bus time, and what comes back:

| Run (98 SE, QEMU) | Frames per 8-packet feedback URB | Feedback packets with 4 bytes | Zero-length (success) | Failed | Plays |
|---|---|---|---|---|---|
| xHCI98 3.1.0.0, `qemu-xhci` | 8 (1019 URBs over 8191 frames): one packet per service interval | 8063 of 8152 (99 %) | 73, all at the stream's start | 0 | 9 of 10 PASS |
| NUSB 3.3, `usb-ehci` (`maxframes` 128), passing play | 1 (4894 URBs over 4891 frames): one packet per microframe | 288 of 39152; 288 of 4894 frames (6 %) | 38803 | 45 (`C0020000`, not accessed) | 2 of 3 PASS |
| NUSB 3.3, failing play | 1 (112 URBs over 109 frames) | 0 of 896 | 878 | 2 (`C0020000`) | - |

The xHCI98 failure was the first play after a boot and three cancelled
wizards; its statistics were overwritten by the next run, so its cause is
not read.

Readings that place the NUSB failure:

- **The driver's request is not the difference.** The same URBs pass on
  xHCI98 (above) and on Windows 7's `usbehci` over the same QEMU
  `usb-ehci` and simulator (`2026-10-21-uac2-vm.md`). Making the feedback
  ring four times longer (build 7: four URBs of 32 packets, 16 frames in
  flight under NUSB) did not help: 0 of 4 plays, 0 four-byte packets. It
  was reverted.
- **NUSB does schedule the feedback endpoint.** The earlier traces that
  showed no iTD for endpoint 3 covered the time before the stream started
  (the simulator logged the stream's start after the trace window). A
  trace taken only while the stream ran (2 s, `ev\nv1-itd-streaming.txt`)
  shows 252 iTDs for endpoint 3 (`mplen 4`) and 252 for endpoint 1: one
  per processed frame for each. That resolves the earlier contradiction
  (no endpoint 3 descriptors, yet 568 valid values).
- **QEMU processed only one frame in eight.** 2 s of streaming should
  visit about 2000 frames; QEMU's EHCI fetched 252. In every traced run it
  ran more than 128 frames behind the guest and then skipped the backlog
  (`usb_ehci_skipped_uframes`, steps of 130-200 microframes). A skipped
  frame's transactions are never offered to the device. Under NUSB a
  feedback URB covers exactly one frame, so a skipped frame is a lost
  feedback URB; under xHCI98 a URB covers 8 frames and QEMU's xHCI model
  does not skip.
- **QEMU's `usb-redir` returns empty isochronous IN packets until its
  buffer is prefilled** (`hw/usb/redirect.c`, `usbredir_handle_iso_data`,
  read 2026-10-23): it waits for 60 ms of packets, counted as
  `8000 / bInterval` packets per second, so 120 packets for this
  endpoint (the simulator logged the stream with `pkts_per_urb` 20,
  `no_urbs` 6, which matches), and it starts that wait again after every
  underrun. Both stacks see this at stream start (the 73 zero-length
  packets under xHCI98). With `maxframes=512` QEMU stops skipping but runs
  up to 512 frames behind and catches up in bursts, emptying the buffer
  each time; that run delivered no feedback at all (0 of 3 plays).

Conclusion: in these runs the feedback data is lost between the
simulator and NUSB's EHCI driver, in QEMU's EHCI model (skipped and
bursty frames on a saturated host) and `usb-redir`'s prefill. The driver
is the same one that passes on xHCI98 and on Windows 7's EHCI driver.
What is not shown: how NUSB's EHCI driver reports a transaction the
controller never touched (most of the 38803 zero-length packets could be
either "touched, no data" or "never touched"). Only a real controller
settles that.

**Bench steps for the owner (real EHCI controller, NUSB 3.3, Sound
Blaster X4):**

1. 98 SE on a PC with a USB 2.0 EHCI controller and NUSB 3.3 installed
   (the PC's own USB 1.1 companions mean `USBHUB.SYS` is present).
2. Plug the X4 into a root port (no hub). In the Add New Hardware wizard
   for the device ("USB Human Interface Device"), search the floppy or
   folder with `uac2wdm.inf` and `uac2wdm.sys` (build 6 or later); skip
   the KS/WDM audio files it asks for if the CD does not have them.
3. Check `HKLM\System\CurrentControlSet\Services\Class\MEDIA\<n>`:
   `MatchingDeviceId` `USB\VID_041E&PID_3278`, `Uac2Build` 6 or later,
   `Uac2M0Stage` 12 after plug.
4. Run `KS98 sys mm` (expect `SysAudio devices=1`, `waveOut=1`), then
   `UACPLAY /playexit` five times; listen for the 440 Hz tone.
5. After each play, export the `MEDIA\<n>` key and decode `Uac2UsbStats`
   (32-bit words: `GoodFeedback` is the 7th, then the build 6 fields from
   the 23rd: current frame, first and last feedback `StartFrame`, first
   data `StartFrame`, 4-byte, zero-length and failed feedback packets,
   four failure codes and their counts). A healthy stream shows one
   4-byte packet per frame (`Fb4` about equal to the number of feedback
   URBs) and `LastStatus` 0.
6. Unplug idle, replug and play, unplug during playback.

If the real controller also returns almost no 4-byte feedback packets,
the cause is NUSB's EHCI driver and the owner's open question (play at
the nominal 6.0 when feedback never arrives) decides what the driver
does. If it returns one per frame, the QEMU result above stands as a
vehicle limit.

Open, separately: one guest hang when the device was unplugged while
