# AX179F (`ax88179`) on Windows 98 SE and ME under xHCI98, 2026-10-22

The first guest legs of the `ax88179` package (`ax179f.sys`, NDIS 5.0 x86
with a WDM lower edge). The device is real: the owner's ASIX AX88179
(`0B95:1790` rev 0100) passed through to the guest. Kind: **real device
via VM**, never a "Tested" cell. Nothing is released.

## Setup and the owner's approval

The owner approved the passthrough (2026-10-22) for these legs, on
`qemu-xhci` with xHCI98: the 2026-10-21 Windows 2000 run on `usb-ehci`
showed QEMU's EHCI presenting the chip's SuperSpeed descriptors at
480 Mb/s ([ax88179-2k-descriptors](2026-10-21-ax88179-2k-descriptors.md)),
which is not a real USB 2.0 path. The owner plugged the dongle in and
bound it to WinUSB on the host himself; nothing was installed or changed
on the host here. The cable was connected to the owner's LAN (a DHCP
server and gateway on it).

- Kit `E:\usb-wdm-free\net9x\`, `scripts\launch-ax.ps1`: stock QEMU
  11.1.0 (TCG, `-smp 1 -m 256`), `qemu-xhci,p2=4,p3=4`, and
  `-device usb-host,vendorid=0x0b95,productid=0x1790,id=ax,bus=xh.0`
  (the 2026-10-21 run's usb-host line, moved from `usb-ehci` to
  `qemu-xhci`). Before each leg the script printed QEMU's own `info
  usb`: "Device 0.1, Port 1, Speed 5000 Mb/s, Product AX88179, ID: ax".
  QEMU also printed `libusb_kernel_driver_active: -12 [NOT_SUPPORTED]`
  (libusb on Windows has no kernel-driver query), with no other error.
- Guests: overlay `ax1.qcow2` of `w98-hcd310` (98 SE with xHCI98
  3.1.0.0), and the ME overlay of `me-hcd310` (ME with xHCI98 3.1.0.0)
  already used for cdcnet.
- Driver: ndis5 **trace** build of `src/net/ax88179`, installed from
  `AX179F98.INF` (`0eb93f76...c653`) on the floppy.
- No program served the guest from the host: traffic is DHCP from the
  LAN and `ping` (the guest's own) to the LAN gateway.

## Install (98 SE)

Add New Hardware found "AX88179", chose `A:\AX179F98.INF` ("ASIX AX88179
USB 3.0 Gigabit Ethernet (AX179F)"), then asked for the disk: the copy
dialog offered `C:\WINDOWS\CATROOT` as the source and needed `A:\` typed
in (the same prompt cdcnet's 98 install records). The miniport then
started at once: probe of configuration value 1, chip start (version
179, 22 vendor requests), "super speed USB", MAC `00:0e:c6:c2:57:ae`
(the chip's own), "link 1, 1000 Mb/s full duplex". Restart as a cold
start; the halt at that shutdown completed.

## The receive defect, and its fix (`d6f514e`)

The first cold boot (`a2`): DHCP failed (APIPA 169.254.214.99, "DHCP
Server Unavailable"), and the halt counted `tx 25/1 rx 0` and 178
dropped frames: every received frame was refused. A trace-only sample of
refused transfers (raw words) showed, for a broadcast ARP:

```
ee ee | ff ff ff ff ff ff 94 83 c4 a6 41 dc 08 06 ... (60-byte frame) | 2 pad
header 0x003e8800: length 0x3e = 62 = 2 (pseudo header) + 60, no FCS
trailer 0x00400001: 1 record, headers at 64
```

The driver verified and stripped a 4-byte FCS from every record
(`AxFrameReceiveFcs`), because the 2026-10-21 host-side run had seen the
same chip forward it. Under the driver on 98 SE the chip forwarded none,
so every CRC check failed. `AxFrameReceiveAuto` now strips the last four
bytes only when they are the frame's IEEE CRC32 and otherwise delivers
the record whole; the chip's own CRC-error drop (`AX_RX_CTL_DROPCRCERR`)
keeps bad frames out. Host tests: the FCS-present, FCS-absent and
bad-FCS aggregates pass (`test.cmd`). Why the chip forwards the FCS in
one setup and not the other is not known; the per-frame rule serves both.

### The mode made explicit (`5bb6c41`, owner)

The owner asked for the mode to be set and read back, not guessed.
`AxStart` now writes `AX_RX_CTL` (Linux's reset bits, `0x3aa`) and reads
it back; the driver logs "rx config: wrote 3aa, read back 3aa". No
source this repository uses names an FCS-forwarding bit (Linux v6.12's
`AX_RX_CTL_*` has none; ASIX's public datasheet has no MAC register
map and only says forwarding is optional), so none is set and the mode
is "no FCS", as Linux assumes. The per-frame CRC32 check is kept only
as a safety net: a frame that arrives with its FCS is stripped, counted
and logged (first one, and the count at halt).

Re-run on 98 SE, xHCI98, SuperSpeed (`a5`): read-back `3aa`; DHCP
lease; pings at 0, 32, 86, 1430, 1472 and 4000 bytes 60 of 60; halt
"0 dropped frames, 0 with an FCS", "tx 124/1 rx 121". **PASS.**

## Legs, after the fix

### 98 SE, xHCI98 3.1.0.0, SuperSpeed (`a4`)

- DHCP: lease from the LAN (192.168.1.166/24, gateway 192.168.1.100).
- `ping -n 10 -l <size>` to the gateway at 0, 32, 86, 1430, 1472 and
  4000 bytes (4000: IP fragments): 60 of 60 replies, 7-21 ms (61 ms at
  4000). **PASS.**
- Removal under traffic (`ping -n 60 -l 1472` running, `device_del ax`
  after 20 s, `device_add` of the same usb-host line 20 s later): the
  driver reported the device gone and halted ("tx 140/4 rx 124", no
  malformed transfers, no dropped frames), the replugged device
  initialized again at SuperSpeed with link, and a new DHCP lease came
  at once. The ping that was running when the device went did **not**
  recover (17 replies, then 43 x "Destination host unreachable" to the
  end, also after the replug); a new `ping -n 10 -l 1472` after the
  replug: 10 of 10. Recovery of the driver and adapter: **PASS**;
  recovery of an application running across the replug: not shown (open
  point below).
- Shutdown: halt clean ("halted: tx 47/1 rx 35").

### ME, xHCI98 3.1.0.0, SuperSpeed (`x1`, `x2`)

- Install: the automatic search found `A:\AX179F98.INF` without a disk
  prompt; the miniport started at once (same trace as 98 SE). Restart
  cold. ME then asked for a network logon (empty password accepted).
- DHCP lease (same address and gateway); pings at the six sizes: 60 of
  60. **PASS.**
- Removal under traffic: as on 98 SE: gone, halt ("tx 146/4 rx 111"),
  re-initialized at SuperSpeed; the running ping did not recover (18 of
  60), a new ping after the replug 10 of 10.
- Shutdown: ME powered off without halting the miniport (as with
  cdcnet on ME).

### 98 SE, NUSB 3.3 EHCI, High Speed (`an2`, `an3`)

The owner put the dongle (its own USB 3.0 hub and the AX88179) behind a
USB 2.0 hub (2026-10-22 ~19:55) and re-checked its WinUSB binding there;
a first launch before that re-check showed only QEMU's unopened
placeholder ("USB Host Device", 1.5 Mb/s) and was quit. Then
`launch-ax.ps1 -Guest n98`: a fresh overlay of `w98-nusb` (98 SE with
NUSB 3.3), the usb-host line on QEMU's `usb-ehci`, only the Ethernet
function's id passed. QEMU's `info usb`: "Device 1.1, Port 1, Speed
480 Mb/s, Product AX88179".

- Install: Add New Hardware first installed NUSB's EHCI driver for the
  controller (`C:\WINDOWS\INF\USB2.INF`, "Intel 82801DB/DBM USB2
  Enhanced Host Controller"), then the AX88179 from `A:\AX179F98.INF`
  (the same disk prompt as under xHCI98, answered `A:\`). The miniport
  started at once: "high speed USB", read-back `3aa`, link 1000 Mb/s,
  bulk-in length 24576.
- **The FCS safety net fired** in this first session: "rx: frame
  arrived with an FCS ... stripped", and 142 frames with an FCS by the
  halt at the install restart (0 dropped). In the next session (`an3`,
  after a cold restart of the guest, the dongle powered throughout) and
  in every SuperSpeed session after `d6f514e`: 0. So the same chip with
  the same receive configuration forwards the FCS in some sessions and
  not in others; the sessions that had it (this one, and the 2026-10-21
  host run) were the first after the dongle was plugged in. Some chip
  state the driver does not set decides it; the safety net covers both.
- `an3`: DHCP lease (192.168.1.166, gateway 192.168.1.100); pings at 0,
  32, 86, 1430, 1472 and 4000 bytes 60 of 60 (14-27 ms; 70-103 ms at
  4000). **PASS.**
- Removal under traffic: gone, halt ("tx 126/3 rx 214"), re-initialized
  at High Speed on the new port with read-back `3aa`; the running ping
  did not recover (17 of 60, as under xHCI98), a new ping after the
  replug 10 of 10. Shutdown halt clean ("tx 47/1 rx 23"). **PASS** for
  the driver; the running-application point stays open.

## Open points and what is owed

- **The 98 SE EHCI leg (NUSB 3.3)**: run above, with the dongle behind
  a USB 2.0 hub. Both 98 SE gates (NUSB EHCI, xHCI98) have now passed
  in a VM with the real device; the open points below remain.
- **FCS forwarding varies by session** (above): the register or state
  that decides it is not known; worth finding before a release.
  Follow-up: [ax88179-fcs](2026-10-22-ax88179-fcs.md) (a settle cycle
  at start, unverified until a physical replug; an FCS is now a logged
  anomaly).
- **ME EHCI**: ME has no NUSB; its USB 2.0 stack would be SweetLow's
  (in xHCI98's `tools\sweetlow-extracted`). An ME image with it is for
  later, after the other drivers' 98 SE gates.
- **An application across a replug**: the running `ping` did not recover
  on 98 SE or ME. A new ping works at once, and DHCP renews at the
  replug; whether a running ping recovers with another NIC driver on 98
  is not known here. Check with cdcnet (same guest, same test) before
  calling it a driver defect. Resolved in
  [ax88179-fcs](2026-10-22-ax88179-fcs.md): `ping -n 60` used up its
  count as instant "unreachable" replies while the device was gone; a
  `ping -t` recovers within 15 s of the replug.
- **Bulk throughput**: no transfer test: NETTEST's TFTP server is QEMU's
  slirp, which this leg does not use, and no program may serve the guest
  from the host. A LAN-side server, or the bench, is needed.
- Not run: standby/resume, cable unplug/replug (link down/up), adapter
  disable/enable, `NetworkAddress` override.
