# AX179F (`ax88179`): FCS forwarding by session, and a ping across a replug, 2026-10-22

Follow-up to [ax88179-9x](2026-10-22-ax88179-9x.md), which left two open
points: the chip forwarded the Ethernet FCS in some sessions and not in
others with the same receive configuration, and a `ping` running across a
replug did not recover. Same kit, same owner's AX88179 (`0B95:1790`
rev 0100, behind its own USB 3.0 hub and a USB 2.0 hub, so 480 Mb/s on both
controllers), same LAN (DHCP 192.168.1.166, gateway 192.168.1.100). Kind:
**real device via VM**. Nothing is released.

Guests: 98 SE with xHCI98 3.1.0.0 on `qemu-xhci` (`launch-ax.ps1`, overlay
`w98\axf.qcow2`), and 98 SE with NUSB 3.3 EHCI on `usb-ehci` (`launch-ax.ps1
-Guest n98`, overlay `n98\axfn.qcow2` of `ax-n2.qcow2`). QEMU's `info usb`
before each leg: "Speed 480 Mb/s, Product AX88179". Replug: QMP
`device_del ax`, then `device_add` of the same usb-host line 20 s later.
Driver: ndis5 trace builds of `src/net/ax88179`.

## 1. FCS forwarding

### What was tried (diagnostic builds, xHCI98)

None of these sessions had the FCS on, so none of them could turn it off;
they looked for something that turns it on.

- MAC registers 00-FF dumped before start and after link up, and the 32
  PHY registers: the same in every session; nothing in them names FCS
  forwarding.
- Written before start: the values the 2026-10-21 host run read before it
  started the chip (RX_CTL 0, medium 0x0039, bulk-IN queue `07 99 00 20
  1f`, RXCOE 0x67, TXCOE 0x27, pause levels 0x5c/0x3c, clocks and PHY off);
  then also MONITOR_MOD cleared and an EEPROM/eFuse reload (vendor request
  0x06, as Linux's `set_eeprom` does): 0 frames with an FCS.
- A sweep under `ping -t`, one bit at a time on the running chip, each for
  two link polls: RX_CTL bits 0x0004, 0x0040, 0x0400-0x8000; medium
  bits 0x0004, 0x0040, 0x0080, 0x0400-0x4000; bulk-IN queue byte 0 bits
  0x08-0x80; MONITOR_MOD off. Twice: 0 frames with an FCS in every step.
- Linux v6.12 `ax88179_178a.c`, FreeBSD `if_axge.c`, ASIX's own Linux
  driver and the datasheet ("optional forwarding of the frame check
  sequence (FCS) field") name no register for it.

So the state is not one the driver can read or set through the registers
it knows. What the two sessions that had the FCS (the 2026-10-21 host run,
and `an2` of the NUSB leg) had in common is that each was the first after
the dongle was plugged in. Every later session began from the state the
driver's Stop leaves.

### The change

`AxStart` (so also Resume) now begins with a settle cycle: the chip is
brought up briefly with this driver's configuration (PHY on, clocks,
bulk-IN queue, pause levels, no checksum offload, RX_CTL 0x3aa, wake on
magic packet armed, gigabit full-duplex medium), then stopped as Stop does
(receive off, RX_CTL 0, clocks and PHY off), then the normal bring-up. 15
requests and 900 ms more per start. It is a hypothesis: that a first
session after power-up then begins where the later ones do. QEMU cannot
power-cycle the dongle (`device_del`/`device_add` closes and reopens it
through libusb, whose WinUSB back end only resets the pipes), so the
first-after-plug state could not be produced here and the hypothesis is
**not verified**.

The per-frame FCS check stays. A frame that still arrives with its FCS is
now an anomaly: the trace says "anomaly: rx frame arrived with an FCS
(configured: none); stripped", the halt line adds "(anomaly)", and once
per adapter the driver writes an NDIS error-log entry
(`NDIS_ERROR_CODE_HARDWARE_FAILURE`, values 1 and the count in that
transfer; the release build has no trace). Shared files (`netusb.*`,
`netcore.c`, `coretest.c`, `shim\`) copied to `rtl815x`. Host tests pass
(`test.cmd` in both packages).

### Sessions with the change (0 frames with an FCS in each)

| Guest | Session | Start | FCS frames |
|---|---|---|---|
| 98 SE xHCI98 | `f1` (after nine diagnostic-build sessions): the build swapped in, then three replugs | "chip start: 0, ... 38 requests", four times | 0 in each |
| 98 SE xHCI98 | `f2`: new QEMU launch, guest booted, no replug | 38 requests | 0 |
| 98 SE xHCI98 | `g1a`: new launch; then a replug | 38 requests, twice | 0, 0 |
| 98 SE xHCI98 | `g1b`: new launch, no replug | 38 requests | 0 |
| 98 SE NUSB EHCI | `h1a`: the old driver (23 requests), then the final build swapped in and two replugs | 38 requests, twice | 0, 0, 0 |
| 98 SE NUSB EHCI | `h1b`: new launch, no replug | 38 requests | 0 |

`f1`, `f2` and `g1` ran the build before the anomaly report took its lock
(Codex round 1); `h1` ran the final build. In each: read-back `3aa`, link
1000 Mb/s full duplex, `ping -n 10` 10 of 10 (`g1b`, `h1a`, `h1b`
screens). The pass condition (no FCS several sessions in a row, cold and
after a reboot) holds, but it held before the change too in every session
but the first after a physical plug, which is the case the change is for.

### Owed: the owner's bench check

1. Shut the guest (or host program) down; physically unplug the dongle
   from the USB 2.0 hub, wait 10 s, plug it back in (this powers the chip
   off and on, which QEMU cannot do).
2. Launch the n98 or w98 guest with this build (`launch-ax.ps1`), let it
   boot, and run `ping -n 20 192.168.1.100`.
3. Shut the guest down and read its 0xE9 trace (`n98\e9-<tag>.log`): pass
   if the halt line says "0 with an FCS" and no "anomaly" line appears; a
   fail if "anomaly: rx frame arrived with an FCS" appears (the frames are
   still delivered, stripped).
4. Repeat 1-3 two or three times. With a release build, look instead for
   an NDIS hardware-failure entry from `ax179f` in the error log.

## 2. A ping running across a replug

Not a driver defect. On 98 SE a ping to a destination with no route answers
"Destination host unreachable" at once, without the one-second wait: in
`pt1` (a diagnostic build, xHCI98, `ping -t` to a file) 20 replies, then
54419 "unreachable" lines in about 28 s while the device was gone, then 80
replies. The earlier legs ran `ping -n 60`: its remaining 43 echoes were
used up as "unreachable" within a moment of the removal, so the ping had
ended before the replugged adapter came up ("17 replies, then 43 x
unreachable"). cdcnet's NETTEST recovers because it retries on a timer.

With `ping -t` typed into Start > Run (a visible window), the device
removed 10 s in and added 20 s later:

- 98 SE xHCI98, `f1` and `g1a`: "unreachable" during the removal, then
  replies again within 15 s of the `device_add` (screens `f1d-w20`,
  `g1p-w15`). **PASS.**
- 98 SE NUSB EHCI, `h1a`: the same; replies by +15 s, all replies at +30 s
  (`h1p-w15`, `h1p-w30`). **PASS.**

The driver came back each time: "device gone", halt, a new DriverEntry,
read-back `3aa`, link 1000 Mb/s, same MAC (00:0e:c6:c2:57:ae).
