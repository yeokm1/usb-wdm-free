## Chip cores: what is ported, and deliberate departures

AX179F (`axchip.c`): `ax88179_reset` (PHY power, clocks, auto-detach from
EEPROM word 0x43, MAC read, queue/pause/RX control/monitor/medium, EEE off,
autoneg restart), `link_reset` (TX FIFO poll, speed/USB-speed queue table,
medium), `set_multicast` (64-bin hash), `status`, `stop`+`unbind`,
`suspend` (without WoL), `resume` (= reset), `tx_fixup` (8-byte header,
padding flag instead of a ZLP). Receive uses `axframe.c`'s FCS mode
(`AxFrameReceiveFcs`), because the physical run of 2026-10-21 showed the
chip forwarding the FCS. Departures: checksum offload written off
(v1 offloads nothing), no LED setting, no WoL read, MAC not written back
at start (the core writes it only when it uses another address), FIFO
poll bounded to 10 reads with 10 ms sleeps. One frame per bulk-OUT
transfer, as Linux; 4 transfers in flight.

RTL815X (`rtlchip.c`), versions 01, 02, 07 (8152/8152B), 03-06 (8153),
08, 09 (8153B), 14 (8153C): version from PLA_TCR0 (3 tries), `rtl_ops_init`
values, `init`, `hw_phy_cfg`, `rtl8152_set_speed` (autoneg, default
advertising), `set_ethernet_addr` (PLA_IDR for 01, PLA_BACKUP to IDR for
the rest), `up`, `down`, `unload`, `enable`/`disable` on carrier change,
`_rtl8152_set_rx_mode` (64-bin hash, applied only with the carrier on),
24-byte rx_desc walk, 8-byte tx_desc (FS|LS|len), aggregated TX up to
16 KiB with 4-byte alignment and no ZLP (as `r8152_tx_agg_fill`), the
OCP byte-enable rules of `generic_ocp_read/write`. Departures: no firmware
patch (Linux's own no-firmware path); RX VLAN untagging off; no
checksum/TSO; saved WoL = 0, runtime suspend never enabled; no dock MAC
pass-through or Dell TB16 quirk; `usb_enable_lpm` has no equivalent;
Resume is `reset_resume` (full init) because 98/2000 sleep may cut power;
`rtl_disable`'s USB parts belong to the lower edge, which has already
stopped the transfers (its FIFO waits stay bounded at 1000 x 1 ms).
Unknown versions (RTL8156 and later) are refused at Start before any
write; the halt path then touches nothing.

Departure in the shared receive path: a transfer whose last frame runs
past its end is rejected whole before anything is emitted (ethernet.md
3.3); Linux delivers the frames before it.

## Core tests on the fake completion backend (later, 2026-10-22)

After the owner accepted the three open points (recorded in ethernet.md
12.1), `netcore.c` and `netusb.c` got host tests of their own, as section
10.3 asks: `coretest.c` compiles both files unchanged (`/W3 /WX`, the
driver's warning level) against `shim\` (stand-in `wdm.h`, `usbdi.h`,
`ndis.h` with test-own layouts, and `fakeos.c` / `fakewin.c`, a fake
operating system on Win32 threads, events and critical sections). It
runs the driver's real worker thread. A fake chip table stands in for the
AX88179/RTL815x cores, which have their own tests; `coretest.c` and
`shim\` are identical in both packages.

The fake USB device completes transfers inline inside `IoCallDriver`,
later from the test thread, with failure, as cancelled under
`ABORT_PIPE`, and as gone (`STATUS_DEVICE_NOT_CONNECTED`). The fake NDIS
protocol returns receive packets inline (reentrant) or holds them, also
across halt. `fakeos.c` counts every IRP, pool block, NDIS memory,
packet, buffer and pool, and records a violation for any `IoCallDriver`,
NDIS indication or completion, wait or delay made while the calling
thread holds a spin lock, for a lock taken twice or released by another
thread, for a completion routine not returning
`STATUS_MORE_PROCESSING_REQUIRED`, and for double frees.

Scenarios, each ending with halt and zero violations and allocations:

- initialize and halt 22 times, half on the Windows 98 path (no wait on
  the thread object);
- no bulk traffic before the link; link up through the interrupt pipe
  (MEDIA_CONNECT once, 4 receive transfers posted);
- the software filter: directed, broadcast, listed multicast accepted;
  other unicast, unlisted multicast and runt dropped; a malformed
  transfer emits nothing and receive continues; promiscuous;
- 5000 consecutive inline receive completions: maximum `IoCallDriver`
  nesting 1 (the pump iterates, ethernet.md 4.7.1);
- receive pool: 56 packets held by the protocol, then RESOURCES
  indications reclaimed at once, no buffer shortage; halt waits for held
  packets (still blocked after 300 ms, finishes once they return);
- send: framing, padding to 60 bytes, 4-byte alignment and contents of
  10 packets split over three buffers; an 80-packet burst (queue of 64);
  a failed transfer; recovery; link down flushes the queue and stops
  bulk traffic; sends fail while the link is down;
- a chip needing a ZLP: payload, then the ZLP, before the next payload;
- D3 drains everything before the OID completes; D0 runs the bring-up
  again, the filter and the link; reset pends and completes once;
- surprise removal: in-flight and queued sends fail once, MEDIA_DISCONNECT,
  later sends fail at once, nothing sent to the gone device at halt;
- addresses: NetworkAddress programmed; a multicast NetworkAddress is
  ignored; no valid chip address gives a generated LAA written once as
  `FallbackAddress` and reused at the next start;
- start failures (chip, device gone at the descriptor) free everything;
- OID length checks, 64-bit counters, unknown OIDs.

Result: **PASS, about 34100 checks** in each package (the count varies by
a few with timing). To check the harness itself, four deliberate faults
were tried on scratch copies (not committed):

| Fault | Result |
|---|---|
| a data IRP not freed in its completion | FAIL, IRP count |
| `NdisMSendComplete` under the adapter lock | FAIL, violation reported |
| the RESOURCES packet never reclaimed | FAIL, pool counts |
| pump re-entry guard removed | the run does not finish (unbounded recursion) |

A fault in the TX-build abort path (`BuildTx` finding the gate closed) was
not caught; the scenarios do not reach that branch.

Still not covered: real IRQL (`DISPATCH_LEVEL` rules are modelled only by
the lock check), the real USB stacks' cancellation timing, and any
Windows 98 behaviour. Those are the guest legs.

## Guest and hardware legs owed

QEMU has no AX88179 or RTL815x model (ethernet.md 10.1), so every leg is
real hardware or `usb-host` passthrough, which the owner's rules now
require to run inside a guest, never as a host program:

1. 98 SE and 2000 SP4 guest load of each driver (`trace` flavour, debug
   console port 0xE9): install from the 98 / NT INF, DriverEntry and
   Initialize reach "initialized", Halt on disable leaves nothing. This
   is also the 98 SE evidence for the three new NDIS imports. Needs a
   device: passthrough of the owner's physical AX88179 (`0B95:1790`
   rev 0100). The 2026-10-21 Windows 2000 passthrough showed QEMU's EHCI
   passing SuperSpeed descriptors (1024-byte bulk) at 480 Mb/s; the probe
   accepts that set as SuperSpeed, so that leg would exercise a
   descriptor/speed mismatch, not a real USB 2.0 path. `qemu-xhci` with
   xHCI98 on 98 SE, or a USB 2.0 connection, avoids it.
2. AX88179 on 98 SE (in-box UHCI via a USB 2.0 hub, NUSB's EHCI) and
   2000 (UHCI, EHCI): DHCP, ping 64/1472-byte, TFTP/SMB transfer, link
   unplug/replug of the cable, adapter disable/enable, device unplug under
   load, standby/resume, NetworkAddress override. Throughput per 6.7.
3. RTL8153 (owner's dongle per 10.2) on the same legs, plus an RTL8152 if
   one is on the bench. Before that: the dongle's configuration
   descriptors (which configuration is vendor, endpoint numbers), read in
   a guest with the usbprobe helper, to confirm `RtlProbe`'s choice.
4. ME guest: build-only ("Built, not tested", 11.1).
