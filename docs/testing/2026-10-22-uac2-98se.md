# uac2 on Windows 98 SE: why WinMM had no wave device, and the first playback, 2026-10-22

The first 98 SE leg of `uac2` (`2026-10-22-98se-legs.md`) started the
driver ("This device is working properly", `Uac2M0Stage` 12) but WinMM
listed `waveOut devices=0`, also after a restart. This record finds why,
fixes it, and plays simulated audio on 98 SE under xHCI98. Development leg
in QEMU, not a release and not "Tested".

## Rig

Kit `E:\usb-wdm-free\nusb-legs\` (`launch.ps1`, `k.sh`, `run.sh`,
`uattach.sh`, `udetach.sh`, `uacmodel.ps1`, `uacbuild.cmd`; monitor 48920,
simulator 48921). Headless QEMU 11.1, TCG, 1 vCPU, 256 MB; throwaway
overlays (`x98u`) of the first leg's 98 SE overlay `m98a` (xHCI98 3.1.0.0
installed, `uac2wdm.inf` installed for `USB\VID_041E&PID_3278&MI_03`,
`USBAUDIO.SYS` renamed `.BAK`). Controller `qemu-xhci,p2=8,p3=0`;
`uacemu.py` (the X4 layout) over `usb-redir`. The host was saturated
(CPU about 97 %, 13 guests), so timings below are slow and noisy.

New test tool: `src/audio/uac2/ks98.c` (`ks98.cmd` builds `KS98.EXE`), a
console probe that lists the KSCATEGORY_AUDIO / RENDER / TOPOLOGY / MIXER /
SYSAUDIO interfaces, reads this driver's filters (topology, every pin
property, a PCM data intersection), dumps the interface registry keys, and
on request asks SysAudio for its devices (`sys`) and counts WinMM devices
(`mm`).

## Reading: SysAudio faults on the driver's topology filter

With the build that ran in the first leg (`Uac2Build` 3), plugging the
simulator and cancelling the HID function's wizard brought:

    A fatal exception 0E has occurred at 0028:FF0C7BA5 in VXD
    SYSAUDIO(04) + 00004505.

(`ev\sysaudio-0E.png`). 98 SE's SysAudio builds its devices from the
KSCATEGORY_AUDIO filters as they arrive; the fault stops it, so WDMAud has
no device to offer and WinMM lists none. In another boot the guest's shell
hung at the same point instead.

`KS98` on the same build (`ev\ks98-k3a.txt`) read the driver's two filters
through the 98 SE kernel-streaming stack without error:

- Interfaces present and linked (`Control\Linked=1`):
  `\\.\000000000000000c#{KSCATEGORY_AUDIO}\Wave` and `\Topology`,
  `{KSCATEGORY_RENDER}\Wave`, `{KSCATEGORY_TOPOLOGY}\Topology`. 98 SE names
  an interface by devnode (`\\.\<devnode>#{guid}\<reference>`); PortCls
  answers `PHYSICALCONNECTION` with `\DosDevices\...` names of the same form.
- Wave filter: categories AUDIO + RENDER; node DAC; links filter pin 0 to
  the DAC and the DAC to pin 1; pin 0 a sink with two data ranges (the
  driver's PCM 2 ch / 16 bit / 48000 Hz and PortCls's own DirectSound
  range); a wide PCM intersection returns 2 ch / 16 bit / 48000 Hz.
- Topology filter: categories AUDIO + TOPOLOGY; **no node, and one link
  from filter pin 0 straight to filter pin 1**; pin 1 the speaker line
  ("Speaker").
- The interface keys carry no `CLSID` or `FriendlyName` values, for this
  driver or any other on the system (98 SE keeps the INF's `AddInterface`
  `AddReg` elsewhere or not at all); SysAudio named the device from the
  driver's description anyway (below), so this is not the cause.

The only shape in these readings outside what a PortCls driver normally
offers is the topology filter's pin-to-pin link with no node. 2000 DDK,
"WDMAud Topology Parsing": parsing of a line "starts at the immediate
parent of the pin" and runs through nodes; here there is none.

## Fix

`uac2wdm.cpp` build 4: the topology filter carries one `KSNODETYPE_SUM`
node between its pins (pin 0 to the SUM's input, the SUM's output to pin
1). WDMAud turns a SUM into no mixer control (same DDK page), so the mixer
offers no control the driver cannot carry out. The link tables moved to
`uactopo.c`, and `UacLinksCheck` (`uactopo.h`) states the rules both
filters must meet, among them "no link joins two filter pins"; the host
test `topotest.c` (run by `test.cmd`) checks the shipped tables and each
rule. Nothing else changed.

## Results, build 4 (`uac2wdm.sys` MD5 `69e25f1c739ae7032a4f2e3b158b57c5`, wdmx86 free)

The new `uac2wdm.sys` was copied over the installed one with the device
unplugged; the INF was not reinstalled.

| Step | Result | Readings |
|---|---|---|
| Plug, cancel the HID/CDC wizards | **PASS**: no fault | while a wizard was open, a SysAudio open from `KS98` waited; after the wizards closed it completed; the tray showed the volume icon |
| SysAudio and WinMM (`KS98 sys mm`) | **PASS** | `SysAudio devices=1`, name "UAC2 X4 stereo playback (experiment)", interface `...\Wave`; `waveOut=1 mixer=1` (one destination); topology NODES `KSNODETYPE_SUM`, links pin 0 -> node 0 -> pin 1 (`ev\ks98-k4-build4.txt`) |
| `UACPLAY /playexit` (2 s, 2 ch / 16 bit / 48000 Hz, 440 Hz triangle) | **PASS** | WinMM open 0, 8/8 buffers, 96000 samples, close 0. Simulator: 16039 packets of 24 bytes (High Speed, one 48 kHz frame of 4 bytes per microframe), 384936 bytes; the capture holds 96000 non-silent frames, L = R, 880 cycles = 440.0 Hz |
| Unplug idle | **PASS** | guest alive, volume icon gone |
| Same-port replug, `UACPLAY` | **PASS** | driver started again; 8/8 buffers, close 0; simulator 16058 packets, 336960 non-zero bytes |
| Unplug during `UACPLAY` | **PASS** (survival) | the application's own check fails as it must (3/8 buffers, completion deadline), `waveOutReset` 0, close 0; no fault, guest alive |

Timing: `UACPLAY` took 8.7 s (guest clock) for 2 s of audio, and the
simulator saw the 16039 packets over 8.57 s of host time. The earlier TCG
runs on other systems showed the same slowness (`2026-10-21-uac2-play-verifier.md`),
here with the host at about 97 % CPU; it is the emulation's pace, not a
verdict on the driver's timing.
