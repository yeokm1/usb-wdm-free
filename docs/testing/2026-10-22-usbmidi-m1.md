# USB MIDI M1 driver: generic transport, ports, 98 SE half, 2026-10-22

This continues [the core log](2026-10-21-usbmidi-core.md), [the Windows 2000
experiment](2026-10-21-usbmidi-vm.md) and [the 98 SE readiness
audit](2026-10-21-usbmidi-98.md). It replaces the exact-device experiment
with the design's M1 driver (docs/design/usbmidi.md sections 4-8, 16).
No physical USB device was used; MIDI devices reach the guests only as the
original `midiemu.py` usbredir simulator (section "How a MIDI device is
presented"). No Microsoft binary code, disassembly or kit sample was read.

## What changed in the code

- `msdesc.c`: the parser follows the design's tolerance (6.1): endpoints
  that are not bulk/interrupt or lack a CS endpoint descriptor are skipped,
  Element and unknown class descriptors are skipped, `wTotalLength` is
  recorded but not enforced, interrupt endpoints are accepted; duplicate
  jack IDs, a bcdMSC other than 1.00, and malformed lengths still fail.
  New: per-cable `iJack` (embedded jack, else the External jack wired to
  it), `UmFindInterface` (first MIDIStreaming interface, alternate 0 or the
  lowest MIDI 1.0 alternate), `UmMapPorts` (ports per endpoint/cable, four
  endpoints and 32 ports per direction) and `UmPortName` (design 5.4).
- `umusb.c`: generic transport for any class-compliant function: full
  configuration read (bounded 16 KiB), every interface of the returned
  descriptor selected at alternate 0 except the MIDIStreaming one, per-port
  4 KiB rings and encoders, round-robin OUT fill a packet per port per pass
  (6.5), two IN requests per IN endpoint in caller-allocated IRPs re-armed
  from the completion routine, STALL cleared by RESET_PIPE from the worker,
  100 ms back-off and give-up after ten consecutive errors (6.7), D3 pause
  and D0 resume, padding packets ignored. The OUT path keeps the earlier
  STOP barrier, per port, with a per-port generation so packets of a port
  stopped mid-pass are dropped before submission.
- `usbmidi.cpp`: one PortCls MIDI filter per port pair (5.2-5.4) with
  render-only/capture-only descriptors where one direction is missing, the
  filter's FriendlyName and KS proxy CLSID written to its interfaces before
  `PcRegisterSubdevice`, adapter power management on the device object,
  `IRP_MN_QUERY_STOP_DEVICE` refused (no resources, no restart path).
- 98 SE half: no `Io*WorkItem` import on x86. A final Release above
  PASSIVE_LEVEL queues `ExQueueWorkItem` with an FDO reference, and the
  work routine is a naked stub that tail-jumps to `ObfDereferenceObject`
  so no code of the image runs after the reference is dropped; x64 keeps
  `IoQueueWorkItem`. `OBJ_KERNEL_HANDLE` is used only where
  `IoIsWdmVersionAvailable(1, 0x10)`. The `umclean` research prototype is
  no longer needed by the driver and stays out of every build.
- INFs: `usbmidi.inf` is a template; `mkinf.ps1` writes one INF per
  release folder (`w98se`, `wme`, `w2k`, `wxp`, `wv-8-x86`, `wxp-x64`,
  `wv-8-x64`) plus never-released `test` and `test-x64` folders with the
  simulator ids, and checks each.
- Build: `build.cmd <wdmx86|wdm64> <free|checked>` as build.md 4; gates are
  the own-PE import allowlist (`imports-wdmx86.txt`, `imports-wdm64.txt`)
  and, for x86, the 98 SE link probe: the same objects linked against the
  98 SE DDK's `wdm.lib` and `portcls.lib` must resolve, with the same
  module per import (build.md 5.1, import-library evidence; a guest load
  stays the final word). `UMTRACE=1` adds a debug-port trace for tests.

## How a MIDI device is presented

QEMU has no MIDI model. `midiemu.py` is a usbredir peer on localhost
(48441) that QEMU's `usb-redir` device connects to; the guest sees a USB
device with the profile's descriptors. Profiles: `acms` (FFFF:0001, AC+MS,
one cable), `multi` (FFFF:0002, AC+MS, two cables each way on one endpoint
pair, External jacks named "Port A"/"Port B"), `lone` (FFFF:0003, a single
MIDIStreaming interface, compatible id `USB\Class_01&SubClass_03`).
`--speed high` presents it as a High Speed device (512-byte bulk, device
qualifier) for an EHCI bus. Every cable echoes on the same cable through
the project's own C codec.

## Windows 2000 SP4, UHCI, simulator (headless QEMU, TCG, 1 vCPU)

Throwaway overlays of `E:/usb-wdm-free/vm/w2k.qcow2` under
`E:/usb-wdm-free/usbmidi/`, monitor 48440, simulator 48441. The driver
was the traced checked flavour (`UMTRACE=1`, debug port 0xE9 to a file).

- First runs (w2k1-w2k3): filters registered, WinMM listed nothing. The
  IRP trace showed every IRP_MJ_CREATE on a filter failing with
  STATUS_OBJECT_NAME_NOT_FOUND: PortCls keeps the subdevice name pointer
  and the driver passed a stack buffer. Fixed with static names.
- w2k4/w2k6 (multi profile): WinMM lists IN/OUT "MIDI 2x2 SIM Port A" and
  "Port B" (runtime names from the External jacks' iJack strings).
  `MIDITEST 0 0` and `1 1`: 355/355 bytes, PASS, cleanup complete; `0 1`
  receives nothing (cable isolation). Stress 5 s: 14826 of 14826 bytes.
- Unplug with both ports open under traffic (w2k4, before the fix): the
  helper hung for good. Trace: after IRP_MN_SURPRISE_REMOVAL PortCls failed
  set-state, cleanup and close itself, pending stream IRPs never completed
  and REMOVE never came; the guest could not shut down. Fixed by stopping
  the transport on surprise removal without passing it to PortCls. w2k6,
  same test: the helper ran on and closed with cleanup complete; REMOVE,
  final destroy and DriverUnload followed (Add 1/Remove 1/Destroy 1, traced
  unload).
- Same-port replug without restart: driver reloads, ports return, both
  loopbacks PASS. Restart and shutdown with the device attached: clean.
- A new instance (other port or hub port) asks for a restart. setupapi.log:
  "files in use, or treated as in use", even when usbmidi.sys is not copied
  (COPYFLG 0x40/0x60 tried, reverted) and the image is unloaded. The INF's
  Needs=KS.Registration,WDMAUDIO.Registration.NT copy the loaded KS/WDM
  audio files (ks.inf/wdmaudio.inf sections read as text). After the
  restart the instance works. Documented in the INF; not fixed.
- Installing over the native usbaudio binding hung or crashed the guest
  twice (STOP 0xD3 in win32k.sys; our driver had not loaded, per its trace).
  Staging the INF first (`MIDITEST stage`) and plugging afterwards avoids
  the native install. A FAT floppy media change after guest writes caused
  STOP 0x23 once (System log "Save Dump"); not driver related.

  "NTKERN.VXD, MMDEVLDR.VXD could not load"); copied by hand, it loaded.
  Whether the KS file prompts appear on a retail 98 SE with its own CD
  is open; the device worked without those files.
- A Windows restart of this guest hung QEMU itself (`system_reset` did
  not reset the vCPU); quitting and relaunching QEMU booted normally.
  Restarts in these legs are done by quit and relaunch.
- **Multi profile (composite), first plug: PASS.** WinMM lists IN/OUT
  "MIDI 2x2 SIM Port A" and "Port B". `MIDITEST 0 0` and `1 1`: 355/355

  stress 5 s on port B: 6276/6276 bytes, 3 SysEx, no errors.

  and lone). The trace stops inside `UmUsbStop`, at the wait on the worker
  thread object: 98 SE sends REMOVE without a SURPRISE_REMOVAL first, and
  waiting on a thread object faults there. Fix: the worker sets an
  `Exited` event before `PsTerminateSystemThread`; the stop waits for it,
  and only on WDM 1.10 systems (2000 and later) also waits for the thread
  object (`IoIsWdmVersionAvailable(1, 0x10)`); 98 SE and ME wait the event
  and 10 ms. With the fix (runs t7, t8): loopback PASS, unplug PASS
  (`UmUsbStop` completes, REMOVE completes, the adapter is destroyed and
  DriverUnload runs), for both the lone and the multi profile.
- **Lone profile (single MIDIStreaming interface, FFFF:0003): PASS.** The
  generic `USB\Class_01&SubClass_03&Prot_00` match installed it silently
  (no prompts, no restart); `MIDITEST 0 0` 355/355.
- **New port (restart question):** the multi device on another root port
  started at once with no prompt and no restart request on 98 SE (unlike
  2000). But after that replug every `midiInOpen` failed with
  MMSYSERR_ALLOCATED (4), on both ports; this happened on the first
  replug on the new port. (Corrected in the evening: output fails too, and
  any replug does it; see "Windows 98 SE replug and freezes" below.)
- **Intermittent guest hang:** three times (one idle unplug of the
  composite device, one first plug, one replug) the guest froze with the
  CPU in VMM code (EIP C000xxxx) and no driver trace after `start`. Not
  reproduced on demand; cause unknown (the host was saturated throughout).
  The evening runs reproduced it without `usbmidi` (below).
- Evidence: `E:\usb-wdm-free\usbmidi\` (`w98a-dbg2..4.txt`,
  `w98a-t5..t11.txt` traces; `w98b-*`, `w98c-*`, `w98d-*`, `w98e-*`,

## Windows 98 SE replug and freezes (2026-10-22 evening)

Kit `E:\usb-wdm-free\midi-replug\` (monitor 48850, simulators 48851 and
48852; `launch.ps1`, `plug.sh`, `unplug.sh`, `exp*.sh`, `fix.sh`), a copy
of the afternoon overlay (`w98r.qcow2`, same 98 SE base), 1 vCPU, 256 MB,
QEMU UHCI, traced checked build of this tree. Host CPU about 85 % (lighter
than the afternoon's 97 %). `MIDITEST` gained `wave`, `outopen n`,
`disable`/`enable`/`cycle <device id> <flags>`, and `open` now tries the
output even when the input fails.

### Replug: every MIDI open on a re-arrived device fails

The afternoon's reading was incomplete: after a replug **both**
`midiInOpen` and `midiOutOpen` fail with MMSYSERR_ALLOCATED (4); output
was never tried (`MIDITEST` stopped at the failed input). What the runs
show:

- It is not about a new port. 98 SE names a device with no serial number
  `INST_0` whatever port it is on (`HKLM\Enum\USB\VID_FFFF&PID_0002&MI_00\
  0USB&VID_FFFF&PID_0002&INST_0`, one `MEDIA\0000` key), so port 1 and
  port 2 are one devnode; that is also why 98 SE asks for no restart on
  another port. A same-port replug fails the same way (runs d2, e2, e4).
- It does not need prior use: plug, no MIDI client at all, unplug,
  replug: both opens fail (e1).
- It is per devnode. With two devices plugged (`multi` on port 1, `lone`
  on port 2), removing either leaves the other's ports working; the
  removed one fails when it comes back (e2, e4). After a Windows restart
  the same devnode works again.
- The failed opens never reach the driver: no IRP_MJ_CREATE on any filter
  (trace), so no driver state is involved; the image is even unloaded
  between plugs (`DriverUnload` runs; on 98 SE the next plug re-runs
  `DriverEntry` on the cached image, so a rebuilt `usbmidi.sys` needs a
  Windows restart to load).
- On the first arrival in a boot the filters see 8 open +
  QUERY_DEVICE_RELATIONS (TargetDeviceRelation) + close sequences; on a
  re-arrival only 4 (d2, e1, f3): one of Windows' WDM audio clients
  (wdmaud or sysaudio, named from the order only) does not attach to the
  re-arrived devnode, and WinMM then answers "allocated".
- Tried in the driver and the INF, none helps: a new device interface
  reference string per arrival (`Midi00g01`, `g02`, ... kept in the
  devnode's driver key; f3), a new FriendlyName per arrival (f4), and the
  stock `WDMA_USB.INF` devnode values (`SubClasses`
  `wave,midi,mixer,aux` with their `Drivers\...\wdmaud.drv` keys, `CLSID`,
  `SetupPreferredAudioDevices`; f5). The interfaces themselves are disabled
  on removal (`MIDITEST ifaces` before/after the unplug). The attempts are
  not committed.
- Windows' own `usbaudio.sys` (QEMU `usb-audio`, same guest): `waveOutOpen`
  works after a same-port replug (e3), so the defect is in the MIDI path
  (devnode-based WinMM MIDI devices), not in WDM audio removal as a whole.
  98 SE has no in-box USB MIDI driver to compare with; its GS software
  synth (the only other WDM MIDI device) froze the guest on open, see
  below.
- `CM_Disable_DevNode` on the device returns 0x28: 98 SE implements a
  disable as QUERY_STOP/STOP, and the driver refuses QUERY_STOP (design
  18: no restart path). So Device Manager cannot disable the device on
  98 SE, and a disable/enable could not be tried as a recovery.

Verdict: a 98 SE limitation in its WDM MIDI / WinMM layer, outside the
driver as far as these runs can see: **on 98 SE, a USB MIDI device that is
unplugged works again only after a Windows restart.** Plugging it in at
boot or keeping it plugged works; a second device is not affected by the
first one's removal. Not fixed. Owner, 2026-10-22: a known limitation, no
code change; README and the release notes say to restart after a replug
(the costly alternative, not taken: a child devnode with a new instance per arrival, which would
install a new device each plug).

Windows ME (`wme.qcow2`, one try, not a leg): Setup picked the floppy's
test INF for the `multi` composite, asked for the KS files (skipped) and a
restart; after it `usbmidi` failed at stage 1 with
STATUS_DEVICE_CONFIGURATION_ERROR (C0000182). Diagnosed and fixed later
the same evening; see "Windows ME: the C0000182 start failure" below.

### The guest freezes

Same signature as in the afternoon (screen and clock stop, mouse pointer
still moves, CPU in VMM code C000xxxx, timer interrupts still counted,
disk idle): four times in this session, every time on the **first** WDM
audio device arrival after boot (d1, f2, and e5 with only Windows' own
`usbaudio.sys` and no `usbmidi` loaded), plus once on `midiOutOpen` of the
GS software synth behind `usbaudio` (e6). About 25 later arrivals and
removals did not freeze. The `usbmidi` trace ends after the arrival
enumeration (every IRP completed). Verdict: a 98 SE / WDM audio freeze
under QEMU TCG, not caused by `usbmidi` (it happens without it). Avoided
in these legs by retrying the boot.

### Windows ME: the C0000182 start failure (fixed)

`wmer.qcow2` (overlay of `wme.qcow2`, ME OEM full, 256 MB, 1 vCPU), QEMU
UHCI, `multi` Full Speed on port 1, the floppy's test INF already
installed for the MI_00 function; traced checked build with create-path
diagnostics (`cf`/`cs`/`ci`/`cp` lines on port 0xE9, traced builds only;
script `me.sh`).

- m3, m4 (before the fix): the device and configuration descriptors
  reach the driver intact (the full 133-byte configuration, interfaces 0
  and 1), `UmFindInterface` and the port map succeed, and the
  SELECT_CONFIGURATION through ME's composite parent succeeds with a
  configuration handle. But the parent leaves every pipe entry of the
  returned interface list as the driver sent it (MIDIStreaming interface
  1: two pipes, address, type and handle all zero), so the first mapped
  endpoint has no pipe handle and the start fails with C0000182. 98 SE's
  and 2000's parents fill the pipes in.
- Fix (`umusb.c`): when a mapped endpoint has no pipe handle after the
  SELECT_CONFIGURATION, the driver sends a SELECT_INTERFACE for the
  MIDIStreaming interface and alternate on the returned configuration
  handle and takes the pipes from that.
- m5 (after): SELECT_INTERFACE succeeds, the start completes; `MIDITEST
  list` 2 in, 2 out; `MIDITEST 0 0` and `1 1` 355/355 PASS; `open 0 1`
  PASS. Unplug: stop phases, REMOVE, `DriverUnload`. Replug on the same
  port in the same boot: `0 0` 355/355 PASS and `open 0 1` PASS, so ME
  does **not** have 98 SE's replug limitation.
- 98 SE with the fix (n6, NUSB EHCI High Speed): the parent fills the
  pipes, no SELECT_INTERFACE is sent; loopbacks and open PASS as before.

ME remains untested by the README's policy (no real-PC leg); the KS file
prompts during ME's first install (skipped) are still open.

### Windows 2000 SP4 and XP SP3 under Windows' EHCI, High Speed

Same kit; QEMU `usb-ehci` beside the UHCI controller, simulator `multi
--speed high` on `ehci.0` port 1 (QEMU `info usb`: 480 Mb/s); traced
checked build with `fc596a2` (the ME SELECT_INTERFACE fallback; not taken
on either system: the parents fill the pipes). Host CPU about 85 %.

- 2000 SP4 (`w2kr.qcow2`, 512 MB, 1 vCPU, `usbehci` of SP4; script
  `w2ke.sh`; k3): first plug, no prompt: `MIDITEST 1 1` 355/355 PASS and
  `open 0 1` PASS (the `0 0` run was lost to the typing); unplug: REMOVE
  and `DriverUnload`. Replug on the same port: `0 0` and `1 1` 355/355
  PASS, `open 0 1` PASS; unplug clean.
- XP SP3 (`wxpr.qcow2`, overlay of `wxp.qcow2`, TCG, 512 MB, 1 vCPU; x1):
  with the test INF only staged (`MIDITEST stage`), PnP gave the function
  to Windows' own `usbaudio.sys` ("USB Audio Device", no `usbmidi`
  trace), as the design expects for an unsigned INF on XP (4.2);
  `MIDITEST install "USB\VID_FFFF&PID_0002&MI_00" A:\USBMIDI.INF`
  (unsigned-driver prompt answered Continue) moved it to `usbmidi`
  without a restart. WinMM numbers the ports **differently per
  direction** on XP: `IN 0` Port A, `IN 1` Port B, but `OUT 0` Port B,
  `OUT 1` Port A, so the same-number loopbacks `0 0` and `1 1` received
  nothing (FAIL, a pairing error, not lost data) while `open 0 1` passed.
  Paired by name, `MIDITEST 0 1` (A to A) and `1 0` (B to B) 355/355
  PASS. Unplug, replug and a third plug on the same port: enumeration and
  `open` PASS each time; the by-name loopbacks ran on the third plug.
  Unplugs clean (REMOVE, `DriverUnload`).

Verdict: PASS on 2000 SP4 and XP SP3 under Windows' EHCI at High Speed,
replug included. Open on XP: the per-direction WinMM order (design 5.4,
port names and numbering unverified), whether it comes from the order
WDMAUD finds the filters' interfaces in; harmless to a user who picks
ports by name.
