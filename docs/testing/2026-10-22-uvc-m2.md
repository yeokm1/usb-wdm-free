# UVC M2: real Brio 100 frames through the project STREAM.SYS miniport (Windows 2000 guest)

Date: 2026-10-22. Experimental NT2000+ build, not a release. No Windows 98 SE,
ME, XP or physical-host-OS claim; no image-quality claim.

## What M2 is

M2 is the M1 worker miniport built with `UVWORK_USB` (`m2build.cmd`, INF
`UVCM2.INF`, per-camera line `USB\VID_046D&PID_094C` only, as the owner's
binding rule requires). The M1 engine is unchanged except for its frame source.
On the first READ, the private passive worker opens the camera through
`uvcusb.c`, the new NT2000+ USB transport:

1. read the configuration descriptor and find the VideoControl interface;
2. read the device descriptor for the per-camera quirk table;
3. determine speed through the XP+ bus interface, falling back on 2000 to a
   recorded inference (high-bandwidth or >1023-byte iso packets imply High
   Speed);
4. select the configuration with every interface at alternate 0;
5. run PROBE/COMMIT through the portable `UvcNegotiateLimited`;
6. select the chosen alternate;
7. run an isochronous IN ring shaped by `UvcIsoPlan`, completions fed in
   order through `UvcIsoFeed` and the payload core into a latest-frame buffer.

READs copy the newest complete frame. UNINITIALIZE stops the stream: the pipe
is aborted, the ring drained, the thread joined and alternate 0 selected.
The import gate (`m2gate.ps1`) allows exactly the kernel imports used,
with no `usbd.sys` (URBs are built by hand).

New portable pieces, all host-tested: `uvciso.c` (walker and plan,
`isotest.cmd`, 2486164 checks) and `uvcneg.c` (PROBE/COMMIT with an
optional payload limit, `negtest.cmd`, 3228 checks over the real Brio 100
descriptor fixture).

## Guest and setup

- Guest: Windows 2000 SP4, TCG, one vCPU. Overlay `E:\usb-wdm-free\wave2\w2km2.qcow2`
  over w2kuvck, over w2kuvcg, over `E:\usb-wdm-free\vm\w2k.qcow2`.
- The base image had no USB stack files. `usbport.sys`, `usbd.sys`,
  `usbhub.sys`, `usbhub20.sys` and `usbehci.sys` were expanded from the
  guest's own `Driver Cache\i386\sp4.cab` and the guest was shut down cleanly
  before the EHCI controller was first added. A first attempt that was
  hard-reset during shutdown lost the file and blue-screened on boot
  (c000026c usbhub20.sys); that overlay was discarded.
- The Brio 100 was passed through with QEMU `usb-host` on an emulated EHCI.
  Later runs used this repository's QEMU 2EDD5707 (`run-orphan\`, with ISO
  tracing) through `w2km2-trace.ps1`. The new hardware was installed from
  A: with the Found New Hardware wizard (unsigned, accepted).

## Findings and limits

- **Brio 100 quirk.** The camera answers its largest payload (3060, a
  high-bandwidth alternate) for every frame. On this guest the
  high-bandwidth isochronous stream stalled; whether Windows 2000
  `usbehci.sys` or the emulation is responsible is not isolated, and design
  section 5.4 lists 2000 high-bandwidth support as unverified. The quirk
  commits the bandwidth the uncompressed frame needs: frame bytes x frames
  per second over the microframes, plus a 12-byte header, rounded up to the
  smallest alternate that carries it (640 for 320x240 YUY2 at 30 fps). The
  camera honours it. This is per-camera evidence, not a class rule.
- **Removal on 2000.** Cancelled isochronous transfers on a surprise-removed
  device did not complete before our REMOVE, which deadlocks it. Aborting
  the pipe first resolves this. A transfer pipeline that stalls (run 1) still
  needs this path; it was not retested with the high-bandwidth alternate.
- **Throughput.** The TCG guest consumes far fewer transfers than the camera
  produces (374 transfers in the first 4 s in run 5), so most frames are
  dropped and READs wait up to 4 s for the first frame and 1 s after that.
  This is a TCG emulation limit, not measured on hardware.
- **Stock vs patched QEMU.** Under the stock Scoop QEMU (run 3) frames never
  completed; under this repository's patched QEMU (runs 5 and 6) they did.
  The difference is not isolated.
- **Camera stop (run 7, driver 706D9E3A).** STOP state, CLOSE and
  power-down (which also covers SURPRISE_REMOVAL) now run a passive worker
  job. It stops and closes the camera before the control completes, so the
  camera no longer streams until UNINITIALIZE; the next READ reopens it.
  Two M1CAP sessions in a row both PASSed. The trace shows `USB_STOPPED`
  at each STOP, then CLOSE, then a fresh `USB_OPEN`/`USB_START`. Detach
  was clean (SURPRISE_REMOVAL, UNINITIALIZE SUCCESS) and Windows reached
  safe-off. Evidence: `E:\usb-wdm-free\evidence\w2k-m2\run7\`.
- **Open:**
  - No bulk camera support, still image, controls or MJPEG. YUY2 sizes
    come from the descriptors since runs 10-14 (below).
  - No 98 SE path yet.

## Format selection from descriptors (item c), runs 8-14, 2026-10-22

Same guest, rig and helper (`E:\usb-wdm-free\wave1\m2run.sh`: boot,
install, attach the Brio 100 on QEMU `usb-ehci`, `cap TAG WxH`, detach,
shutdown). Host controller driver: Windows 2000 SP4's own `usbehci.sys`.
M2 now builds its format table from the camera's descriptors at bootstrap
(9 YUY2 sizes, 640x480 to 160x120, default interval 333333 each), selects
one on OPEN_STREAM, sizes READs to it, and keeps the device open across
sessions, stopping the stream (alternate 0, per-stream buffers freed) at
each STOP.

| Run | Driver | Sizes | Result |
|---|---|---|---|
| 8 | (first build) | 640x480 | FAIL: alternate 10 (3 x 896, high bandwidth) stalled after 48 packets, no frame. |
| 9 | A5CAB5CB | 320x240, 160x120 | FAIL both. 320x240: alternate 4, 95 frames dropped. 160x120: the PROBE answer resolved to a 153600-byte frame. Both stops logged `UVU_ALT0 C0000001`: selecting alternate 0 failed, so the camera kept streaming. |
| 10 | 6F4697E1 (PROBE trace) | 320x240, 160x120 | **PASS both**, three changing frames each (153600 and 38400 bytes). The answer named the requested frame each time (bFormatIndex 1, bFrameIndex 5, then 2) and both stops selected alternate 0. |
| 11 | CB696F6B | 160x120, 176x144, 320x240 | FAIL all: this build selected alternate 0 before every PROBE, and that select failed (C0000001) straight after configuration, so no stream started. |
| 12 | 10BBD840 (final) | 160x120, 320x240, 176x144 | **PASS all three in one boot**, switching sizes between sessions. Each PROBE answer matched the request; each stop selected alternate 0. |
| 13 | 10BBD840 | 640x480 | FAIL, high bandwidth (below). The guest then hung in the drain and was powered off by the helper. |
| 14 | 10BBD840 | 320x240 | **PASS** after run 13's hard power-off. The frames show a real scene (a plain wall), `frame3.png`. Clean detach and safe-off. |

What run 9 shows, from the PROBE trace of the later runs: a camera left at
a streaming alternate answers PROBE with the frame it is already sending.
The final build therefore:

- retries alternate 0 before PROBE when a stop left another alternate
  selected, and refuses to start if that still fails;
- refuses to stream when the PROBE answer names another frame than the one
  requested (it could never fill a READ of the selected size);
- does not select alternate 0 when the interface is already there (run 11:
  that select fails on 2000 right after configuration).

Why run 9's stops failed to select alternate 0 is not established; the
stops of runs 10, 12 and 14 on the same stop code succeeded. USBD's status
for a failed select is now traced (`UVU_SELECT_USBD`).

### High bandwidth on 2000 (640x480)

640x480 YUY2 at its default 30 fps needs about 2.3 KB per microframe, so
only alternates 10 and 11 (3 transactions per microframe) carry it. Run 13
traced the host side of the passthrough (QEMU `usb_host_iso_*` events,
`w2km2-iso.log`): QEMU submitted four host transfers of 32 packets x 2688
bytes (3 x 896); **every packet of every transfer failed on the host** with
status 0xC0020000 (USBD_STATUS_ISO_NOT_ACCESSED_BY_HW), 0 bytes received.
QEMU then stopped the host stream, and the guest's six URBs never
completed: ABORT_PIPE returned C00002B6 and the drain waited for good
(`UVU_DRAIN_OUTSTANDING 6`).

So on this rig the failure is in the host passthrough (the Windows 11
host's USB stack under QEMU `usb-host`/libusb), before Windows 2000's
`usbehci.sys` sees any data. The native Windows 7 `usbvideo` run through
the same passthrough at 640x480 also got only 5-6 frames
(`2026-10-21-brio100-native.md`). Whether 2000's `usbehci.sys` carries
high-bandwidth isochronous transfers stays **unverified**; it needs a 2000
PC with the camera on a real EHCI port, or a host path that carries
high-bandwidth isochronous IN. The sizes are still advertised (owner,
2026-10-22: do not hide them yet).

If 2000 turns out not to carry high bandwidth: 640x480 at 10 fps (interval
1000000, about 780 bytes per microframe) and 640x360 at 15 fps fit
alternate 6 (944 bytes, one transaction), so choosing a longer listed
interval would keep those sizes without high bandwidth.

Separate driver issue seen in run 13: when the lower stack never completes
cancelled isochronous URBs, the stop drain waits forever and the guest
cannot shut down. That is the designed rule (only a completion frees a
transfer), but a stalled high-bandwidth stream reaches it.
