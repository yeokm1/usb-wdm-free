# rtl815x on 98 SE with a simulated RTL8153, 2026-10-23

Development legs, not a release and not "Tested": no RTL8152/8153 is on
the bench (`2026-10-22-ax88179-rtl815x.md`). These are the first runs of
`rtl815x.sys` against anything but its host tests' register file.

## The simulator

`src/net/rtl815x/rtlemu.py` (branch `simcov`, 620d7c9): a SIMULATED
RTL8152 (RTL_VER_02), RTL8153 (RTL_VER_04) or RTL8153B (RTL_VER_09) over
usbredir. It models what the driver's chip core reads and writes, not the
chip's firmware: the vendor configuration (class FF, bulk 0x81/0x02,
interrupt 0x83), the r8152 register protocol (request 0x05, PLA/USB MCU
types, byte enables), the PLA and USB spaces and the PHY OCP window (the
semantics of `rtltest.c`'s register-file model), the version in
`PLA_TCR0`, link in `PLA_PHYSTATUS` after an autonegotiation delay with an
`INTR_LINK` interrupt report on each change (`--flap-after`/`--flap-for`
pull the cable once), receive framing (24-byte rx_desc, FCS, 8-byte
records, several frames per bulk-IN transfer) gated by `PLA_CR` RE and the
`PLA_RCR`/`PLA_MAR` filter, and transmit framing (8-byte tx_desc). Behind
it a SIMULATED host 192.168.77.1 answers ARP, ICMP echo and DHCP
(192.168.77.2/24).

Limits: the register semantics are this repository's own model of
r8152.c's protocol, so a real chip's undocumented behaviour (firmware
patches, timing, what the PHY really reports) is not exercised. A real
RTL8152/8153 leg stays owed (REAL CHECK below).

Host tests: `python -B rtlsimtest.py` (8 tests) drive the driver's own
`NetPackageChip` (rtlchip.c, netchip.c, x64 DLL from `host.ps1`) through
the model's usbredir paths; see the commit.

## xHCI98 3.1.0.0: PASS

- Install: Add New Hardware found "RTL8153 Ethernet - SIMULATED", chose
  `A:\RTL81598.INF` ("Realtek RTL8153 USB Gigabit Ethernet (RTL815X)"),
  copied the networking files from the 98 SE CD and asked for a restart.
- Trace: probe of configuration 0 (value 1), chip start "version 4, 151
  requests", buffers rx 4 x 16384 / tx 4 x 16384, MAC 00:e0:4c:77:00:02
  (the simulator's `PLA_BACKUP`), "link 1, 1000 Mb/s full duplex".
- After the restart: DHCP DISCOVER, OFFER, REQUEST, ACK through the
  driver (simulator log), so receive and transmit both carry frames.
- `ping 192.168.77.1`: 8/8 at 1400 bytes, 4/4 at 1472 (the largest
  unfragmented frame) and 4/4 at 32 bytes, 0 % loss.
- Removal (usb-redir `device_del`): "halted: tx 35/4 rx 19 nobuf 0".

## NUSB 3.3 EHCI: PASS

- Plug on `ehci.0` (480 Mb/s): New Hardware Found, the INF's disk prompt
  needed `A:\` typed; the driver started as above, link 1000 full.
- DHCP REQUEST renewed the lease (ACK).
- Cable pulled 40 s after link-up for 8 s (`--flap-after 40 --flap-for
  8`): the interrupt report reached the driver, trace "link 0, 0 Mb/s",
  then "link 1, 1000 Mb/s full duplex".
- After the flap: `ping` 6/6 at 1000 bytes, 10/10 at 1472 bytes.
- Removal: "device gone", "stopped; 0 malformed transfers, 0 dropped
  frames, 0 with an FCS", "halted: tx 49/3 rx 18 nobuf 0".

## Verdict

rtl815x on 98 SE with the simulated RTL8153: install, bring-up, MAC,
link up/down/up, DHCP and ping at 32-1472 bytes, and removal PASS under
xHCI98 and under NUSB's EHCI. Not run: RTL8152 and RTL8153B on a guest
(host tests only), ME, 2000, multicast traffic, throughput, standby.

REAL CHECK NEEDED: an RTL8152 or RTL8153 adapter on 98 SE, under xHCI98
and under NUSB's EHCI (behind a USB 2.0 hub): install from
`RTL81598.INF`, then the trace lines "chip start: 0, version N" and
"link 1", a DHCP lease (`winipcfg`), `ping -n 20 -l 1472 <gateway>`, a
cable pull and replug during `ping -t`, and device removal. Look for: no
refused vendor request in the trace, the chip's own MAC, 0 malformed
transfers at halt.
