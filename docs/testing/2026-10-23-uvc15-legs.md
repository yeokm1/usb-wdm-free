# uvc98 on 98 SE with a simulated UVC 1.5 camera, 2026-10-23

Development legs, not a release and not "Tested". They run `uvc98` (the M2
stream-class miniport) against `uvcsim.py --uvc 1.5`, the UVC 1.5 profile
added for the simulator-coverage audit (`simulator-coverage.md`, rank 1).
No physical UVC 1.5 camera is on the bench.

## What the profile is

`uvcsim.py --uvc 1.5` (branch `simcov`, fabbc81): `bcdUVC` 0x0150, the
48-byte probe/commit (bUsage 1, bBitDepthLuma 8, payload version 1), a
13-byte processing unit (bControlSize 3), an encoding unit between the
processing unit and the output terminal, and four or five formats: YUY2,
MJPEG, NV12 (continuous intervals), and H.264 as frame-based
(`--h264 frame`, the default), as the UVC 1.5 `VS_FORMAT_H264` family
(`--h264 native`), or both (`--h264 both`). Layouts are from the UVC 1.5
class specification and its uncompressed, frame-based and H.264 payload
documents.

## Host tests

`python -I -B uvcsimtest.py` (24 tests) runs the profile through the
driver's own descriptor parser, payload assembler and, new here, its own
probe/commit sequence (`uvcneg.c` `UvcNegotiateLimited`, now in the
`host.ps1` DLL): every non-MJPEG frame at High and Full Speed negotiates
with three requests, the 1.5 tail survives COMMIT, and an NV12 interval
inside the continuous range is kept.

The `--h264 native` test found a driver defect: `uvcdesc.c` did not count
`VS_FORMAT_H264` (0x13), H.264 simulcast (0x15), VP8 (0x16) or VP8
simulcast (0x18) against `bNumFormats`, so such a camera was refused whole
(`UvcDescParse` returned `UVC_DESC_BAD`). Fixed on branch `uvc15-fix`
(576fc46, a90cf6f, 8a36d53; Codex rounds 1-3, the last "no findings"):
those subtypes are counted and skipped. All 24 tests pass against a DLL
built from the fixed parser; against the older parser the `native` test
fails.

## Rig

- Kit `E:\usb-wdm-free-vm\simcov` (scripts copied from the uvcsim kit with
  this kit's paths): monitor 49200, simulator 49201. Headless QEMU (Scoop
  `qemu-system-i386`), TCG, `-cpu pentium3,-apic`, 1 vCPU, 256 MB,
  `qemu-xhci` and `usb-ehci`. Overlay `s1` of
  `E:\usb-wdm-free\net9x\base\w98-nusb-hub.qcow2` (NUSB 3.3 and xHCI98
  3.1.0.0 installed); the base was only read.
- First boot: the Add New Hardware wizard installed NUSB's `USB2.INF` for
  the EHCI controller.
- Driver: `uvcm2.sys` checked VM-trace build of `uvc15-fix` 576fc46
  (`m2build.cmd checked vmtrace`), SHA-256 `72E72853...D228B`;
  `UVCM298.INF` `5A585A7F...B9FB`; `M1CAP.EXE` `06f41355...1c49`. The first
  plug (under xHCI98) raised the wizard, which found `UVCM298.INF` on the
  floppy and installed it.
- Capture: `M1CAP <hardware id> WxH`: three READs of a complete, changing
  frame = PASS.

## xHCI98 3.1.0.0 (QEMU `qemu-xhci`): PASS

| Simulator | Size | Result | Driver counters |
|---|---|---|---|
| `--uvc 1.5` | 160x120 | PASS; 3 frames byte-exact against the simulator's pictures (`vframes.py`) | alt 1 (192), 0 failed, 2-12 dropped |
| `--uvc 1.5` | 320x240 | PASS | alt 3 (640), 0 failed |
| `--uvc 1.5` | 640x480 | PASS (QEMU-paced, as with UVC 1.1) | alt 7 (3 x 800), 0 failed |
| `--uvc 1.5 --h264 both` | 160x120 | PASS; the driver loads with 3 YUY2 formats exposed (`USB_FORMATS 3`), i.e. the `VS_FORMAT_H264` and frame-based H.264 formats skipped | alt 1, 0 failed |

Every probe and commit was 48 bytes (simulator log: GET_LEN answered 48,
`requested: 48`); the committed values were the device's own (160x120:
interval 333333, frame 38400, payload 192). The 320x240 and 640x480 frame
files were not saved (the floppy folder is read by QEMU's vvfat once), so
those two rely on M1CAP's three complete changing frames.

## NUSB 3.3 EHCI (QEMU `usb-ehci`): binds, FAIL in QEMU

`--uvc 1.5 --h264 both` on `ehci.0` (480 Mb/s): the driver loaded with
the 3 YUY2 formats and the 48-byte negotiation committed 160x120 (interval
333333, payload 192). The capture failed as every NUSB-on-QEMU leg has
(`2026-10-23-uvcsim-98se.md`): the simulator sent 65929 packets, the guest
counted 41936 (64 %), 11982 of them zero-length (QEMU underruns) and 794
failed, 0 frames, READ error 1460. Same signature as the UVC 1.1 runs; the
2000 `usbehci` control there passes, so the loss is NUSB on QEMU's EHCI,
not the profile. The REAL CHECK for NUSB on real EHCI hardware stands.

## Verdict

UVC 1.5 descriptor parse, 48-byte negotiation and streaming: PASS under
xHCI98 at 160x120, 320x240 and 640x480, and with a `VS_FORMAT_H264`
format present once the parser fix is in. NUSB EHCI: binds and negotiates;
streaming FAIL in QEMU (vehicle, unchanged).
