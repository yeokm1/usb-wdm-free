# xpad98 first guest legs with the pad simulator, 2026-10-23

The owner decided on 2026-10-22 that xpad98's VM legs use a usb-redir pad simulator, as `usbcom` and
`usbmidi` do; real pads stay with the owner's bench. These are xpad98's first guest legs. They ran in QEMU
(TCG, headless), one guest at a time: smp 1, except smp 2 on Vista. They are VM passes and do not make a
"Tested" cell. Nothing is released.

## Tools

The tools are in commit `a1075e2`, with the later sequence-check fix:

- **`src/hid/xpad98/xpademu.py`** is the simulator. It is exported to QEMU over localhost usbredir, and has
  four profiles:
  - `x360`: 2DC8:3106, a 360-protocol pad outside x360c's list.
  - `xone`: 045E:02EA.
  - `series`: 045E:0B12.
  - `receiver`: 045E:0719.

  It runs at Full Speed, or High Speed with `--speed high` (a test device shape so that EHCI carries
  it; real pads are Full Speed). It answers what the driver sends and walks a fixed pattern: every
  button, the four d-pad directions, both ends of each stick axis, and each trigger.
- **`simtest.ps1`** builds the driver's own cores (`xusb.c`, `gip.c`, `xpcfg.c`, `devtab.c`, `report.c`)
  as an x64 DLL. **`xpsimtest.py`** then checks the simulator's descriptors and packets with those parsers:
  12 tests, all passing.
- **`joytest.c`** builds `JOYTEST.EXE` (MSVC 6.0, WinMM) with `joytest.cmd`. It polls `joyGetPosEx` on ids
  0-15 for N seconds and writes `C:\JOYTEST.TXT`. An id passes when every button it reports was seen
  pressed, every axis it reports reached both ends of its range (within 10 %), and the POV showed the four
  directions and centre.

## What this shows and what is owed

- **The driver's USB protocol work** behaves as the design says on 98 SE, 2000, XP and Vista: the 360
  start request and LED, and the GIP init sequence, sequence numbers and Guide acknowledgement. This
  is against a simulator built from the same packet layouts, so it shows the driver and the
  simulator agree, not that a real pad agrees.
- **NT HID path:** PASS on 2000, XP and Vista (WinMM sees every control). The axis maps differ: U/V on
  2000, R/U on XP and Vista. This is a design 4.1/6.2 reading for M1/M2.
- **98 SE gate: FAIL.** Under UHCI and NUSB EHCI the HID collection exists, but WinMM cannot read it
  ("not connected correctly"). The likely place is the 98 SE HID read path (`joyhid`/VJOYD reading
  through HIDCLASS from xpad98), which design 12 marks undocumented. Under xHCI98 3.1.0.0 the start
  fails with Code 10 before SET_CONFIGURATION. Both need a trace build of xpad98 (the driver has no
  0xE9/debug trace) and the driver owner's work. The simulator and JOYTEST make the rerun one command each.
- **Not run:** the receiver profile; ME; 2000 under xHCI98; XP x64 and Vista x64. The x64 build is
  unsigned and needs test signing (build.md 7.4).

## 98 SE: the two failures diagnosed and fixed (commit `5758369`, reruns 2026-10-23)

### Tools added

- **Trace flavour.** `build.cmd wdmx86 trace` is a free build with `XP_TRACE_E9`. It writes
  `xp: <event> a b c` lines to QEMU's 0xE9 debug console: PnP, power, every HID IOCTL, the descriptors,
  the reports and every URB status. It is test-only and never released.
- **`HIDTEST.EXE`** (`hidtest.c`, `hidtest.cmd`) is a guest tool. It reads a HID device through hid.dll
  and reports what the guest's HID parser makes of it: `HidP_GetValueCaps`, and per report
  `HidP_GetUsageValue` / `HidP_GetScaledUsageValue` with their status codes.
- **Reference profiles in the simulator**, served by Windows' own `hidusb.sys` (USB HID class 03), to
  separate the descriptor from the minidriver:
  - `hidpad`: a plain 1990s-style 8-bit pad;
  - `hidxpad`: xpad98's own report descriptor;
  - `--variant`: test changes to that descriptor.

### (a) UHCI and NUSB EHCI: "not connected correctly"

Three causes, all in the report descriptor. They were isolated with the reference profiles on 98 SE under
UHCI:

1. **98 SE's HID parser reads a 16-bit field as signed.** The old axis range 0..65535 put every value from
   32768 up out of range. The centre is 32768, so the pad was out of range at rest. HIDTEST showed
   `HidP_GetScaledUsageValue` returning `C0110005` for those values and succeeding below 32768. Changing
   the range to signed -32768..32767 fixed the parse but not joyhid.
2. **joyhid refuses a collection that uses Rx or Ry.** The `hidxpad` profile (xpad98's descriptor, but
   under hidusb) failed the same way: WinMM showed no joystick at all. The `rz` variant, which moves the
   right stick to Rz and Slider, passed JOYTEST. Rz lands on WinMM R and Slider on U.
3. **VJoyD maps a signed logical range wrongly.** With the `rz` variant the centre read 0, and negative
   values clamped to 0. The `rz15` variant (Rz/Slider with Logical 0..32767) passed with correct centres.

The fix in `report.c` and `xpad98.c`:

- Axes are Logical 0..32767 in 16-bit fields on every system. This reads the same whether a parser treats
  the field as signed or unsigned, and WinMM still maps it to 0..65535.
- On 9x the right stick takes Rz and Slider. The driver detects 9x as `IoIsWdmVersionAvailable(1, 0x10)`
  false and sets `XP_OPTIONS.Win9x`. Layout 2 already uses Rz, so there it takes Slider and Dial; that case
  is unverified.
- NT keeps Rx/Ry.

New host checks:

- every value field's logical range must fit its report size read as signed (the 98 SE rule);
- the 9x usage map for layouts 0 to 2, against the descriptor and the report.

### (b) xHCI98 3.1.0.0: Code 10

The trace showed the cause: `select 000000e4 00000004 00000007` followed by
`select-done c000009a 00000000 80000100`. That is a SELECT_CONFIGURATION listing all four interfaces of
the wired 360 pad, 7 endpoints in total, refused with `USBD_STATUS_NO_MEMORY`. UHCI and NUSB accept the
same URB. In xHCI98's source, `xhci.h` defines `XHCI_MAX_DEVICE_ENDPOINTS 4UL` as a per-device ring-pool
cap. That is a candidate, not a confirmed cause: xHCI98 task 43.67 is checking it.

Observed so far:

- the 360 pad's 7 endpoints are refused, its own 2 are accepted;
- the receiver's 4 pad interfaces, 8 endpoints, are refused too (below).

The fix in `usbio.c` and `xpcfg.c`: when the full select fails, select again listing only the interfaces a
channel uses (`XpSelectSet`, host-tested). The 360 pad's headset, plug-in and security interfaces are
never used here. The trace shows the fallback: `select 00000050 00000001 00000002`, then `select-done 0`,
then `start 0`.

**xHCI98 task 43.67.** The build is branch p43-67 `ef9c8194`, which raises the ring pool's per-device
cap to 16, in its gated qemu flavour: `src\objchk_qemu\i386\xhci98.sys`, SHA-256 `F6171904...2895` as
in `out\gated-x86-qemu.txt`. I did not build it. It was copied over a fresh `w98-hcd310` overlay's
`XHCI98.SYS`, and the guest was cold started; its trace confirmed the new driver. The xpad98 trace build
then ran:

- **360 pad**: the **full** select now succeeds on the first try. The trace shows
  `select 000000e4 00000004 00000007` then `select-done 00000000`; no fallback was needed.
  JOYTEST **PASS**.
- **Receiver**: the full select of all 8 interfaces and 16 endpoints succeeds
  (`select 000001d8 00000008 00000010` then `select-done 00000000`), and the driver starts with 4
  channels. JOYTEST: 4 ids, the connected slot **PASS**.

So under xHCI98 3.1.0.0 the receiver stays unsupported, as decided on 2026-10-23. With 43.67 it works,
and xpad98's interface-subset fallback remains only for older xHCI98 releases.
