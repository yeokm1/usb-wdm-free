## The release operation

`release\release.ps1 -Definition release\0.1.0.psd1` (build.md section 7)
copies the build results into `free\<class>\<pkg>\<folder>\` and checks:

1. each INF: Signature (no `$CHICAGO$` INF for an x64 system), DriverVer
   (a real date, parts below 65535, not 0.0.0.0), AddService names, their
   service-install sections and ServiceBinary, the 9x NTMPDriver,
   DeviceVxDs and PortDriver files, every file it copies present in its
   folder or a declared Windows file (LayoutFile) or section (Include),
   models for every system its line names, the folder's systems fitting
   its architecture, whole-device ids only
   where the definition records the design's allowance, no bare
   `USB\Class_xx`; each image's architecture; x86 images unsigned; x64
   drivers with one aligned WIN_CERTIFICATE (revision 2.0, PKCS#7, zero
   padding) holding one signature by thumbprint
   `814CF778B45159EC2659C39C16C7E75EB3C37145`, SHA-1, whose
   SpcIndirectDataContent digest matches the image, and that differ from
   their unsigned build only in the checksum and the certificate table;
2. 8.3 names, reserved DOS names, case-insensitive collisions under `free\`;
3. each folder holds exactly its files (README.TXT and declared extras
   aside);
7. `STAGE.TXT` written from the definition (STAGE/COPY, PACKAGE, EXCLUDES,
   COEXISTS lines): every INF on one line, no hardware id staged twice on
   one system over this set and usb-wdm-nonfree's (`-NonFree`); then
   `SHA256.TXT` over `free\`, verified.

Build results are taken from `out\` when their build record names HEAD or
an earlier commit whose package sources (images: code; copied files: their
own source and build scripts) did not change since. The four x64 drivers
were built at d8d6e0b and signed by the owner (WDK 7.1 SignTool, SHA-1,
`/nph`, no timestamp); cdcnet's two builds are kept as `keep-ndis5` and
`keep-ndis51` so the signed image stays bound to its build when cdcnet's
INFs changed. The xHCI98 packager's own readers (`Read-StageText`,
`Assert-StageCovers`, `Read-OtherStageMeta` with `brand-words.txt`,
`Test-OtherStageIds` over both sets; p43-42t `package-common.ps1`) accept
the result: 39 lines for 39 INFs, 15 metadata lines, no id twice.

## cdcnet's released INFs bind QEMU usb-net (2026-10-24)

xHCI98's matrix leg N6 (98 SE, xHCI98 3.2.0.0, the free set staged) found
that the released `free/net/cdcnet/w98se-me/CDCNET.INF` does not bind QEMU
`usb-net`: Add New Hardware said "Windows was unable to locate a driver".
The device is class `02` at the device level (hardware ids
`USB\VID_0525&PID_A4A2&REV_0000`, `USB\VID_0525&PID_A4A2`; compatible ids
`USB\CLASS_02&SUBCLASS_00&PROT_00`, `USB\CLASS_02&SUBCLASS_00`,
`USB\CLASS_02`), so no stack splits it, and the released INFs listed
interface-level ids only. Every `cdcnet` leg had run the test INFs
(`CDCT98.INF`, `CDCTEST.INF`), which bind `USB\VID_0525&PID_A4A2`, so
STAGE.TXT's "legs passed (QEMU usb-net)" was never true of the released
INF.

Fix (branch `cdcnet-rel` from v0.1.0): `CDC98.INF` and every models section
of `CDCNET.INF` list `USB\VID_0525&PID_A4A2` on the same `CDC` install
sections the test INFs use; no device-class line (it would take CDC ACM
modems). The release definition records the id as allowed for `net/cdcnet`
(ethernet.md section 5.1) and takes cdcnet's INFs from the tree
(`tree:src\net\cdcnet\...`, CRLF as `build.cmd` writes them): the images
stay the 0276532 builds the owner signed, and the out\ INF copies are bound
to that build's commit. `release.ps1 -OutRoot E:\usb-wdm-free\wt-release
-X64Dir <the four signed x64 images as committed at v0.1.0> -NonFree
<usb-wdm-nonfree v1.0.0>`, with `CAMCHECK.EXE` placed in `out\` from its
v0.1.0 blob, passed. Against v0.1.0, every file under `free/` but the five
`CDCNET.INF` files has the same git blob (the eight x64 `.sys` files, both
x86 `CDCNET.SYS`, `CAMCHECK.EXE` among them); `usb-wdm-free-test.cer` is
untouched; `STAGE.TXT` changes only in cdcnet's notes and `SHA256.TXT` only
in the five INF lines. cdcnet ships no catalog (build.md section 7, step 4),
so the INF change needs no signing.

## uvc98 streams to Video for Windows; the final re-cut (2026-10-24)

CamCheck previewed 0 frames from `uvcm2.sys` on 98 SE and 2000: the
capture pin declared no `KS_FRAME_INFO` extended header and no connection
or dropped-frames properties, so the VfW mapper's reads never reached the
driver. Branch `uvc-vfw` (from v0.1.0, head `e749085`) fixes the pin,
offers RGB24 (converted from YUY2 in the driver) ahead of YUY2, reopens
the device queue at `SRB_UNINITIALIZE_DEVICE` (the unplug hang) and counts
dropped frames from each stream's start. Preview, camera switching, and
unplug with Stop then re-preview pass in QEMU on 2000 SP4 (Windows' EHCI)
and 98 SE (xHCI98 3.1.0.0) with simulated cameras:
[uvc98-vfw](2026-10-24-uvc98-vfw.md). No real camera has run this build.

Branch `rel-0.1.0-final` merges `cdcnet-rel`, `uvc-vfw` and `main`'s
`11ef0de` onto v0.1.0 and regenerates the tree: `release.ps1 -OutRoot
<E:\usb-wdm-free\wt-release's out\, with uvc-vfw's m2x86 free build in
place of its uvc98 one> -X64Dir <the four signed x64 images as committed
at v0.1.0> -NonFree <usb-wdm-nonfree v1.0.0>`, `CAMCHECK.EXE` placed in
`out\` from its v0.1.0 blob: PASS, 81 files. The released `uvcm2.sys` is
the tested image (29,312 bytes, SHA-256 `d344ecef...a9afa5`); a rebuild
of the merged tree with `m2build.cmd free` differs from it only in the PE
time stamp and checksum. Against v0.1.0 only the five `CDCNET.INF` files,
both `uvcm2.sys` copies, `STAGE.TXT` (cdcnet's notes) and `SHA256.TXT`
(those seven lines) change; uvc98's INFs, every x64 `.sys`, `CAMCHECK.EXE`
and `usb-wdm-free-test.cer` keep their blobs. uvc98 is x86 only and
unsigned, so nothing is re-signed; no catalog.
