# uvc98 in Video for Windows (CamCheck): live preview, 2026-10-24

## The finding

A tester's CamCheck run of usb-wdm-free v0.1.0 (36e0a3d3) found that
`uvc98` never shows live video in a Video for Windows application on
Windows 2000 SP4 or 98 SE. The setup:

- two emulated cameras, `uvcsim.py` over `usb-redir`;
- CamCheck connected to "Microsoft WDM Image Capture (Win32)", the VFWWDM
  mapper.

What it saw:

1. Preview failed with VfW error 439, "Unable to draw this data format".
   `uvc98` offered YUY2 only, and neither system has a YUY2 decompressor.
2. With XP's `msyuv.dll` added as a test aid, preview said "Preview=on" with
   0 frames. The driver's VM trace showed the mapper open the stream and
   set its state, and no `SRB_READ_DATA` reached the driver. M1CAP, the
   package's own capture tool, read frames from the same driver.
3. Smaller issues:
   - both cameras have the same name in the Source dialog;
   - on 2000, unplugging the open camera while it previews hangs CamCheck.

These are development legs in QEMU with simulated cameras, not "Tested".

## Causes

**No frames.** The capture pin did not meet the 2000 DDK's video capture
pin contract (`docs/design/uvc.md` 3(c), "What the capture pin must
declare to stream").

- **Extended header.** A capture pin's stream header extension is
  `KS_FRAME_INFO`, declared in `StreamHeaderMediaSpecific`. `uvc98`
  declared 0.
- **Property sets.** `KSPROPSETID_Connection` (allocator framing) and
  `PROPSETID_VIDCAP_DROPPEDFRAMES` are required. `uvc98` declared none.
- **What M1CAP did differently.** M1CAP sent bare 48-byte headers, so it
  streamed. The mapper's reads carry the `KS_FRAME_INFO` (112 bytes) and
  never reached the 0.1.0 driver.

**Error 439.** The mapper's default format is the pin's first range, and
0.1.0's first range was YUY2.

**The unplug hang (2000, and 98 SE too once preview streams).**
- On surprise removal, the stream class sends `SRB_SURPRISE_REMOVAL` and
  then `SRB_UNINITIALIZE_DEVICE` at once, while the client's stream is
  still open.
- `uvc98` completed the UNINITIALIZE without reopening its device queue: a
  bare `DeviceRequestComplete`, where every other request completes with
  `StreamClassCompleteRequestAndMarkQueueReady`.
- So the client's later close of the pin (`SRB_CLOSE_STREAM`, a device
  request) could never be dispatched. CamCheck hung in its Stop, and the
  process could not be ended.
- Read statuses were not the cause. The DDK's documented
  `STATUS_DEVICE_REMOVED` alone changed nothing.

## The fix (branch `uvc-vfw`)

- **`uvcm1.c`:** the pin declares `StreamHeaderMediaSpecific =
  sizeof(KS_FRAME_INFO)` and the two property sets, answered from the
  engine's counts:
  - `KSPROPERTY_CONNECTION_ALLOCATORFRAMING`: 3 frames of the open
    format's size;
  - `KSPROPERTY_DROPPEDFRAMES_CURRENT`.
- **`uvcwork.c`:** fills the `KS_FRAME_INFO` of each completed read.
  - Picture number and drop count are kept since the stream was opened or
    stopped. Drops include the camera frames no read took, counted from the
    camera's frame sequence at each stream start (`UvuLatestSequence`), so
    an earlier session's frames are neither delivered nor counted.
  - Once the camera has started, a camera timeout completes an empty read
    instead of a failed one. A failed start still fails the read
    (`UVPORT.AllowEmpty`, M2 engine only).
- **`uvcfmt.c`:** RGB24 bottom-up ranges, converted in the driver from
  YUY2, come before the YUY2 ranges.
  - There are up to 32 frames, each offered both ways (`UVFMT_MAX` 64).
  - The open stream accepts any frame rate the client asks for, and the
    camera's committed rate is delivered.
  - Matching and intersection handle RGB24 and wildcard GUIDs.
- **Removal (`uvcportn.c`, `uvcm1.c`):**
  - The M2 driver completes UNINITIALIZE with
    `StreamClassCompleteRequestAndMarkQueueReady`, like every other request.
  - A `CLOSE_STREAM` that arrives after it succeeds (nothing is left to
    close).
  - A read after `SRB_SURPRISE_REMOVAL` fails with `STATUS_DEVICE_REMOVED`
    (2000 DDK, USBCAMD processing table), and a later state change succeeds.
  - The M2 import gate no longer lists `StreamClassDeviceNotification`.
- **`m1cap.c`:** sends the `KS_FRAME_INFO` header, picks a YUY2 range, and
  has a 64 KB range buffer.
- **`uvcsim.py`:** `--mark N` puts N-wide white cells in the bottom
  quarter of the YUY2 picture, so two simulated cameras look different.

Tried and dropped: holding `SRB_SURPRISE_REMOVAL` until the client closed
its stream.
- On 2000 it worked.
- On 98 SE it blocked Msgsrv32 ("Not responding") and CamCheck's keyboard
  input.
- The queue fix above makes the hold unnecessary on both.

Sources: the 2000 DDK stream class and video capture documentation
(`D_STREAM.CAB`, decompiled to HTML and read as documentation), the 2000
DDK `ks.h`/`ksmedia.h`/`strmini.h`, and MSVC 6.0 `UUIDS.H` for the RGB24
subtype GUID. No driver-kit sample source was read.

## Review

A Codex review of the first commit (6514c14) found no P1 and four P2. All
four are fixed in the second commit (7fdfe19):

1. RGB24 ranges could take the capacity the YUY2 ranges had.
2. M1CAP's 4 KB range buffer was too small for the doubled list.
3. Drops omitted overwritten frames.
4. An empty-read success could hide a failed stream start.

A second Codex review, of 7fdfe19, found one P2: frames overwritten before
the first read of a stream were still not counted as drops. It is fixed in
the third commit. That review found the removal change sound: no engine or
device-extension access after the UNINITIALIZE notification, and every
request after it answered without the engine.

## Results

### Windows 2000 SP4, Windows' EHCI

**Trace build, the mapper's session.** CamCheck previewed live (160x120
RGB24, frame counter rising):

```
DEVICE_SRB 0000010C   INTERSECT_SUBFORMAT E436EB7D (RGB24), 160x120
DEVICE_SRB 00000101   OPEN_SUBFORMAT E436EB7D  OPEN_MATCH 00000000
CONTROL_SRB 00000005  STREAM_PROPERTY_SET 0  ID 3 (ALLOCATORFRAMING)
CONTROL_SRB 00000003  SET_STATE 00000002 (PAUSE)
CONTROL_SRB 00000003  SET_STATE 00000003 (RUN)
READ_SRB 00000000     READ_HEADER_SIZE 00000070  READ_FRAME_EXTENT 0000E100
COMPLETE_SRB 00000000 COMPLETE_STATUS 00000000   (repeats)
```

**Camera switch.** Choosing the other camera in the Source dialog gave
PAUSE, STOP and CLOSE_STREAM on the first, then intersection, open,
framing, PAUSE, RUN and reads on the second. The picture changed to the
other camera's mark.

**Unplug, trace of the final build.** With camera 2 open and previewing:

```
DEVICE_SRB 0000010E   (SURPRISE_REMOVAL; USB stop)   COMPLETE 00000000
DEVICE_SRB 00000109   (UNINITIALIZE)                 COMPLETE 00000000
DEVICE_SRB 00000102   (CLOSE_STREAM, after Stop)     COMPLETE 00000000
```

CamCheck: "Preview stopped; camera disconnected." Preview then showed the
remaining camera, and CamCheck exited normally.

**Final free build, every check PASS:**
- preview of camera 1 (320x240 RGB24) and camera 2 (160x120);
- switching via the Source dialog;
- unplugging the open camera, then Stop;
- preview of the remaining camera;
- exit;
- M1CAP on camera 1: three changing 160x120 YUY2 frames, header bytes
  112, pictures 1-3.

Earlier runs of the first commit also showed:
- the Format dialog offering 160x120, 320x240 and 640x480, with RGB 24
  the default depth;
- 320x240 RGB24 previewing live.

**Mapper selection after a restart.** After a guest restart, the
mapper's remembered device and the name its Source dialog showed did not
agree. Choosing an entry explicitly always opened that camera.

**Screendump tearing.** Some screenshots show two bar phases in one
picture. The frames themselves are whole (M1CAP's frames, and the next
screenshots). The likely cause is QEMU's screendump catching the window
mid-paint, under TCG.

### Not done

- The two cameras still share one name ("USB Video Class camera (uvc98)")
  when one INF binds both. The INF writes one `FriendlyName` per
  interface. A per-device name (from the camera's product string) needs
  the driver to write its interface keys. Not attempted.
- A camera replugged on 2000 while the other still uses `uvcm2.sys` asked
  for a restart: Setup wanted to replace the loaded driver file. This is
  an install artifact of these legs, not a removal fault.
- The package's host tests were not run: they execute test programs on the
  host, which this task's rules do not allow. The changed portable code
  (`uvcport.c`) keeps its old behaviour unless the M2 engine sets
  `AllowEmpty`.
- No NUSB leg; no real camera; no ME; 640x480 RGB24 not previewed (TCG).
