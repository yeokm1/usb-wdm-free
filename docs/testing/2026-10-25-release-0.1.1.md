# Release 0.1.1: `ax88179` added, 2026-10-25

Owner decision 2026-10-25: release `ax88179` in 0.1.1, for xHCI98
3.3.0.0's `-free` download. 0.1.0 had left it out (no decision recorded
then); the README said so from `896c598`. Branch `rel-011` from `main`
`896c598`.

## What changed

- `ax88179` is version 0.1.1: `DriverVer=10/25/2026,0.1.1.0` in
  `AX179F.INF` and `AX179F98.INF`, 0.1.1.0 in `ax179f.rc` (`a081065`).
  No code change: the source is the final one of
  [ax88179-fcs](2026-10-22-ax88179-fcs.md) (the settle cycle at start and
  the FCS anomaly report), whose `h1` sessions ran it.
- `release\0.1.1.psd1`: 0.1.0's definition plus `net/ax88179` (DEVICE,
  service `ax179f`, folders `w98se-me` and `w2k` as ethernet.md section
  7.4 lists them) and its `EXCLUDES` line with usb-wdm-nonfree's
  `ethernet/ax88179` on every system (the same chips, as `rtl815x`).
  Every 0.1.0 package and the CamCheck tool take their files from the
  0.1.0 tree (`tree:free\...`), not from `out\`: their bytes are 0.1.0's,
  and the out\ build records of 0.1.0 name commits this repository's
  history no longer has. The four signed x64 images come the same way;
  the release operation still checks each one's signature, signer and
  SHA-1 image digest (`Test-Image`); only the comparison with the
  unsigned build (`x64:` sources) is not repeated.

## STAGE.TXT and the README

- `AX179F98.INF`: `STAGE` on 98 SE and ME. The legs, all with the
  owner's AX88179 (`0B95:1790`) passed through to the guest in QEMU
  ("real device via VM"), with ndis5 trace builds: 98 SE under xHCI98
  3.1.0.0 and under NUSB 3.3's EHCI, ME under xHCI98 3.1.0.0: install,
  DHCP, pings at 0 to 4000 bytes, removal under traffic and replug

## Not run, and the open point

- The release build itself (no trace) has no guest leg: the legs ran
  trace builds, which differ from a free build of their source only by
  the 0xE9 trace calls.
- **FCS after a plug-in**: in the first session after the dongle was
  plugged in, the chip forwarded the FCS of every frame (once under
  NUSB's EHCI on 98 SE, and in the 2026-10-21 host-side run). The
  driver strips a valid FCS and writes one NDIS hardware-failure entry
  per adapter. The settle cycle at start is meant to avoid it and is
  unverified: QEMU cannot power the dongle off. The owner's bench check
  in [ax88179-fcs](2026-10-22-ax88179-fcs.md), "Owed", settles it.
- Windows 2000 not evaluated; no ME leg under an EHCI stack; no bulk
  throughput test; standby/resume, cable unplug, disable/enable and
  `NetworkAddress` not run.
