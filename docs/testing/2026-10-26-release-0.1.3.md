# Release 0.1.3: class matches, 2026-10-26

Owner decision 2026-10-26 (xHCI98 roadmap 44.44): a class driver matches
its USB class's compatible ids on every system where Windows has no
driver of its own for that class, and lists devices elsewhere, so that
Windows' own class driver stays the default there. Branch `relicense`,
after `v0.1.2` (`c9b5269`).

## The table, and what changed

[build.md section 7.1](../design/build.md) tabulates each class driver and
system with the source of each fact. `uac2`, `usbmidi` (98 SE and 2000),
`cdcnet`, `usbflop` and `uvc98` already matched their classes on the
systems where Windows has none. `usbcom` did not: `90fd078` adds
`USB\Class_02&SubClass_02` (the CDC-ACM function) to `USBCOM.INF` (98 SE,
ME) and to `USBCDC.INF`'s 2000 section, as `USBCDC.INF` already had on XP
and later ([serial.md section 5.4](../design/serial.md)). The three usbcom
INFs are `DriverVer=10/26/2026,0.1.3.0`; `USBCOM.SYS` and `USBCOMV.VXD`
are unchanged. Found in review: `cdcnet`'s `CDCRNDIS.INF` matched
`USB\Class_EF&SubClass_04&Prot_01` on 7, which Windows 7's own
`rndiscmp.inf` matches; that line is dropped from its 7 sections (x86 and
x64), the INF 0.1.3.0, `CDCNET.SYS` unchanged.

## The release operation

`release\release.ps1 -Definition release\0.1.3.psd1 -NonFree
<usb-wdm-nonfree 418dda1>`: PASS, 85 files. Against 0.1.2 only seven
INFs change: usbcom's three (`w98se-me/USBCOM.INF` `e2cafa33...9d23cf844`,
`w98se-me/USBCOMP.INF` `8c7f54dd...b51910f62b`, `w2k-8/USBCDC.INF`
`41dee8ee...bf9c71b7`) and cdcnet's four `CDCRNDIS.INF` copies (`w2k-xp`,
`wv-7-x86`, `wxp-x64`, `wv-7-x64`, each `ca53f2fb...ab3ad1561e`), with
`STAGE.TXT` (usbcom's note) and `SHA256.TXT`.
No image changes, the signed x64 images among them: nothing to sign.
