# uac2 and Windows' software MIDI synth (98 SE, XP x64), 2026-10-28

A user reported "midi is just silent" with `uac2`. They then said they use
Windows XP x64, a CX31993-based USB headphone DAC, and "MIDI" means a `.mid`
file played through Windows' own software synth. That synth is the
"Microsoft GS Wavetable SW Synth": `SWMIDI.SYS`, which SysAudio renders
through KMixer to the default WDM audio device. This record runs that case
with simulated devices on 98 SE and XP x64. Development legs in QEMU, not
"Tested". Branch `uac2-midi` from `48c1366` (release 0.1.4).

## Result

**Cause.** `uac2wdm.inf` (every folder, released 0.1.0 to 0.1.4) registered
`Drivers\SubClasses` = `"wave,mixer"`. Without the `midi` subclass, WDMAud
gives WinMM no MIDI output for the device, so when a `uac2` device is the
only audio device no SW synth is listed. `SWMIDI.SYS` is installed either
way (`WDMAUDIO.Registration`; MEDIA keys "Microsoft Kernel GS Wavetable
Synthesizer" on both systems). Media Player (`mplayer.exe` on 98 SE,
`mplay32.exe` on XP x64) answers "This device cannot play." for a `.mid`
file, while `.wav` files play. Windows' own USB audio INF (XP x64
`wdma_usb.inf`, `[USBAudio.AddReg]`) registers `"wave,midi,mixer,aux"` with
`Drivers\midi\wdmaud.drv` for its playback sections and `"wave,mixer"` for
its microphone section.

**Fix** (`90ac079`). `uac2wdm.inf` and `x64\uac2wdm.inf` register
`"wave,midi,mixer"` and `Drivers\midi\wdmaud.drv` (`Driver`,
`Description`), `DriverVer` 0.1.5.0. With it the SW synth is listed on both
systems and `.mid` files reach the device with signal. Driver binary
unchanged (0.1.4's `uac2wdm.sys`).

**Workaround for the released 0.1.4 INF** (until a release carries the
fix): add the three values to the device's driver key and restart
Windows. On 98 SE the key is `HKLM\System\CurrentControlSet\Services\Class\MEDIA\<nnnn>`.
On XP it is `HKLM\SYSTEM\CurrentControlSet\Control\Class\{4D36E96C-E325-11CE-BFC1-08002BE10318}\<nnnn>`.
In both, `<nnnn>` is the instance whose `DriverDesc` is "UAC2 USB audio
(experiment)". The values are `Drivers` `SubClasses` = `wave,midi,mixer`,
and `Drivers\midi\wdmaud.drv` `Driver` = `wdmaud.drv` and `Description` =
any name, all strings (`REG_SZ`). This workaround was not run here.
Reinstalling the device with the fixed INF was run (below). On XP x64 the
reinstall over the 0.1.4 INF (`xp1`) also wrote `midi` = `wdmaud.drv` under
`HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Drivers32`
(`ev\xp1b\d33.reg`). The first install of the fixed INF (`xp2`) did not
(`ev\xp2\d33.reg`, `d34.reg`), and the synth was listed there all the
same (`ml3.txt`, `mw3.txt`), so that value is not needed.

## Rig

Kit `E:\usb-wdm-free-vm\uac2-midi`, ports 49290-49293, headless QEMU,
TCG, `-machine pc` (i440FX, as the earlier `uac2` legs). The uac2 binaries
under test are the release 0.1.4 `uac2wdm.sys` files: `w98se-me` (sha256
`ec4fcce5...cec24d51`) and `wxp-x64` (`a5bb67a1...536fd7`). The INFs are
0.1.4's (`w98se-me` `8d0de7c4...00f04144`, `wxp-x64` `d53312e8...6456dc`)
and the fixed ones (`c21b7eac...95481ba` x86, `c2b15e80...30c1c5` x64).

- **98 SE**: overlays `m1`, `m2`, `m3` of
  `E:\usb-wdm-free\net9x\base\w98-nusb-hub.qcow2` (98 SE with NUSB 3.3 and
  xHCI98 3.1.0.0); 1 vCPU, 256 MB, `qemu-xhci`, the device on `xhci.0`
  port 1 (xHCI98). The INF and `.sys` were copied into `INF` and
  `SYSTEM32\DRIVERS`, then the guest was shut down and cold-started with
  the simulator attached. The device was present at boot, as the README's
  freeze advice says. The install asks for the "UAC2 experimental build
  folder" disk and then for KS files (`ks.cat`, `ksclockf.ax`, ...) that
  are already installed. Those prompts were skipped, as in the ME leg of
  release 0.1.1.
- **XP x64**: overlays `xp1`, `xp2` of `E:\usb-wdm-free\vm\wxp64.qcow2`;
  2 vCPU, 2 GB, `usb-ehci` with Windows' EHCI driver. `uac2` was installed
  with the native x64 `MIDITEST install` (`MT64.EXE`), unsigned prompt
  accepted.
- Players: Media Player with `/play /close`. On 98 SE the file was
  `TEST.MID` (a 7.75 s piano scale and chords, written by the kit's
  `tools\mkmid.py`). On XP x64 it was the in-box `town.mid` and
  `flourish.mid`. WAV: `tada.wav` (98 SE), `Windows XP Startup.wav`
  (XP x64). WinMM lists: `UACWAV list` (wave), `MIDITEST list` (MIDI; x64
  and WOW64 builds on XP x64), the Multimedia control panel's MIDI tab
  (98 SE).
- At the simulator (`uacemu.py`): the alternate, format and rate of each
  stream, and the OUT bytes and non-zero bytes per quarter second. One
  `x4` leg also kept the PCM, which its 4 MiB limit ended after 22 s.

## The CX31993 model (`uacemu.py --profile cx31993`)

Source: the `lsusb -v` listing of a "CX31993 384Khz HIFI AUDIO" (`06cb:1595`,
Synaptics) in a Linux hardware probe,
<https://linux-hardware.org/?log=lsusb&probe=908f53f58b> (read 2026-10-28,
facts only):

- **Read from the listing.** An IAD with function 01/00/20 over interfaces
  0 and 1. AC interface 0 (UAC 2.0, header `wTotalLength` 0x40) holds
  clock source 9 (internal programmable, frequency read/write, validity
  read), input terminal 1 (USB streaming, 2 channels, `bmChannelConfig` 3),
  feature unit 2 (`bmaControls` master 0x03, channels 0x0c 0x0c: master
  mute, per-channel volume) and output terminal 3 (headphones 0x0302).
  AS interface 1 has alternates 1, 2 and 3: 2 channels, subslot 2/3/4,
  16/24/32 bits, OUT endpoint 0x01 isochronous **synchronous** (0x0d),
  `wMaxPacketSize` 192/288/384, `bInterval` 1, no feedback endpoint. HID
  interface 2 has an interrupt IN endpoint.
- **Assumed.** The rate list (the clock's RANGE answer is not in a
  listing): 44.1, 48, 88.2, 96, 176.4, 192, 352.8 and 384 kHz, from the
  product name.
- **Not modelled.** The HID interface, and a microphone: other CX31993
  dongles have one, and this listing's has none. The ids stay `FFFF:0207`.
  `--vid 06cb --pid 1595` gives the listing's.
- Linux's `sound/usb/quirks.c` lists two Conexant ids, `0572:1b08` and
  `0572:1b09`, with `QUIRK_FLAG_MIXER_PLAYBACK_MIN_MUTE`: the lowest
  playback volume step means mute (`usbaudio.h`). Whether either is a
  CX31993 is not stated there.

The simulator now answers a feature unit request only for a control its
`bmaControls` declares, read only (1) or read/write (3). Earlier it
answered mute and volume on every channel of every feature unit. The X4
capture's channel-mute requests now stall, as its descriptors say.

The driver's plan accepts every rate of this layout: for a synchronous
endpoint it adds no headroom, and stereo 16-bit needs 180 bytes per
microframe at 352.8 kHz and 192 at 384 kHz, within the listed 192. No
stream ran above 48 kHz here.

## Other findings

- **XP x64 binds Windows' `usbaudio.sys` to a UAC 2.0 device first.** The
  in-box `wdma_usb.inf` matches `USB\Class_01` and is signed, so on XP x64
  it outranks the unsigned `uac2wdm.inf` class match: "USB Audio Device",
  no wave device (`xp1`, `xp2`). Installing `uac2` over it with `MIDITEST
  install` hung 2 of 2: the setup call never returned, the device saw no
  further request, and shutdown hung. After a restart `uac2` was bound
  (`MatchingDeviceId` `usb\class_01&subclass_00&prot_20`) and played. Not
  read further. A user replacing `usbaudio` on XP x64 may need a restart
  after the update.
- **98 SE, after a replug:** with the device unplugged and plugged again
  in one boot, Media Player said "MMSYSTEM337 The specified MIDI device is
  already in use." This is the 98 SE limitation `usbmidi`'s record describes
  (any WDM MIDI open fails after a device removal until a restart). It
  applies to the SW synth too.
- **98 SE, `cx31993` first arrival:** the cold boot that installed the
  `cx31993` instance (`m2`, first boot) showed `waveOut` 0. Hot arrivals
  later in that boot showed `waveOut` 1, with the rates limited to 192 kHz
  and with the full list. A clean cold boot with the device present
  (`m2`, third boot) showed `waveOut` 1 and played. The first boot's
  failure did not recur with the full rate list; its cause remains
  unknown.
- The fixed INF still prompts for the KS files on 98 SE (its one
  `[SourceDisksNames]` disk is offered for them); unchanged here.
