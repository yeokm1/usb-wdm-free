# uac2 on 32-bit XP: the hang when the driver is changed to it, 2026-10-29

A user of xHCI98 3.2.0.0 (whose free download carried this repository's
v0.1.0) reported that the wizard stopped responding on 32-bit XP while it
installed `uac2` for a USB Audio 2.0 device, and that the device worked
after a restart. xHCI98's task 45.24 read it; its record is xHCI98's
`docs/contributing/runs/run-45.md`, "45.24", and its fix there is design
record 13 section 10.7.2. This is the part that concerns `uac2`.
Development legs in QEMU (q35, TCG), simulated device only, not "Tested".

## Rig

- XP SP3 x86 q35 guests, stock QEMU 11.1.0 with `usb-redir`.
- `uacemu.py` profile `hs24` (`FFFF:0201`) on `qemu-xhci` (xHCI98
  3.2.0.0 and 3.3.0.0) or on `ich9-usb-ehci1` (Windows' own `usbehci.sys`
  and `usbccgp.sys`, no xHCI98).
- `uac2` 0.1.0.0 (`uac2wdm.sys` `ec4fcce5...`) and 0.1.4.0 (`0aafc635...`),
  from `w2k-xp`, by Device Manager's Update Driver, Have Disk.

## Result

| What | Under xHCI98 | Under Windows' EHCI |
|---|---|---|
| Plug, `uac2wdm.inf` copied in before or not | "USB Audio Device", Windows' `usbaudio.sys`, silently | the same |
| Update Driver to `uac2` | waits at "uac2wdm.sys To C:\WINDOWS\system32\DRIVERS"; `usbaudio` RUNNING, `uac2wdm` never started | the same |
| Disable the device | waits | not run |
| Unplug, then shut down | "Windows is shutting down" waits; reset | the same |
| After the reset, plug | `uac2` binds and plays (`sndrec32 /play`) | not run |
| Unplug, restart, update the hidden devnode to `uac2`, plug | completes in about 3 minutes; `uac2` binds and plays | not run |

Signed `wdma_usb.inf` (`USB\CLASS_01`) outranks the unsigned
`uac2wdm.inf` on XP, so `usbaudio.sys` takes every new UAC 2.0 function
first, and nothing changes that devnode until a restart. `uac2` itself
never runs before that: no change in this repository fixes it. The
README's known issue now says so for XP as well as XP x64, with the way
round it read above. Under xHCI98 from 3.4.0.0 the bus no longer offers
the bare `USB\Class_01` for a UAC 2.0 function, so `usbaudio.sys` does not
take it there.

## Three experiments, 2026-10-30

A fresh XP SP3 x86 q35 guest, Windows' own EHCI (no xHCI98), `uac2`
0.1.4.0 (`0aafc635...`) in `C:\UAC2` and on `DevicePath`, no co-installer,
never-seen `hs24` devices (`FFFF:02A1` to `02A3`). The updates were made
by a test-only program (not tracked) that builds the driver list from
`uac2wdm.inf` alone and calls the install `DIF_` codes in the order the
default installer does.

- **(a) `[ControlFlags] InteractiveInstall`** for `uac2`'s two class ids,
  added to a copy of `uac2wdm.inf`: no change. The first plug installed
  `usbaudio` silently (`RUNNING`), no wizard, `uac2wdm` never installed.
  The flag governs `uac2`'s own lines only, and those lose the rank.
- **(b) the wait and Windows Audio.** Baseline (`AudioSrv` running, no
  audio program open): the update waits in `DIF_INSTALLDEVICE` (more than
  2.5 minutes; `DIF_INSTALLDEVICEFILES`, `DIF_REGISTER_COINSTALLERS` and
  `DIF_INSTALLINTERFACES` completed). `net stop audiosrv` during the wait:
  the service stopped, the wait went on. `AudioSrv` stopped and disabled
  before the plug, `usbaudio` then bound, the update: the same wait. So
  Windows Audio does not hold it. A stack of the waiting call was not
  taken (no kernel debugger on this rig).
- **(c) `DI_DONOTCALLCONFIGMG`.** The same install with that flag set
  (the running devnode left alone) completed: `DIF_INSTALLDEVICE` returned,
  the devnode's service became `uac2wdm`, `usbaudio` kept running, and no
  restart flag was set. A restart then waited at "Windows is shutting
  down" (more than 4.5 minutes, the device plugged in), as the baseline's
  shut down does; after a reset the device came up on `uac2` (`uac2wdm`
  `RUNNING`, `usbaudio` stopped) and played (Windows' start-up sound and
  `sndrec32 /play`, the signal read by the simulator).
