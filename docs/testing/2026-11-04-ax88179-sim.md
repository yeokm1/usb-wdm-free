# ax88179 with a simulated AX88179: 98 SE against the real adapter, then 2000, 2026-11-04

Owner, 2026-11-04: test `ax88179` on Windows 2000 and stage it there if
it passes. At v0.1.7 its 2000 INF was copy only, because it had no leg.
The owner's adapter is not on this host, so ax88179 now has a simulator,
`src/net/ax88179/axemu.py` (`46d1215`, then `65ee538`), modelled on
`rtlemu.py`. First it was checked on 98 SE against the owner's adapter's
recorded results ([ax88179-9x](2026-10-22-ax88179-9x.md),
[ax88179-fcs](2026-10-22-ax88179-fcs.md)), then the 2000 leg was run. All
of this is emulated: no physical device was used and none is claimed.

## The simulator

`axemu.py` models what the driver's chip core (`axchip.c`, `axframe.c`)
reads and writes, not the chip's firmware. Its docstring names the source
of each fact:

- **Descriptors.** At SuperSpeed the device and configuration descriptors
  are the physical capture in `testdata/ax179/`, byte for byte
  (`0B95:1790`, bcdDevice 0100). The High and Full Speed forms and the BOS
  are the model's own choice.
- **Vendor requests.** As `axchip.h` names them from Linux
  `ax88179_178a.c`: ACCESS_MAC (wValue the register, wIndex its width),
  ACCESS_PHY at PHY address 3, the EEPROM word 0x43, and the TX FIFO
  status (0x81, wValue 0x8c).
- **Chip state.** The MAC register file and PHY power. Link comes up after
  autonegotiation and is shown in PHYSR. The status report is 8 bytes, with
  the link in bit 16.
- **Framing.** The receive aggregate (2-byte pad, 8-byte records, one
  header dword per frame, the count/offset trailer; `--fcs` forwards an
  FCS) and the 8-byte transmit header with its padding flag.
- **The network behind it.** The simulated host 192.168.77.1 of
  `rtlemu.py`, answering ARP, ICMP and DHCP. It checks each request's
  IPv4 header, UDP length and checksums before answering, reassembles
  fragmented datagrams and fragments long answers, as a real host does.

`axsimtest.py` (15 tests) drives the driver's own `NetPackageChip` through
the model at the host. `axchip.c`, `axframe.c` and `netchip.c` go into an
x64 DLL built by `simhost.ps1`. The tests cover bring-up at Super, High
and Full Speed, the queue rows for 1000/100/10 Mb/s, link reports, ARP,
ICMP and DHCP through the driver's framing, aggregation with and without
an FCS, the receive filter, the padding flag, Stop, refused requests,
corrupted and fragmented datagrams, and the reassembly bounds. The model's
limits: a real chip's undocumented behaviour (timing, the first-session
FCS that the owner's adapter showed, what its PHY really reports) is not
exercised. The FCS case exists only as `--fcs`, and it was not run in a
guest.

  `qemu-xhci`.
- **98 SE** runs on the pc machine, as an overlay of the pristine 98 SE
  base `E:\xhci98-vm\p43-5\base\w98se-pristine.qcow2` (SHA-256
  `d5479ea5...ef09` before and after the legs). The q35 98 SE base does
  not boot on stock QEMU, which `usb-redir` needs, so the earlier `uac2`
  98 SE legs used this base too (the coordinator's choice). This base has

  - The 2000 guest was then stopped with a QMP quit (its Standard PC HAL
    did not act on a power-down request), and started cold.
- The released files, from `free/` at `2e40492`: `AX179F.SYS`

## 98 SE under xHCI98 3.4.0.0: the simulator against the real adapter

| Step | Real AX88179 (98 SE, xHCI98 3.1.0.0; ax88179-9x, ax88179-fcs) | Simulated AX88179 |
|---|---|---|
| Install | New Hardware Found took `AX179F98.INF` | New Hardware Found picked "ASIX AX88179 USB 3.0 Gigabit Ethernet (AX179F)" from the `DevicePath` folder by itself and asked for "AX179F installation disk" (`C:\AX98` typed). No restart prompt |
| Bring-up, DHCP | link, DHCP lease | link 1000 Mb/s full, DHCP DISCOVER/OFFER and REQUEST/ACK at once, lease 192.168.77.2 |
| Ping | 0 to 4000 bytes | 4/4 at 32 bytes, 8/8 at 1472, 4/4 at 4000 (three fragments each way). See the note below |
| Removal under traffic | survives | `ping -n 60` stopped at the unplug, 25 replies then "unreachable"; the guest kept running |
| `ping -t` across a replug | replies again within 15 s of the plug | "unreachable" while it was gone, then replies within 15 s of the plug (screens `ax98-pt-gone`, `ax98-pt-w15`, `ax98-pt-w30`) |

The first 4000-byte ping got no answer. The simulator's host refused each
fragment for its ICMP checksum, because it did not reassemble then. The
host was given IPv4 reassembly (`65ee538`, reviewed), and the second plug
answered 4/4. A running `ping -n` does not recover across a replug on 98
SE, with the simulator as with the real adapter: 98 SE answers
"unreachable" at once while the device is gone, so the count runs out
(ax88179-fcs). That is why the replug was read with `ping -t`.

**The simulator matches the real adapter in each step the real legs
recorded** for 98 SE under xHCI98.
