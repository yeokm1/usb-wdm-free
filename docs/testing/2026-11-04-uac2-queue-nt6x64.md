# uac2 0.1.8 on 64-bit Vista, 7, 8 and 8.1: update and the CPU-load comparison, 2026-11-04

This record covers the 64-bit NT6 systems and is a sibling of
`2026-11-04-uac2-queue.md` (the XP x64 comparison and the design reasons)
and `2026-11-04-uac2-queue-nt6x86.md`. The legs were run by worker
uwf-audio64. They are development legs in QEMU (TCG) with the simulator,
not "Tested": no real CX31993 and no game. Raw logs, screenshots and
scripts are in `E:\xhci98-vm\p46\uwf-audio64\` (`STATE.md` indexes them).

Only 7 x64 was run. The coordinator stopped the remaining build-24 legs
when v0.1.8 moved to build 26 (2026-11-05). Build 26 gets a short check
on Vista, 7, 8 and 8.1 x64 of its own.

## Rig

- **Guests:** q35 overlays of the shared `w7x64` base, 2 vCPUs and 2 GB
  each, on the usb4-emu QEMU fork build `cb36497` (isochronous real-time
  fix, `usb-redir`), with `-Tablet`. The clock is the base's pinned
  2026-09-20.
- **Golden disk** (`w7\`):
  - A throwaway certificate made in the guest (MakeCert, CertMgr Root
    and TrustedPublisher), plus xHCI98 3.4.0.0's own test certificate
    trusted. `bcdedit /set testsigning on`, restart.
  - xHCI98 3.4.0.0 as released, `nt-x64`, installed with
    `INSTALL.BAT /console /yes /nopause /usb`. It exited with code 3
    (xhci98 3.4.0.0 started), and the guest was cold-started.
  - The co-installer `UACCI.INF` (DefaultInstall).
  - `uac2` 0.1.6.0 as released (`free/audio/uac2/wv-8-x64`), re-signed
    with the throwaway certificate, added with `pnputil -a`. The prompt
    "Windows can't verify the publisher of this driver software" was
    answered "Install this driver software anyway". The INF was
    published as `oem4.inf`.
  - At the first plug of the device: DriverVersion 0.1.6.0, and a 5 s
    play PASS.
  - The golden disk was then made read-only.
- **Twins:** two overlays of the golden disk, one updated to the new
  build and one kept on 0.1.6.0. Each comparison ran both twins at the
  same time so that both saw the same host load. Other workers' guests
  used about 50-75 % of the host's 32 threads throughout.
- **Device and load:** the simulator `uacemu.py --profile cx31993` (High
  Speed, `bInterval` 1) through `usb-redir` on `qemu-xhci` port 1. One
  `cmd` busy loop per processor at normal priority. A play is
  `UACWAV play 2 16 48000 60`, five per set, with an `XHCITR64 /snapshot`
  before and after.
- **Builds:** the test kit's copy of each new build's INF carries
  DriverVer `0.1.8.<build>`. The driver store dedupes a byte-identical
  INF, so builds 20 to 24, which share one INF, would otherwise reuse the
  first staged copy. The source INF is unchanged. The files used:
  - build 22: `45f011a`, `uac2wdm.sys` `b650b9de...`
  - build 24: `899b9f4`, `688b158a...`
  - both signed in the guest with the throwaway certificate.

## The update from 0.1.6.0 (7 x64)

The steps:

1. `pnputil -a C:\B24\uac2wdm.inf`. The publisher prompt was answered
   Install anyway, and the INF was published as `oem5.inf`.
2. Device Manager > the device > Properties > Driver > Update Driver >
   Browse my computer > `C:\B24` > Next. Windows answered **"The best
   driver software for your device is already installed"**, and the
   device stayed on 0.1.6.0. This is the 7 x86 answer of the sibling
   record.
3. Update Driver > Browse > "Let me pick from a list of device drivers on
   my computer" listed 0.1.6.0 [31/10/2026] and 0.1.8.24 [4/11/2026].
   Picking 0.1.8.24 > Next gave "Windows has successfully updated your
   driver software", with no prompt and no restart.

After the update:

- DriverVersion 0.1.8.24 (`oem5.inf`).
- `Uac2QueueMs` 0x20 and `Uac2Realtime` 1, both written by the INF.
- `Uac2UsbStats`, 65 words: QueueMs 32, DataTransfers 8, TransferUs
  4000, RealtimeRead 1, Realtime 1, WorkerPriority 16,
  WorkerThrottles 0.
- A 5 s play PASS.

Build 22's update on an earlier twin went the same way: refused by
Browse, then Let me pick worked, giving 0.1.8.22 with the same stats
(WorkerPriority 16, WorkerThrottles 0).

## CPU-load comparison (7 x64)

Pair `7a1`, both twins at the same time, CPU load, 5 x 60 s plays each:

| uac2 | plays incomplete (> 70 s) | Ring Underrun | Missed Service | OUT packets/s, host time | gaps >= 10 / 20 / 50 ms | stats after |
|---|---|---|---|---|---|---|
| 0.1.6.0 | 5 of 5 | +13960 | 0 | 3083 | 13905 / 3213 / 130 | 57 words (no queue fields) |
| build 24 | 0 | +72 | 0 | 6462 | 37 / 5 / 0 | WorkerPriority 16, WorkerThrottles 0 |

- Under this load the build-24 guest's clock ran slow. Its plays measured
  42-43 s by the guest's clock, so packets per second are given over the
  set's host-time window.
- Run `7p1h` (build 22 alone, CPU load): Ring Underrun +31081, 6057
  packets/s by host time, WorkerPriority 16, WorkerThrottles 0. Its
  0.1.6.0 twin `7p1o` is not a result: its play line was lost under load
  and nothing played. The harness now types each batch line again, up to
  three times, when its start marker does not appear.
