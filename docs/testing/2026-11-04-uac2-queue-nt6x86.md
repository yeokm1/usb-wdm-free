# uac2 0.1.8.0 on Vista, 7, 8 and 8.1 x86: update, regression and the CPU-load comparison, 2026-11-04

The sibling of `2026-11-04-uac2-queue.md` (the XP x64 comparison and the
design reasons) for the 32-bit NT6 systems: worker uwf-audio6. These are
development legs in QEMU (TCG) with the simulator, not "Tested": there
was no real device and no game. Raw logs, screenshots and scripts are in
`E:\xhci98-vm\p46\uwf-audio6\` (`STATE.md` indexes them).

## Rig

- Guests: q35 overlays of the shared clean bases (`w7x86`, `w81x86`,
  `vx86`), 2 vCPUs and 2 GB each, at most two guests at once. Each guest
  ran on the usb4-emu QEMU fork build `cb36497` (the isochronous real-time
  fix and `usb-redir`, as in the XP x64 legs), with `-Tablet`. 7 and Vista
  keep the bases' pinned clock (2026-09-20); 8.1 runs on local time.
- xHCI98 3.4.0.0 as released, `nt-x86`, unsigned, installed with
  `INSTALL.BAT /console /yes /nopause /usb` from an elevated prompt. Each
  "Windows can't verify the publisher" prompt was answered "Install this
  driver software anyway". It exited with code 3 each time, and the guest
  was then shut down and cold-started. On Vista the first run exited with
  code 4 ("Nothing was changed") because Found New Hardware windows were
  open for devices with no driver. Those were answered "Ask me again
  later", and the second run exited with code 3.
- The device was the simulator `uacemu.py --profile cx31993` (High Speed,
  one synchronous playback endpoint, `bInterval` 1) through `usb-redir`
  on `qemu-xhci` port 1. `hs24` was used for recording.
- Drivers:
  - 0.1.6.0 as released (`free/audio/uac2/wv-8-x86`, `uac2wdm.sys`
    `dd5e14f5...`). On Vista and 7 the co-installer `UACCI.INF` was
    installed first (DefaultInstall). 8.1 needs no co-installer and was
    given none.
  - HEAD x86 of `1976c9e` (`uac2wdm.sys` `df1f7078...`, the same file as
    `out\` before build 20; its INF is `299010ca...`, DriverVer 11/04/2026
    0.1.8.0).
  - Build 20 (`2249164`, `1de6931b...`) on 7 where named; build 21
    did not reach the device (see the update section).
- Load: one `cmd` busy loop per processor, at normal priority. A play is
  `UACWAV play 2 16 48000 60` (WinMM, eight 7.5 s buffers; the play gives
  up after 70 s). Each set is five plays. Counted for each set:
  - xHCI98's completion codes from `XHCITR /snapshot` before and after.
  - The plays' time by the guest's clock.
  - The simulator's OUT packets: per second of play by the guest's clock
    (the XP x64 record's measure), and per host second over the set's
    window.
  - The simulator's gaps between successive OUT packets.
- Only one measured set ran at a time (a lock across the two guests).
  Other workers' VMs ran on the same host throughout, at about half of
  its 32 threads. The 7 HEAD set overlapped Vista's xHCI98 install in the
  other guest.

The 7 x86 Browse refusal, and what was checked about it:

- It is not the pinned clock. With the guest's date set to 5/11/2026 the
  Browse route gave the same answer. The date was set back afterwards.
- It is not the ranking. A new device instance (the CX31993 on another
  port) got 0.1.8.0 at its first plug, with both packages in the driver
  store.
- It is not the co-installer. `src/audio/uac2/uacco.c` touches no uac2
  driver node: `MarkNodes` (lines 193-232) sets `DNF_BAD_DRIVER` only on
  the nodes of `wdma_usb.inf` that install `usbaudio`, and
  `CheckSelected` (lines 235-250) refuses only a selected `usbaudio`
  node. `UACCI.LOG` read "usbaudio nodes marked=0" for every pass.
- The two INFs differ only in `DriverVer` and the `Uac2QueueMs` AddReg.
- `pnputil -i -a` updates the device. With that new instance moved back
  to 0.1.6.0 (Let me pick) and the first device unplugged,
  `pnputil -i -a C:\NEW\uac2wdm.inf` moved it to 0.1.8.0 with no prompt.
  It nevertheless printed "Failed to install the driver on any of the
  devices on the system : No more data is available". The unplugged
  instance is the likely source of that message, but this was not
  confirmed.

For the release notes, the route that works on 7 x86 is Device Manager >
Update Driver > Browse my computer > "Let me pick from a list of device
drivers on my computer" > the 0.1.8.0 entry > Next. `pnputil -i -a` with
0.1.8.0's INF also works.

The Browse refusal is unexplained, and it was seen on 7 x86 only. On 8.1
the same Browse route updated the device.

Build 20 (`2249164`, the stream worker at `LOW_REALTIME_PRIORITY`,
`uac2wdm.sys` `1de6931b...`; INF `ab1c0647...`, the same DriverVer as
HEAD) went on 7 through `pnputil -a` (`oem6.inf`, publisher prompt) and
Update Driver > Browse > Let me pick > Have Disk > `C:\B20` > Next:
"successfully updated", no restart. A 5 s play passed; the stats read
`Realtime` 1 and `WorkerPriority` 16 (64 words).

Build 21 (`7430bf2`) did not reach the device. Its INF is byte-identical
to build 20's, and neither has a catalog. `pnputil -a` of build 21's INF
said "added" but named build 20's existing `oem6.inf`, and the store kept
build 20's `uac2wdm.sys`. Have Disk then reported "successfully updated"
while the device kept running build 20 (64 stats words, no
`WorkerThrottles`). So the 7 set below headed "build 20" ran build 20.

The driver store treats a rebuilt driver with an unchanged INF and no
catalog as the package it already has. A test build therefore needs its
own DriverVer, which goes only in the test kit's copy of the INF. A user
who reinstalls a rebuild over an equal DriverVer keeps the old file.

## The CPU-load comparison (step 4)

"Incomplete": the play's eight buffers were not all played back by its
70 s give-up.

| system | uac2 | plays | incomplete | Ring Underrun | packets/s of play (guest clock) | packets/s (host, set window) | gaps >= 10 / 20 / 50 ms |
|---|---|---|---|---|---|---|---|
| 8.1 x86 | 0.1.6.0 | 5 | 5 | 11014 | 4413 | 3617 | 8242 / 3073 / 0 |
| 8.1 x86 | HEAD | 5 | 1 | 3121 | 7735 | 6208 | 3058 / 3 / 0 |
| 7 x86 | 0.1.6.0 | 5 | 5 | 14370 | 4909 | 2765 | 14596 / 9651 / 274 |
| 7 x86 | HEAD | 5 | 0 | 14458 | (18977; guest clock slow) | 6248 | 14245 / 10 / 0 |
| 7 x86 | build 20 (see below) | 5 | 0 | 24 | (12232; guest clock slow) | 6525 | 7 / 1 / 0 |
| Vista x86 | 0.1.6.0 | 5 | 5 | 12189 | 4423 | 2683 | 12100 / 9235 / 187 |

- 8.1: HEAD cut Ring Underrun to about a quarter, brought the packet rate
  near real time, and left one play of five incomplete. This is much
  better than 0.1.6.0, but far above XP x64's 34-62 Ring Underrun for
  the same build. The rigs differ (8.1's audio engine sits between WinMM
  and uac2; the host was shared with other workers' guests), so this
  table does not say how much of the gap is the system and how much the
  rig.
- 7: the guest's clock runs slow while audio plays under CPU load (TCG).
  The guest timed HEAD's 60 s plays at 24-41 s while the host took far
  longer, and an idle guest kept time (1.002 against the host). The
  guest-clock columns for 7 are therefore not comparable. By the host's
  clock, HEAD delivered 2.3 times 0.1.6.0's packets per second and
  completed every play, but its Ring Underrun count did not fall.
- A first 7 set on 0.1.6.0 (`s7-o-cpu`) had no snapshot, because XHCITR
  3.4.0.0 refuses a `/snapshot` name longer than 8 characters: 5/5
  incomplete, 4984 packets/s of play. A second set (`7oc`) ran with the
  guest clock already slowed and timed out after three plays; both are
  left out of the table.
- 7, build 20 (the real-time worker): Ring Underrun fell from about
  14400 (0.1.6.0 and HEAD) to 24. Gaps of 10 ms or more fell from about
  14000 to 7. Every play completed, at 6525 packets per host second. The
  guest's clock still ran slow during the plays (about 41 s each).
- 0.1.6.0 under CPU load reproduces the user's failure on all three
  systems (every play incomplete, thousands of Ring Underrun).

## Regression with HEAD (steps 2 and 3)

| system | play, WinMM client 16/48 and 24/96 (the device ran 16/44.1) | ramp | seek (`UACSEEK wo s16 48000 3 2000 p`) | `Uac2QueueMs` default / 128 / 16 (DataTransfers) | `hs24` play, record, ramp |
|---|---|---|---|---|---|
| 8.1 x86 | PASS, PASS | PASS | PASS, 0 stale blocks in the part read (`--coarse` at 44.1 kHz; the capture starts late, the first 64 ms not covered) | 32 (8) / 128 (32) / 16 (4) | PASS, PASS (signal present), PASS |
| 7 x86 | PASS, PASS | PASS | PASS, 0 stale blocks in the part read (`--coarse` at 44.1 kHz; the capture starts late, the first 75 ms not covered) | 32 (8) / 128 (32) / 16 (4) | PASS, PASS (signal present), PASS |

- The audio engine opened the simulator at 16-bit 44.1 kHz on both
  systems (the device's first format) and resampled the 48 kHz seek
  signal. The seek runs were therefore read with `uacseek.py --coarse`,
  each from its own capture that held only the seek. The first try on
  each system shared one capture with the earlier plays and could not be
  read.
- Every stream in these regression legs ran at 16-bit 44.1 kHz on the
  USB side: the engine converted the WinMM clients' 48 kHz and 24-bit
  96 kHz. These legs therefore show that the clients' requests completed
  through the engine. They do not cover uac2 itself running at 48 kHz or
  at 24 bits on NT6; that coverage is outstanding. The CPU-load sets ran
  at 44.1 kHz too.
- The seek analysis covers the capture after its first 64 ms (8.1) or
  75 ms (7). A stale block at the very start of a stream is not ruled
  out.
- A new device instance installed from the driver store took 0.1.8.0
  with `Uac2QueueMs` 0x20 (8.1: the `hs24` device; 7: the CX31993 on
  another port).
