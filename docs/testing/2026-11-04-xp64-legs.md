# uac2, cdcnet and usbflop on XP x64: the staging legs, 2026-11-04

Owner, 2026-11-04: XP x64's staged set should match XP x86's. At v0.1.7
three XP x64 INFs differed: `uac2`'s `wxp-x64/uac2wdm.inf` and `cdcnet`'s
`wxp-x64/CDCNET.INF` were copy only, and `usbflop`'s
`w2k-8/USBFLOP.INF` had no XP x64 token. This record holds the XP x64 legs
that the XP x86 lines rest on, each run on the released v0.1.7 files.
`STAGE.TXT` now stages all three on XP x64. All legs ran in QEMU (TCG)
with simulated or emulated devices; no real device was used and none is
claimed.

## Rig

- Guest: XP Professional x64 SP2 on q35, fresh overlays of the shared clean
  base (`g2`, then `g3`), 2 vCPUs. Stock QEMU 11.1.0, `usb-redir` to the
  simulators. Every overlay had the same three controllers: `qemu-xhci`
  under xHCI98, `ich9-usb-ehci1` under Windows' `usbehci`, and its
  `ich9-usb-uhci1` companion (ports 1 and 2) under Windows' `usbuhci`.
- xHCI98 3.4.0.0 as released (`xhci98.sys` x64 `919aa64a...`), installed
  by its `INSTALL.BAT /console /yes`: exit 3, "xhci98 3.4.0.0, started",
  then a cold start. Its catalogs are signed with the xHCI98 test
  certificate. XP x64 has no `certutil`, so that certificate went into the
  machine Root and TrustedPublisher stores with the WDK's `CertMgr`. A
  first overlay without that step failed the controller install with
  0x800B0109 and was dropped.
- Staging as `STAGE.TXT` does it on 2000 and later: each INF was passed to
  `SetupCopyOEMInfA(path, media, SPOST_PATH, 0)` by a small test program.
  The INF landed in `%windir%\inf` (`oem3.inf` for `uac2wdm.inf`,
  `oem4.inf` for `CDCNET.INF`, `oem5.inf` for `USBFLOP.INF`). Windows
  showed "has not passed Windows Logo testing" once for each, and Continue
  Anyway was chosen.
- Driver signing policy: the base's default (Warn). Each unsigned INF gave
  one Logo prompt at the first plug, and Continue Anyway was chosen. XP
  x64 needs no test signing: the released x64 images load as they are.
- Files, from `free/` at `2e40492` (v0.1.7 + 3; no file under `free/`
  changed since v0.1.7): `uac2wdm.sys` `c21c9425...`, `uac2wdm.inf`
  `65c9a4d7...`, `UACCI1.DLL` `857e11a0...`, `UACCI.INF` `17a3aec7...`;
  `CDCNET.SYS` `bd431e0a...`, `CDCNET.INF` `77277329...`; `USBFLOP.INF`
  `4cb558a2...`.
- Test programs, built in this tree: `UACWAV.EXE` (`wav.cmd`,
  `2fac61f6...`), `UACSEEK.EXE` (`seek.cmd`, `ae7a52f9...`),
  `NETTEST.EXE` (`nettest.cmd`, `54c6b66a...`). The floppy reads used a
  scratch copy of `fread.c`, `FREADC.EXE` (`8815481b...`). It differs only

## `uac2`

`UACCI.INF` was installed by `InstallHinfSection DefaultInstall`, which
registered `UACCI1.DLL,UacCoInstaller` as the only MEDIA class entry. Then
`uac2wdm.inf` was staged by `SetupCopyOEMInf`.

| Leg | xHCI98 3.4.0.0 | Windows' EHCI |
|---|---|---|
| First plug, never-seen `hs24` (`FFFF:02C1` on xHCI98, `FFFF:02C3` on EHCI) | Found New Hardware ran twice, first for "xHCI98 USB Composite Device" and then for the function. The function's wizard offered "UAC2 USB audio (experiment)" by itself. `setupapi.log`: `USB\Class_01&SubClass_00&Prot_20` found in `oem3.inf`, `[UAC2.NTAMD64]`, version 0.1.6.0. The file was copied from the staged folder, and no restart prompt or "required reboot" line followed. `UACCI.LOG`: `marked=0` | the same wizard and the same choice; `UACCI.LOG`: `marked=1` |
| `UACWAV list` | one input and one output, "UAC2 USB audio (experiment)" | the same |
| `play 2 16 48000 2` | 8/8, PASS | 8/8, PASS |
| `rec 2 16 48000 2` | 8/8, 1001 Hz tone, PASS | 8/8, tone, PASS |
| `ramp 2` (volume and mute) | PASS, 0 failed operations | PASS |
| Seek legs, `cx31993` (`FFFF:02C2`), 0.1.6.0: `wo s16 48000 p`, `ds s16 48000`, `ds f32 44100` and `wo s16 44100 p` (simulator at 44.1 kHz only), `ds s16 48000 h` | 5 of 5 PASS, **0 stale blocks** in each; 1.7 s captured per leg (the isochronous stream runs slower than real time under TCG, as in the XP x86 seek legs) | 5 of 5 PASS, **0 stale blocks** in each; 8.3 s captured per leg |

The seek legs are those of the seek record
([uac2-seek](2026-10-31-uac2-seek.md)), and `uacseek.py` applied the same
stale-block rule. Each leg had its own simulator, its own capture and its
own plug.

**Replugs on the first overlay (`g2`), not repeated on `g3`.** On `g2`
the seek legs replugged the simulator 4 s after the unplug, on whatever
port QEMU chose, and nobody answered any wizard. After the first played
session every later plug found no device to play on. Under xHCI98 no
composite devnode appeared at all (`wmic`), although the device was
configured on the bus. Under EHCI each plug came up as a new function
instance (new `UACCI.LOG` lines), and no wave device appeared. On `g3`
the plugs went to a fixed QEMU port, with the wizard answered on every
plug and a 30 s gap before any second plug. There every replug after
playback worked, on both controllers. The one `g3` plug that found no
device was the very first one, which was still in Found New Hardware when
UACSEEK started. What on `g2` kept the devices from appearing was not
investigated further.

## `cdcnet`

`CDCNET.INF` (`wxp-x64`) was staged by `SetupCopyOEMInf` (`oem4.inf`).
`CDCRNDIS.INF` was not staged: it stays copy only, as on XP x86.

| Leg | Result |
|---|---|
| QEMU `usb-net` (`0525:A4A2`, Full Speed) on Windows' UHCI, first plug | Found New Hardware took the staged INF ("USB Ethernet (Linux USB gadget)"), with one Logo prompt. DHCP gave 10.0.2.15. `NETTEST`: ICMP 21/21 replies verified, TFTP 2 x 1 MiB verified with 0 retransmits. **PASS** |
| The same device on xHCI98 3.4.0.0 (another port, so a new instance) | installed in the same way ("... #2"), DHCP 10.0.2.15, `NETTEST` 21/21 and 2 x 1 MiB. **PASS** |
| `ncmemu.py` with an unlisted id (`FFFF:0303`, CDC NCM by class, High Speed) on Windows' EHCI | the class line matched ("USB Ethernet (CDC-NCM)"), DHCP gave 192.168.77.2, and `ping -l 1400 192.168.77.1` got 8/8. **PASS** |

RNDIS: the XP x64 models of `CDCNET.INF` (`[Models.NTamd64]`) list ECM,
NCM and the gadget id only, the same lines as `[Models.NTx86.5.1]`, so a
staged `CDCNET.INF` takes no RNDIS device by its class. XP x64's own
`netrndis.inf` has no USB id of its own (its `[Msft.NTamd64]` model is
`ms_rndisusb`, a template for vendor INFs). So staging takes nothing away
from Windows' driver that it would otherwise get. QEMU's `usb-net` is one
whole device with an RNDIS and an ECM configuration. The gadget line binds
it whole and `cdcnet` uses ECM, as on XP x86.

## `usbflop`

`USBFLOP.INF` (`w2k-8`) already has `[Models.NTamd64]`, and it was used
unchanged. It was staged by `SetupCopyOEMInf` (`oem5.inf`). The drive was
`ufiemu.py` (unlisted, FAT12 medium), as in the
[usbflop-nt-xpad-x64](2026-10-24-usbflop-nt-xpad-x64.md) legs.

| Leg | Result |
|---|---|
| CBI (`FFFF:0020`, later `FFFF:0025`) on Windows' UHCI | Found New Hardware took the staged INF ("USB UFI floppy (CBI, usb-wdm-free)") with one Logo prompt. The `USBSTOR\SFLOPPY` child had code 0. `FREADC`: `README.TXT` A4C945E0, `PATTERN.BIN` 9512AC89, `CRC.TXT` 02BD3B5B, the expected CRC-32s, 0 failures. **READ PASS** |
| CB (`FFFF:0021`, later `FFFF:0026`) on Windows' UHCI | "USB UFI floppy (CB, usb-wdm-free)"; **READ PASS**, the same CRC-32s |
| CBI (`FFFF:0022`, later `FFFF:0027`) on xHCI98 3.4.0.0 | **READ PASS**, the same CRC-32s |

**Drive letter.** The first plugs got a volume but no drive letter
(`mountvol`: "NO MOUNT POINTS"). The rig had caused this: an earlier step
in the same session had run `subst A:` for `NETTEST`'s report. After a
`mountvol` assignment the reads above passed. Afterwards the floppy's
letter was removed, the drive unplugged, the mount manager's entries for
it cleared (`mountvol /R`), and the drive plugged again. This time XP x64
gave it A: by itself.

## `ax88179` on 2000: not run

The owner asked for `ax88179`'s 2000 INF (copy only at v0.1.7) to be
tried as well. This repository has no AX88179 simulator: no `usb-redir`
model, and `axnet.py` is a host test that needs a real adapter. Its 98 SE
and ME legs used the real adapter passed to the VM. The line stays copy
only, and the owner's real-adapter leg on 2000 is owed. The non-free set
stages no `ethernet/ax88179` INF on 2000, so a later `STAGE | W2K` line
would not stage any id twice. Its `EXCLUDES` relation stays.

## The `STAGE.TXT` change

Three lines change, and nothing under `free/` does:
`free/audio/uac2/wxp-x64/uac2wdm.inf` and
`free/net/cdcnet/wxp-x64/CDCNET.INF` become `STAGE | WXP64`, and
`free/storage/usbflop/w2k-8/USBFLOP.INF` becomes
`STAGE | W2K WXP WXP64 W7X64`. The `UACCI.INF` lines stay `COPY`, because
the co-installer is set up by hand (`DefaultInstall`). The file was
written by `release\release.ps1 -Check`, with `-NonFree` set to the
non-free checkout, from a scratch copy of the 0.1.7 definition with these
three lines changed. The output was "release: checks PASS", with no
hardware id staged twice over both sets. Its `SHA256.TXT` matched the
tree's byte for byte. The release definition that carries these lines is
the next release's.
