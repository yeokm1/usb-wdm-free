# uac2 build 25: no gain above 0 dB, 2026-11-05

A user report (Windows XP x64 SP2, xHCI98 3.4.0.0 on a Fresco FL1100,
`uac2` build 24): a CX31993 + MAX97220 headphone dongle (`3302:12C3`)
sounds distorted, even at a low volume, and badly at the maximum. A plain
CX31993 dongle on the same system is fine. The change is design record
section 20 (`docs/design/uac2.md`). These are development legs in QEMU
(TCG) with the simulator, not "Tested": there is no real dongle, and
the device's real volume RANGE is not known (20.5 says how the next
report will carry it).

## Rig

- Guest: XP x64 SP2, a q35 overlay of an XP x64 disk that already had
  xHCI98 (the 3.4.1.0 tree's amd64 release build `8b962d4e`) and `uac2`
  installed (2 vCPUs, 2 GB), on the usb4-emu QEMU fork `cb36497` (its
  isochronous real-time fix and `usb-redir`). Windows' EHCI was present
  and unused.
- Device: `uacemu.py` through `usb-redir` on `qemu-xhci` port 1.
  `--profile cx31993m` replays the user's descriptors
  (`src/audio/uac2/testdata/cx31993m`); `--vol-range` sets the Feature
  Unit's RANGE, which the report does not hold, and `--vol-cur` sets
  its CUR at plug-in.
- Drivers: build 24 (`282ff63`; `uac2wdm.sys` x64 `355538fa...`) and
  build 25 (`746b809`; x64 `d5bb67d3...`, x86 `95c79113...`), each
  copied over the installed `uac2wdm.sys` with the device unplugged and
  compared by `fc`.
- Signal: `UACWAV play 2 16 48000 4`, a 440 Hz sine at -1 dBFS
  (`UACWAV_DBFS=-1`). The volume was set through the mixer API as the
  Volume Control sets it (`UACWAV vol`), to 65535, 32768 and 6554 (100,
  50 and 10 %). The simulator recorded the PCM it received (`--pcm`)
  and every Feature Unit request. On the host, each play's PCM was
  analysed (a least-squares 440 Hz fit, THD+N the residual's power
  over the fit's), then the same PCM after the hardware gain in force,
  clipped at full scale. That models a DAC that clips digitally.

## What uac2 sends (both builds)

Every play below was alternate 1 (16-bit stereo), 48 kHz, 24 bytes in
every microframe (6 frames, `bInterval` 1, adaptive). The received tone
measured -1.00 dBFS peak with THD+N -90.5 dB on every play of every
leg, on both builds, at every slider position. The payload the driver
builds (sample values, 16-bit packing, frames a packet) is clean.

What this cannot show is packet timing on the user's FL1100. The
simulator checks framing and records payloads; it does not consume them
against a DAC clock, and `qemu-xhci` under TCG is not that controller.
It also counted gaps of 2 ms or more between OUT packets: 115 and 225
in two cx31993m legs, 182 on the plain cx31993, on both builds. Where
they come from is not established. Adaptive timing on the real
controller remains a separate, unresolved candidate. The device's RANGE
answer (design 20.5) tests the gain explanation: a top above 0 dB
supports it, and a top at or below 0 dB rules it out. Either way the
RANGE says nothing about timing.

## The slider and the device's gain

XP's mixer maps its slider (0-65535) from the top of the KS range (design
20.2). Volume SET values the simulator received, and the tone after
that gain:

| Range (simulated) | Build | 100 % | 50 % | 10 % | Tone samples past full scale, 100 / 50 / 10 % | THD+N after the gain, 100 / 50 % |
|---|---|---|---|---|---|---|
| -127..+12 dB, 1 dB | 24 | +12 dB | +3 dB | -17 dB | 81.8 % / 41.5 % / 0 | -9.4 / -20.7 dB |
| -60..+6 dB, 0.5 dB | 24 | +6 dB | 0 dB | -14 dB | 61.8 % / 0 / 0 | -13.8 dB / clean |
| -127..0 dB, 1 dB | 24 | 0 dB | -8 dB | -26 dB | 0 / 0 / 0 | clean |
| -127..+12 dB | 25 | 0 dB | -8 dB | -26 dB | 0 / 0 / 0 | clean |
| -60..+6 dB | 25 | 0 dB | -6 dB | -20 dB | 0 / 0 / 0 | clean |
| -127..0 dB | 25 | 0 dB | -8 dB | -26 dB | 0 / 0 / 0 | clean |
| -127..+12 dB, `Uac2VolAboveZero` = 1 | 25 | +12 dB | +3 dB | -17 dB | 81.8 % / 41.5 % / 0 | -9.4 / -20.7 dB |

With build 24 and the -127..+12 dB range, the device's own 0 dB read
back on the slider as 25240 of 65535 (38 %). The top 62 % of the
slider was gain. The build 25 rows match the -127..0 dB row of build
24: the device behaves as one whose range tops out at 0 dB. With
`Uac2VolAboveZero` = 1 (`REG_DWORD` in the device's driver key, read at
start), build 25 reproduces build 24's row exactly.

## The start

- **CUR above the top** (`--vol-cur=3072`, +12 dB at plug-in, the volume
  never set on that instance): build 25 read CUR +12 dB on both
  channels and wrote 0 dB to each before the first play. `Uac2UsbStats`
  after the play: `VolLayout` 25, `VolMode` 2 (per channel),
  `VolLowered` 1, slots 1 and 2 `[count 1, MIN -32512, MAX 3072, RES
  256, top 3072, offered 0, CUR at start 3072]`. Then a SET came
  through KS (-11 dB, the same value at each start of that instance;
  XP's mixer restoring its own setting). The tone played at -12 dBFS,
  with nothing past full scale.
- **Master and channels** (`hs24` profile, a master with read/write
  volume and read/write channel volumes, range -60..+12 dB; master
  +6 dB, channels -40 dB at plug-in, so -34 dB in all): build 25 wrote
  the master to 0 dB and left the channels at -40 dB, -40 dB in all,
  which is quieter than before. Stats: `VolMode` 1, `VolLowered` 1, CUR
  at start 1536 / -10240 / -10240. Build 24 on the same instance
  received XP's mixer setting at start as a SET: master +12 dB (the
  slider's top), channels normalized to 0 dB, +12 dB in all. The -1
  dBFS tone then rendered at +11 dBFS, with 148036 of about 187000
  samples a channel past full scale.
- **CUR not read** (`--vol-cur=-15360 --vol-cur-stall=2`: the first two
  volume GET CURs stall): build 25 wrote nothing at start. Its next
  read found -60 dB. The only SET was the system's -11 dB, as above.

## Devices whose range tops at 0 dB

The `cx31993` profile (master mute, volume per channel, -96..0 dB) and
`x4full` (master volume) were played on both builds. Each build wrote
the same values at the same slider positions: 0, -6 and -20 dB at 100,
50 and 10 %. Each made the same RANGE and CUR requests. The tone had
the same level and THD+N (-90.5 dB). The PCM files differ only in how
long each play's stream ran, so they are not byte-identical. Build
24's first value on each instance was the level saved by an earlier
leg, which was set at start. For a range whose top is at or below 0 dB,
`KsMax` equals `KsTop`, as build 24's top (the `voltest` vectors), and
no CUR can be above it. So the KS range, the writes and the software
gain are build 24's.

## Not covered

- The 24 and 32-bit alternates (XP's KMixer opened 16-bit, the first
  listed), rates other than 48 kHz, and the other systems. The change
  is in the level code, the same on every system, and the x86 build
  compiled and passed its gates, but no other system was run.

  New Connection Wizard and stopped the sequence. The X1 profile went
  through the host parser test only.
