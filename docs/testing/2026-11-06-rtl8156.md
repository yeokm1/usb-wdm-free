# rtl815x with the RTL8156 and RTL8156B on 98 SE to XP x64, 2026-11-06

xHCI98 task 47.25 (owner, 2026-11-06): the Realtek RTL8156 and RTL8156B
in `rtl815x` on 98 SE, ME, 2000, XP and XP x64, the makers' drivers
first. The owner has none of these adapters, so every leg ran against
the SIMULATED chip of `rtlemu.py`. No physical device was used and none
is claimed. Nothing here is "Tested".

## What was already there

The chip core has served these chips since task 44.70 (2026-10-27; see
`ethernet.md` sections 6.4.0 and 7.6). That covers the chip ids `7020`,
`7030`, `7400` and `7410`, Linux's `RTL_VER_10` to `13`. The INFs list
them as follows:

- `RTL81598.INF` (98 SE, ME) and `RTL815X.INF` (2000) list `0BDA:8156`
  and `0BDA:8155`.
- `RTLXP7.INF` lists `0BDA:8156` for XP, XP x64 and Vista only.

`rtlemu.py` has modelled the four ids since 2026-10-27
([rtl815x-sim-newchips](2026-10-27-rtl815x-sim-newchips.md)).

The legs then ran as follows:

- 98 SE, ME and 2000 under xHCI98 3.1.0.0
  ([rtl815x-newchips](2026-10-27-rtl815x-newchips.md)).
- XP to 7 under Windows' own EHCI, at High Speed only
  ([rtl815x-xp7](2026-10-27-rtl815x-xp7.md)).

This record adds the legs that were missing:

- the released xHCI98 3.4.1.0 on every target;
- 98 SE under NUSB's EHCI;
- 2.5 Gb/s links on XP and XP x64;
- the RTL8156B on XP x64.

No code changed.

The coverage table (`ethernet-coverage.md`, 2026-10-27) still marked the
two chips a gap from 98 SE to Vista. It was written before the chip
core arrived. It now names `rtl815x`.

## The makers' drivers, system by system

Realtek's live download list for its USB Ethernet chips was read on
2026-11-06. The URL is <https://www.realtek.com/Download/List?cate_id=585>.
The page as fetched was 103,733 bytes, SHA-256
`9a009dacb52bb42267161061b9bbbb847cfedba9b3cfc0931a710f44b549b63b`. It
offers:

- "WinXP Auto Installation Program for FE/GBE" 5.23 (2021/07/27);
- Vista 6.27 (2018/08/02);
- 7 7.61.20 (2021/12/28);
- 8/8.1 8.68.20 (2021/12/28);
- Win10 10.68.20 (2026/08/31);
- Win11 (NetAdapterCx).

It offers nothing for 98 SE, ME or 2000. Realtek's INFs in
`usb-wdm-nonfree` (its XP 5.23, Vista 6.27 and 7 7.61.20 packages, read
2026-11-06) list these ids:

| Package | Realtek ids (`0BDA:`) on active lines | On commented-out lines only |
|---|---|---|
| XP 5.23 (x86, x64) | `8050`, `8152`, `8153` | - |
| Vista 6.27 (x86, x64) | `8050`, `8152`, `8153` | - |
| 7 7.61.20 (x86, x64) | `8050`, `8053`, `8056`, `8152`, `8153`, `8155`, `8156` | `8057`, `805A`, `8157`, `815A`, `A157`, `A15A` (no binding) |

So Realtek's drivers cover the RTL8156 and RTL8156B on 7 only, which
the pack already carries. 98 SE, ME, 2000, XP, XP x64 and Vista have
no maker's driver. Nothing new goes to `usb-wdm-nonfree`.

`0BDA:8056` is in Realtek's 7 INF (in its RTL8156B sections) and not in
Linux's table (`r8152.c` v7.3, `rtl8152_table`). It was not listed by
`rtl815x` at first; the owner added it the same day (below).

## Rig

- Emulator: a copy of the usb4-emu fork build `cb36497`, which has
  `usb-redir` (`qemu-system-x86_64.exe` SHA-256 `3e7f6bf5...`). TCG, one
  vCPU per guest, at most two guests at once, headless.
- Guests:
  - 98 SE, ME, 2000, XP and XP x64 each on a fresh overlay of its q35
    base in `E:\xhci98-vm\q35-bases\`.
  - 98 SE under NUSB on QEMU's pc machine, an overlay of the 98 SE +
    NUSB 3.3 EHCI base (the w98-nusb-hub chain the earlier 98 SE legs
    used, with `usb-ehci`).
- xHCI98 3.4.1.0 as released (`releases/3.4.1.0`), by
  `INSTALL.BAT /console /yes /nopause`:
  - 98 SE and ME: exit 3, then a cold start.
  - 2000: started at once.
  - XP: exit 3. The root hub's Found New Hardware wizard was finished by
    hand, then Windows was restarted.
  - XP x64: exit 4 on the first run, because a Found New Hardware window
    was open ("Nothing was changed"). The window was closed and the
    installer run again: exit 3, the root hub wizard, a restart.
- The driver: `build.cmd ndis5 trace` and `ndis51 trace` at `3942e20`
  (usb-wdm-free 0.1.8), the released source with the port-0xE9 trace.
  - `rtl815x.sys` x86 SHA-256 `d38ac63347905483...`.
  - x64 SHA-256 `ece06bff8ee9c2a7...`, unsigned. XP x64 warns and installs.
  - The INFs are the released files, byte for byte: `RTL81598.INF`
    `048b69dc...`, `RTL815X.INF` `42d166f1...`, `RTLXP7.INF`
    `479bf50c...`.
- The device: `rtlemu.py` at `3942e20` (SHA-256 `05f14740...`),
  `--chip 8156`, `8156b`, `8156-7020` or `8156b-7400`.
  - At SuperSpeed on the xHCI port (`--speed super`), at High Speed
    with `--speed high`.
  - `--serial` keeps one device instance per guest.
  - `--flap-after 25 --flap-for 8` pulls the cable once.
- Install: the Found New Hardware wizard, pointed at the driver's folder
  on the transfer disk. 98 SE and ME asked for the driver disk once and
  took the folder typed. 98 SE then asked for a restart (TCP/IP was set
  up); 2000 and XP asked about the missing signature (Yes / Continue
  Anyway).

Each leg:

1. Plug.
2. Bring-up and link (the trace).
3. DHCP (the simulator's log).
4. `ping -n 8 -l 1472` and `ping -n 4 -l 4000` (sent as three
   fragments; the simulated host answers the first) to 192.168.77.1.
5. `ping -n 20` with the unplug after 6 s.

PASS means all of these:

- chip start 0, and link at the speed in the table;
- a lease;
- 8/8 and 4/4 replies;
- after the unplug, "device gone", then "0 malformed transfers,
  0 dropped frames" and the halt, and the guest kept running.

## Owner, 2026-11-06: 0BDA:8056 and staging

`0BDA:8056` was added to `RTL81598.INF`, `RTL815X.INF` and `RTLXP7.INF`'s
XP, XP x64 and Vista sections (usb-wdm-free `52a29f2`). It is listed under
the RTL8156 name and taken from Realtek's 7 INF, the id only, with no
device on it seen. 7 stays Realtek's. The chip core reads the chip from
`MR_TX_CONFIG` (`rtlchip.c`) and nowhere from the USB product id, so
the id needs no chip path.

`rtlemu.py` gained `--chip 8156b-8056`: chip id `7410` behind
`0BDA:8056`. Which chip is behind the id is the model's inference.
`rtlsimtest.py`: 31 tests OK.

One XP leg, on the XP guest above:

- Rig: xHCI98 3.4.1.0, SuperSpeed, `build.cmd ndis5 trace` at `52a29f2`
  (`rtl815x.sys` `39cb628c...`, `RTLXP7.INF` `6888a8a0...`).
- The new device found no driver in the earlier `RTLXP7.INF` already
  installed (a Found New Hardware wizard came up). Pointed at the new
  INF, it installed as "Realtek RTL8156 USB 2.5G Ethernet (RTL815X)".
- The trace: "device bda:8056 rev 3000", "chip start: 0, version 7410",
  link 2500 Mb/s full duplex.
- DHCP, 8/8 at 1472 bytes, 4/4 at 4000, `ping -n 20` with the unplug,
  "0 malformed transfers" and the halt: PASS.

`STAGE.TXT`: the `net/rtl815x` lines for W98SE WME, W2K, WXP and WXP64 went
from COPY to STAGE, "staged on simulator legs (owner, 2026-11-06)". The
Vista and 7 lines stay COPY.

The gate was `releaseelease.ps1 -Check -NonFree` (the usb-wdm-nonfree
checkout at `1a3bdb9`). It ran on two scratch copies of the 0.1.8
definition with these four lines changed, and passed both times:

- one with the released `free/` INFs;
- one with `src`'s INFs carrying `0BDA:8056`. No id was staged twice on
  any system, the free and non-free sets taken together.

The `STAGE.TXT` written each time equals the committed one. The released
`free/` INFs are 0.1.8's until the next release copies `src`'s INFs into
`free/`.
