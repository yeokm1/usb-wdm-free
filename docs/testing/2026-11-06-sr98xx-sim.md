# sr9700 and the SR9800 in ax88772 with simulated chips: 98 SE, ME, 2000, XP and 7, 2026-11-06

xHCI98 roadmap 47.27 (owner, 2026-11-06): the CoreChips SR9700 and SR9800,
which no driver serves on any of this project's systems (ethernet.md
section 6.9). No such adapter is on the bench, so the legs ran against
simulators written from the same Linux facts as the drivers (`sr9800.c`,
`sr9800.h`, `sr9700.c`, `sr9700.h` at v7.3, facts only):
`ax7emu.py --chip sr9800` and `src/net/sr9700/sremu.py`. A misreading the
drivers and the simulators share passes here: the real chips stay owed.
All of this is emulated: no physical device was used and none is claimed.

## The drivers and their host tests

- `ax88772` at `f428b74` for the SR9800 legs (`ax772f.sys`, trace build,
  `b70a7c20...` ; free `ndis5` and x64 `ndis51` builds also made), and
  `sr9700` at `8272e2e` for the SR9700 legs (`sr9700f.sys`, trace build,
  `02b84f01...`; free `2f2298fd...`, x64 `a44cc1e2...`). The two later
  commits to `src/net/ax88772` change comments only.
- `ax88772` `test.cmd`: `chiptest` 58863 checks (the SR9800's bring-up
  order, LED and bulk-IN requests, link medium, filter base and Linux's
  pad rule added), `coretest` passes; `ax7simtest.py` 13 tests (the
  SR9800 through the simulator: bring-up, link, ARP, ICMP to 8000 bytes,
  the pad rule).
- `sr9700` `test.cmd`: `chiptest` 50 checks (bring-up, link, filter, the
  address, the retries of a failed filter or address write, receive
  packets and refusals, the transmit length bump and pad byte),
  `coretest` passes; `sr9simtest.py` 4 tests through `sremu.py`.
- The design and the code were reviewed and revised until no material
  finding was left but one: the shared core's worker thread on 98 SE and
  ME, which cannot be joined there, so halt waited 100 ms after its exit
  event in these builds. A later change sets that event from no
  instruction of the image (ethernet.md section 6.8, item 6), in every
  package's copy of the core.

## Rig

As [ax88772-sim](2026-11-06-ax88772-sim.md): stock QEMU 11.1.0, pc
machine, TCG, one vCPU; the 98 SE overlay (NUSB 3.3 EHCI, xHCI98 3.4.1.0)
and the ME overlay (xHCI98 3.4.1.0) of that run; the drivers from a
virtual floppy through the hardware wizard; a new simulator process per
plug. The SR9800 at High Speed; the SR9700 at Full Speed (a USB 1.1 chip).

The second 7 x64 guest: a fresh overlay of the same base, on which
Microsoft's servicing stack update KB4490628 (`wusa`, exit 0) and then
KB4474419 v3, SHA-2 code signing support (exit 3010), were installed
before xHCI98, the certificate and the INFs as above, then a restart.
Both from the Microsoft Update Catalog (2019-03 and 2019-09, "Windows 7
for x64-based Systems"), their SHA-1 equal to the catalog's digests:
`windows6.1-kb4490628-x64.msu` `d3de52d6...`, SHA-256 `8075f6d8...`;
`windows6.1-kb4474419-v3-x64.msu` `b5614c6c...`, SHA-256 `99312df7...`.
`wmic qfe` lists both; the Code Integrity log holds no event. The
guest's clock stayed at the base's 2026-09-20, before the certificate's
start.

**PASS on XP x64, and on 7 x64 with KB4490628 and KB4474419; FAIL on
the same 7 x64 base without them.** That comparison is what was
measured, on this one base. The explanation is inferred: the images'
file digest is SHA-1, but the test certificate is itself signed with
SHA-256 (`sha256WithRSAEncryption`), which 7's kernel Code Integrity
verifies once SHA-2 code-signing support is installed. xHCI98's own
test certificate, which the base accepts, is SHA-1-signed. Microsoft's
earlier KB3033929 also adds SHA-2 signing support; it was not tried. Earlier `usb-wdm-free` legs on Vista and 7 x64 signed the
images in the guest with a throwaway certificate instead
(2026-11-05-uac2-build26-nt6x64.md), so these are the first legs of
images signed with this certificate on 7 x64. Vista x64 was not run.
Microsoft's article on the SHA-2 requirement (KB4472027, read
2026-11-06) names the updates for 7 SP1, Server 2008 R2 SP1 and Server
2008 SP2 only; it lists no update for Vista. Whether Vista x64 takes
these images is not known.

## Not run

- The SR9700 under 98 SE's other host stack: it is a Full Speed device,
  which NUSB's EHCI does not take (a companion USB 1.1 controller does,
  and this rig has none). Owed with the real chip.
- Vista x86 and x64. The `0FE6:9702` (the SR9700 with a
  CD-ROM) is listed only in `SR9700F.INF` and was not run. The 2000 to 7
  legs ran the larger transfer at 4000 bytes, not 8000, and no cable
  flap.
- 10 Mb/s and half-duplex SR9800 links in a guest, multicast traffic,
  standby, throughput, Full Speed SR9800.

## Owed to the bench

A real SR9800 and SR9700 on 98 SE (xHCI98; NUSB's EHCI for the SR9800,
Windows' own USB 1.1 stack for the SR9700) and ME, and on 2000 to 7 with
`AX772F.INF` and `SR9700F.INF`: install, the trace lines above, a DHCP
lease, `ping -n 20 -l 1472` and `-l 4000`, a cable pull and replug during
`ping -t`, removal. What the simulators cannot show: the SR9800's own
reset timing, whether its bulk-IN transfers end with its 4 KiB burst,
how it takes a transfer that ends on a packet boundary unterminated (as
Linux sends it), its PHY's id and behaviour; the SR9700's descriptors
and endpoint numbers (inferred), its status report, and the `9702`
composite on each Windows.
