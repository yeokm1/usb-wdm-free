# The simulated AX88772B/C against ASIX's own drivers, 2026-11-07

xHCI98 Phase 47 (coordinator, 2026-11-07). The reference-driver record of
2026-11-06 (`2026-11-06-reference-drivers.md`) left `ax7emu.py` with two
open failures: ASIX's XP driver 5.4.3.0 bound but never had a network,
and ASIX's Windows 7 driver 5.12.12.0 ignored the model's DHCP OFFERs and
ended at Code 43. Here the model was changed until ASIX's drivers for XP,
7, 8 and 10 configure, get the link and pass DHCP, ping and TCP against
it; then `ax772f` ran against the changed model on 98 SE, 2000, XP and
7 x86. Everything here is emulated: no physical device was used and none
is claimed. The makers' binaries were only run, never read, and none is
tracked. The only sources were the USB traffic (QEMU's `pcap=` on
`usb-redir`), the model's own trace, Linux (`asix_common.c`,
`asix_devices.c`, `asix.h`, `sr9800.c`, `sr9800.h` at v7.3; the `sr9800`
files GPL version 2 only, facts only), the drivers' INF files, and what
each guest showed (its screen, `ipconfig`, `ping`, the System event log,
Device Manager codes).

## What the drivers showed, and what changed

Each item is marked INFERRED in `ax7emu.py`: no specification or open
driver gives it; the drivers' traffic does.

1. **The receive header's extension.** A2 to A5 write RX_CTL `0x0398`:
   SO, AB, AM and bits 8 and 9, which `sr9800.h` names RH1M and RH2M
   ("RX header mode"). `sr9800` sets RH1M alone and reads Linux's 4-byte
   header. With the 4-byte header A2 and A3 took no frame at all: A2
   repeated DHCP DISCOVER, A3 ignored the OFFERs (the 2026-11-06 failure).
   Two more bytes after the length word, before the frame, made both take
   every frame. The model now sends them, as zeros, when RX_CTL bit 9 is
   set; what a real chip puts there (a receive checksum result, by the
   INFs' receive offload settings) is not known, and zeros were taken.
2. **One record per bulk-IN transfer.** A2 to A5 write QCTCTRL with
   wValue `0x0000` (wIndex `0x8666`) at bring-up and at 100 Mb/s, and
   `0x008F` (wIndex `0xB500`) after a 10 Mb/s link; Linux writes `0x8000`
   / `0x8001`. With records cut across transfers (the model's 2 KiB
   bursts) A2 answered no `ping` above the MTU: the three fragments of a
   4000-byte reply came in transfers of 1520, 2048 and 560 bytes, and the
   driver took only the first. With one whole record per transfer every
   size passed. The model sends one record per transfer when wValue bit
   15 is clear and keeps Linux's bursts when it is set. The drivers ask
   for 32 KiB (A2, A3) and 64 KiB transfers; whether a real chip packs
   several whole records into one is not known.
3. **BMCR's resolved mode.** After a link change A2 and A3 read only
   BMSR and BMCR and write the medium mode from them: against the model's
   BMCR `0x1000` they wrote `0x0134` (A2) and `0x0104` (A3), that is
   10 Mb/s half duplex on a 100 Mb/s full-duplex link. With BMCR's speed
   (bit 13) and duplex (bit 8) reading as the mode autonegotiation
   resolved, they write `0x0336` and `0x03B6`. `ax772f`, as Linux,
   resolves the mode from ADVERTISE and LPA and is not affected.
4. **Transmit checksum offload.** Requests 2C and 2E (no data) carry
   `0x0319` and `0x0307`, which match the INFs' offload defaults (IPv4
   header, TCP and UDP over IPv4 and IPv6); A2 writes `0x0009` and
   `0x0003` once the link is up. Counted per record, as the drivers sent
   them:

   | Header bits 11-15 | A2 (XP) | A3 (7) | A4 (8) | A5 (10) |
   |---|---|---|---|---|
   | `0x8000` | ARP, ICMP, UDP: all sums right | ARP, IPv6 | IPv4 with all sums right (92), ARP, IPv6 | ARP, IPv6 |
   | `0x4000` | TCP: IPv4 header right, TCP wrong (1126) | UDP: header right, UDP wrong; TCP: both wrong (1113) | TCP: both wrong (287) | TCP: both wrong |
   | `0x0000` | - | ICMP, IGMP: IPv4 header wrong | ICMP, IGMP: header wrong | ICMP, IGMP, two UDP: header wrong |

   The model's old rule (insert the sums only for a record with a flag
   bit) left every unflagged ICMP echo with a wrong header, which the
   simulated host drops: A3's `ping` failed and A5's DHCP DISCOVER never
   reached the host. The model now keeps 2C and 2E as the receive and
   transmit offload settings and, unless header bit 15 is set, inserts
   what TXCOE asks for: the IPv4 header checksum (bit 0) and the TCP (bit
   1) or UDP (bit 2) checksum of a whole datagram; a fragment gets only
   its header checksum. Which of bits 1 and 2 is TCP is not shown: both
   were set whenever a driver sent UDP with a flag. IPv6 insertion (bits
   8 and 9) is not modelled;
   the simulated host ignores IPv6. Linux's transmit form and `ax772f`
   never write 2E, so nothing is inserted for them.
5. **A2's configuration.** A2 sets configuration 1, then configuration 0
   about 100 ms later, sends its whole bring-up on endpoint 0, and sets
   configuration 1 again about 3 s later. It did so on every plug here,
   the "before" run against the model at `6740d1b` included, which already
   answered vendor requests while unconfigured. The 2026-11-06 record saw
   the device left at configuration 0; why that run ended there and these
   did not is not settled. Nothing was changed for it.

The trace now counts each transmit record's checksum state as sent
(`tx_as_sent_<bits>_<state>`) and each bulk-IN request's size.

**Not modelled.** A3, A4 and A5 stop about 30 s after they start against
the model: the System event log has, from source AX88772B (A3) or
AX88772 (A4, A5), "Non-authentic ASIX product." and "ASIX does not
support it." (A4 and A5 log "INT send request failed." 50 ms before),
and the device ends at Code 43. Nothing on USB precedes it: A4's last
requests are a medium-mode write with RE clear. A model with a status
report on the interrupt endpoint every 128 ms instead of on link changes
only (A3) stopped the same way. What the drivers check is not known and
is not imitated. A2 logged nothing like it, over several minutes per
plug. Every leg on A3 to A5 below ran inside those 30 s.

## The simulated host's TCP

`src/net/ax88772/tcphost.py` (new, used by `ax7emu.py` only): TCP for
`axemu.py`'s simulated host, after RFC 9293 for a link that seldom loses
a frame (no window scaling, MSS only, a fixed 1 s retransmission from the
oldest byte, a zero-window probe, TIME-WAIT 30 s), with echo (7), discard
(9), a byte source (19) and HTTP (80: `GET /source?n=N`, POST with a
Content-Length). Each connection's end is logged with the byte counts and
the SHA-256 of what the guest sent.

## Full Speed on UHCI: bulk-OUT a packet at a time

A Linux run against the model (the SR9800 on UHCI at Full Speed) ended
the model with "transmit transfer 64 bytes, expected 337 (frame 333)":
QEMU passes such a transfer one 64-byte packet at a time, and the model
took the first packet as the whole transfer. The same path serves the
AX88772B/C. The model now joins packets until a short packet or a ZLP
ends the transfer, or until the bytes so far end a record (Linux's form
by its header's length, with sr9800's rule of no pad on a packet
boundary; ASIX's form at a record's end, so a whole 512-byte High Speed
transfer with no ZLP is still taken at once, and a pad word sent on its
own after it is taken as that transfer's end). A joined transfer is
bounded at 64 KiB; a USB reset, a configuration or an accepted
SET_INTERFACE drops a part-joined one. Host tests: `ax7simtest.py` 28 (3
new). Legs, 98 SE with `ax772f` as above, the 98 SE disk with a
`piix3-usb-uhci` added (98 SE's own `USB.INF` bound it):

| Leg | Result |
|---|---|
| UHCI, Full Speed, SR9800 | DHCP; `ping` 4/4 at 32 and 1472, 2/2 at 4000; 252 packets joined |
| UHCI, Full Speed, AX88772B | the same; 257 packets joined, 5 transfers with the pad word |
| UHCI, Full Speed, AX88772C (tip `646a880`) | DHCP; `ping` 4/4 at 1472, 2/2 at 4000 |
| NUSB's EHCI, High Speed, AX88772C | DHCP; `ping` 4/4 at 32 and 1472, 2/2 at 8000; no packet joined |
| NUSB's EHCI, High Speed, SR9800 (tip `646a880`) | DHCP; `ping` 4/4 at 1472, 2/2 at 4000 |
