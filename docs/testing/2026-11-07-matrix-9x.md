lists for 98 SE or ME, plus the new packages (`ax88772`, `sr9700`,
`absptr`), tested against the current simulators on 98 SE and ME. Each
one ran under xHCI98 and, where `STAGE.TXT` lists it, under NUSB 3.3 or
Windows' own UHCI. Worker mx9x, Phase 47. These are development legs in
QEMU (TCG) with the simulators, not a release and not "Tested". Raw

- `ev\faults.txt`: every fault screen's text and the controller state;
- `shots\`;
- `g\<leg>\`: serial and QEMU logs per boot;
- `scripts\report.py`: the classification used below.

## Method

Each leg follows these steps:

1. Stage the driver the way xHCI98's 9x STAGE does: copy its folder to `C:\WDMFREE\<driver>` and append that folder to `DevicePath`.
2. Plug the simulator and answer the hardware wizard. Copy prompts get the driver folder, the 98 SE CD files or `C:\WINDOWS\SYSTEM32\DRIVERS`.
3. Cold start after the first install. For `uac2` on 98 SE, also cold start after every profile, because 98 SE brings a new audio device up only at the next start.
4. For each profile:
   1. Run the functional test.
   2. Unplug, replug and test again.
   3. Restart and test again.

The functional tests are:

| Driver | Functional test |
|---|---|
| `uac2` | `UACWAV` play and record |
| `usbmidi` | `MIDITEST` loopback |
| `uvc98` | `M1CAP` frames |
| `xpad98` | `JOYTEST` |
| `absptr` | `PTRTEST` |
| `usbcom` | `COMTEST` full, quick, and hold across a pull |
| Network drivers | DHCP, ping (32 to 4000 bytes) and TCP, and a link flap where the profile has one |
| `usbflop` | read, write and format |
| `usbprn` | Add Printer and a test page; the simulator checks the PJL job |
| `libusb0` | install and listing |
| `noaud` | the device left driverless |

Every step runs as its own DOS box through Start > Run and reports on
COM1.

Other cases the harness records:

- 98 SE audio-arrival wedges (task 36.41): when the guest stops answering after a plug, the step is recorded as WEDGE, counted separately, and the harness resets the guest and cold-starts it.
- ME fault screens at boot: answered with Enter and logged with the screen text and the qemu-xhci `USBCMD`/`USBSTS`.
- Shutdown hangs: logged as SHUTHANG.

## uac2 under NUSB: the stall in bf92407 and the candidates after it

The bf92407 rebuild's `uac2wdm.sys` `24925d7f` is 8e2b8729 plus the u2iso merge. Under NUSB 3.3 on 98 SE it sometimes stalled:

- `UACWAV` reported `open=0 completed=0/8` after 15 s.
- The simulator's OUT stream sent a burst of 0.2 to 1 s and then nothing, while feedback kept flowing.
- In the 8e2b8729 and 0.1.8.26 legs of this matrix, every failed play read "no UAC2 output" (no device); none had an open stream with 0/8.

The coordinator and u2iso had candidate builds tested. Each build ran repeat legs on base `w98n2`:

- One install, then cold starts with 2 or 4 plays of 5 s each.
- After every play, the guest exported `HKLM\System\CurrentControlSet\Services\Class\MEDIA` (`STATS.BAT`). Each export is in `ev\<leg>-stats-c<cycle><play>.reg`.
- `Uac2UsbStats` is decoded in a `stats` step of `ev\results.jsonl`; `scripts\fsplays.py` classifies each play.

How plays are classed:

| Class | Meaning |
|---|---|
| deadline stall | `LastStatus` C00000B5 (the feedback deadline) |
| feedback-URB stop | `LastStatus` C000009C with `FbUrbFailed` at least 1 and `LastUsbStatus` C0000A00 (BAD_START_FRAME) |
| pace | the stream ran but the play ended at 6/8 or 7/8 at `UACWAV`'s 15 s limit; hs24 under QEMU's EHCI takes 7 to 16 s per 5 s play on every build |

### New in the method

- **TCP.** The network legs now carry a TCP step. Each simulator bridges its frames (`--udp`) to a QEMU user network on a hub, so the guest gets 10.0.2.15 by DHCP, and pings go to 10.0.2.2. `NETPERF.EXE` in the guest (`w47-tcp98b` `out\`) is reached through a forwarded port, and `netperf.py` on the host runs both directions for 10 s with a checked pattern.

## ME: the fault screen at a cold start (0E at BFF62170)

Under xHCI98, ME sometimes stopped at a cold start on "An error has
occurred ... Error: 0E : 0177 : BFF62170". After Enter, the boot went on
or never reached the desktop. The precedent is ME0E.1 in the 3.2.0.0
matrix: "0E : 0197 : BFF62170", 1 of 7. The coordinator's question
(2026-11-07) was whether 3.4.2.0 brought it in. Device-free boot loops
answer it: N cold starts of one fresh overlay of a read-only base, each
ended by a clean shutdown.

| ME base | Cold starts | Fault screens | Screen text |
|---|---|---|---|
| `men`: ME with no xHCI98 and no qemu-xhci (Windows' own UHCI only) | 111 | 2 | `0E : 016F : BFF62170` |
| `mex`: xHCI98 3.4.2.0 `3990e17d` | 105 | 4 | `0E : 0177 : BFF62170` |
| `mex4205`: `mex` with the tip's `xhci98.sys` `a38d2aa6` | 130 | 6 | `0E : 0177 : BFF62170` |
| `mex341`: xHCI98 3.4.1.0 | 145 | 4 | `0E : 0177 : BFF62170` |

- **Rates.** Fisher's exact test (two-sided) cannot separate any pair:
  - 3.4.2.0 builds (10 in 235) against 3.4.1.0 (4 in 145): p = 0.58;
  - 3.4.2.0 against no xHCI98 (2 in 111): p = 0.35;
  - any xHCI98 (14 in 380) against none: p = 0.54.

  So no bisect was run.
- **Controller state.** With xHCI98, every fault had qemu-xhci's `USBCMD` = 0x5 (Run set): `xhci98.sys` had started the controller before the fault.
- **Without xHCI98.** The same fault came with no xHCI98 and no xHCI controller in the machine. It has the same offset and only another selector.
- **Driver legs.** The same screen also stopped four cold starts in driver legs on `mex` (`usbflop-me-xh-a` b1, `sr9700-me-xh-a` b3, `uac2pu-me-xh-a` b2, `uac2pu-018-me-xh-a` b2); those steps are marked BOOTFAULT, not driver results.

**Reading:** Windows' or the rig's, not xHCI98's. The 98 SE fault
another worker saw on a q35 guest with no xHCI98 (`0E at 0167:BFF72170`)
shares this rig's emulator build (`cb36497`), TCG, the `pentium3` CPU
