# Windows 2000's own usbaudio.sys and a USB MIDI function, 2026-11-07

xHCI98 Phase 47 (owner, 2026-11-07): the 0.1.9 matrix on Windows 2000
found that a simulated USB MIDI function (AudioControl + MIDIStreaming,
`midiemu.py` profiles `acms` and `multi`, ids `FFFF:0001` and `FFFF:0002`,
which the released 2000 INF does not list) is taken at the plug by
Windows 2000's own `usbaudio.sys` (`wdma_usb.inf`, by class), and that
2000 then stops: STOP 0x1E in `usbaudio.sys` under Windows' EHCI, a
restart with no STOP screen under xHCI98. This record asks whether the
model is at fault, whether a real device does the same, how often it
happens, and what can be done. Development legs in QEMU (TCG) with the
simulator, not "Tested".

## Verdict

- **No fault found in the model.** `acms`'s configuration has the layout
  of the MIDI 1.0 specification's example device (Appendix B) and of the
  Roland UM-ONE mk2's own descriptors captured from the real device
  (`testdata/umtab`); the differences are listed in section 1 and none of
  them is in what the function is. The UM-ONE mk2's captured descriptors
  (profile `umtab`, Full Speed, at the real device's own id), replayed
  through the same simulator, stop 2000 the same way. The model already
  passed under the MIDI-capable `usbaudio.sys` of XP SP3 and 7 SP1
  ([inbox-reference](2026-11-06-inbox-reference.md)). No physical MIDI
  device was plugged into 2000, so a cause the simulator path shares with
  every profile is not excluded by these legs alone; the Microsoft
  statement below is what makes it expected.
- **Real, and Windows 2000's own.** Microsoft's page on `usbaudio.sys`
  names USB MIDI as supported from Windows Me and XP only; 2000's
  `usbaudio.sys` has no MIDI support, yet its `wdma_usb.inf` binds every
  audio-class function by `USB\CLASS_01`, so a MIDI-only function goes to
  a driver that cannot serve it. Before the stop the device sees no class
  request at all: one standard GET_DESCRIPTOR (device) after the
  function's configuration, then nothing.
- **Every plug.** 14 of 14 trials went down (below; 7 under Windows' own
  UHCI/EHCI, 7 under xHCI98), 12 of them within 15 s of the plug; the one
  that survived its first plug stopped at the unplug. The same fault address
  in `usbaudio.sys` (offset `0x4A90`, 10 of the 14) recurs under all three
  host controllers; the other stops are in `ntoskrnl.exe` (pool corrupted, bad
  pool free, wild pointers), always with `usbaudio.sys` on the function.
- **It does not need xHCI98.** It happens under Windows' own EHCI and
  UHCI, with the same `usbaudio.sys` offset as under xHCI98. (These legs
  do not show that xHCI98 has no fault of its own on such a device; they
  show that this one is not it.)
- **The "multi" restarts are not crashes.** The restarts with no STOP
  screen that the matrix saw at the `multi` plug (both stacks) are an
  orderly restart: `usbmidi` installed on the function from the test INF,
  2000 asked for a restart ("files in use"), the matrix's wizard answerer
  accepted it, and QEMU (`-action reboot=shutdown,shutdown=pause`) stopped
  at the reset. Section 5.
- **Recommendation:** option C now (document; grow the device list), and
  option D (a 2000 co-installer that reads the function's descriptors) as
  a design for the owner to decide. Option B (a class line) is not
  recommended: it cannot tell a MIDI function from a speaker. Section 6.

## 1. The model against the specification and real devices

`acms` (`midiemu.py` `CONFIG`), the MIDI 1.0 specification's Appendix B
example and the UM-ONE mk2 (TAB switch) captured 2026-10-21:

| | `acms` | MIDI 1.0 Appendix B | UM-ONE mk2 (`testdata/umtab`) |
|---|---|---|---|
| Device | USB 2.0, class 0, endpoint 0 64 bytes, `FFFF:0001` | USB 1.1, class 0, endpoint 0 8 bytes | USB 1.1, class 0, endpoint 0 64 bytes, `0582:0168` |
| Configuration | 101 bytes, 2 interfaces, bus-powered (`bmAttributes` 0x80), 100 mA | 2 interfaces, bus-powered, 100 mA | 101 bytes, 2 interfaces, bus-powered (0x80), 70 mA |
| Interface 0 | AudioControl (01/01/00), 0 endpoints | the same | the same |
| AC header | bcdADC 1.00, wTotalLength 9, one collection: interface 1 | the same | the same |
| Interface 1 | MIDIStreaming (01/03/00), 2 endpoints | the same | the same |
| MS header | bcdMSC 1.00, wTotalLength 65 | 65 (0x41) | 65 (0x41) |
| Jacks | IN embedded 1, IN external 2, OUT embedded 3 (from 2), OUT external 4 (from 1) | the same | the same shape, ids 0x40, 0x80, 0x20, 0x10 |
| Endpoints | bulk OUT 01 (jack 1), bulk IN 81 (jack 3), 9-byte, 64 bytes (512 with `--speed high`) | the same, 64 bytes | bulk OUT 02, IN 81, 64 bytes |

The AudioControl interface of a MIDI-only function holds a header and
nothing else (no terminal, no unit); that is the specification's own
example and the real device's form. `multi` (`MULTI`, two cables) is the
same shape with four more jacks; its MS header counts the jacks only
(wTotalLength 67, the specification's text) where `acms` and the real
device count the endpoints too (the Appendix's figure). Neither reading
matters here: `acms` and `umtab` stop 2000 as `multi` does.

What `usbaudio.sys` on 2000 sends before the stop (`pcap=`, the plug of
`t-xh-acms-high-1`; `t-win-acms-high-1` the same after Windows' own hub
and composite parent): the hub's enumeration (device, configuration,
string 0 and 2), SET_CONFIGURATION 1 by the composite parent, the strings
again, then **one GET_DESCRIPTOR (device, 18 bytes)** about 6 s (EHCI)
or 9 s (xHCI98) after the plug, which is the last request the device
sees. No SET_INTERFACE, no audio class request, no bulk transfer. The
wire does not say which driver asked or where it stopped; that the stop
comes while `usbaudio.sys` sets the function up from its descriptors is
an inference from that silence and from the STOP screens.

## 2. Does Windows 2000's own usbaudio.sys serve USB MIDI?

No. Microsoft, "USB Audio Class System Driver (Usbaudio.sys)"
(learn.microsoft.com, windows-hardware/drivers/audio): "In Windows 98
Usbaudio.sys introduced support for USB devices such as speakers and
microphones. Support for MIDI devices was added in Windows Me." and "In
Windows Me, and Windows XP and later, USBAudio supports all the features
that are supported in Windows 98 SE and Windows 2000. In addition,
Windows Me and Windows XP support USB MIDI". 2000's `wdma_usb.inf`
binds `USB\CLASS_01` to `USBAudio` and registers one wave interface
([usbmidi.md](../design/usbmidi.md) 3.1). So every class-compliant
MIDI-only device that no other INF claims by its id reaches a driver
without MIDI support, at the first plug, with no wizard to stop it.

What 2000 presents (the `Enum\USB` export of `t-win-umtab-full-1`):
Windows' own hub makes a composite parent `USB\Vid_0582&Pid_0168`
("USB Composite Device", `usbhub`) and one function
`USB\Vid_0582&Pid_0168&Mi_00` holding interfaces 0 and 1 ("USB Audio
Device", `usbaudio`), as xHCI98's bus does (`XHCI98_COMPOSITE` parent,
`&MI_00` function). This settles the open point of usbmidi.md 4.1 for
2000: the AC and MS interfaces are one function, whose compatible ids
are the AC interface's.

A real-shape device stops 2000 too: `umtab` (the UM-ONE mk2's own
descriptors, Full Speed as the real device) on Windows' UHCI stopped at
its unplug (STOP 0xC2, below), on xHCI98 14 s after the plug (STOP 0x1E
in `usbaudio.sys`).

## 4. The by-hand route on 2000

With `usbaudio.sys` going down at the first plug, the by-hand route of
usbmidi.md 4.3 (Update Driver, Have Disk, on the device once it is
present) seldom gets its turn on 2000. What works is an INF that names the
device by its id, staged before the first plug: 2000 ranks an INF's
hardware-id line above `wdma_usb.inf`'s `USB\CLASS_01` line even when the
INF is unsigned (the matrix's `setupapi.log`: "Found
USB\VID_FFFF&PID_0002&MI_00 in oem3.inf ... Found USB\CLASS_01 in
wdma_usb.inf ... Selected driver installs from section UM in oem3.inf"),
and `usbmidi` then binds at the first plug and `usbaudio.sys` never starts
on the function (the matrix's `usbmidi-w2k-*-11071513` `acms` legs:
MIDITEST 355/355 twice, both stacks). The released 2000 INF lists only the
UM-ONE mk2 in TAB mode: with the released INF staged
(`SetupCopyOEMInf`) before the first plug, `umtab` at the UM-ONE mk2's own
id (`t-win-umtab-full-9`, Windows' UHCI) bound `usbmidi` ("Roland UM-ONE
mk2 (TAB)") at the first plug and 2000 survived all three plugs and the
two unplugs; the same on xHCI98 (`t-xh-umtab-full-9`, `usbmidi` on the
`&MI_00` function). Any other AudioControl + MIDIStreaming function
that no installed INF names by its id reaches `usbaudio.sys` (a lone
MIDIStreaming interface takes the released INF's generic line instead,
and a vendor-class device its maker's driver).

## 5. The matrix's `multi` restarts

Coordinator's question (mxnt, `usbmidi-w2k-{xh,win}-11071513`): 2000
resets a few steps after the `multi` plug, no STOP screen, the same
registers on both stacks (EIP 80069519, CR2 a0130d72), QEMU "paused
(shutdown)". Read from the two guests' disks after the run (`qemu-img
convert -U` to a scratch copy; `setupapi.log` and the System event log):

- `setupapi.log`: the `multi` function installed from the test INF
  (`oem3.inf` / `oem1.inf`, section `UM`, chosen over `wdma_usb.inf`), and
  "Device required reboot: files in use, or treated as in use" (xHCI98
  15:23:26, EHCI 15:25:31). `usbmidi`'s INF notes this: 2000 asks for a
  restart when the KS/WDM audio files it copies are loaded.
- The screen kept by the matrix at 15:23:38 (xHCI98): "Completing the
  Found New Hardware Wizard ... The hardware you installed will not work
  until you restart your computer". The matrix's answerer presses Enter on
  every wizard page, which is Finish and then Yes to "restart now".
- The System event log: event 6006 (the event log service stopped, an
  orderly shutdown) at 15:23:46 (xHCI98) and 15:25:51 (EHCI), 20 s after
  each install, and no record of a stop.
- 2000 on the q35 board does not come back from a warm restart, and the
  matrix's QEMU turns a guest reset into a pause; EIP 80069519 lies in the
  HAL's range, where the restart ends.
- No function driver ever talked to the `multi` device: its trace holds
  the hub's enumeration only (under xHCI98 also the composite parent's
  SET_CONFIGURATION), no request from `usbmidi` or `usbaudio`.

So these are not crashes and not this family: an install that needs a
restart, accepted by the harness. (Under Windows' EHCI the test INF's
whole-device line `USB\VID_FFFF&PID_0002` matched the device node itself,
ahead of `usb.inf`'s composite parent, so `usbmidi` took the whole device
there; under xHCI98 the device node is `XHCI98_COMPOSITE&...` and
`usbmidi` took `&MI_00`.) The same reading holds for the
matrix's earlier `usbmidi-w2k-xh-11071432` `multi` restart (install
14:42:58 "required reboot", event 6006 at 14:43:12). The `acms` plugs of
`11071227`, `11071244` (xHCI98) and `11071233`, `11071433` (EHCI) end
with no 6006 record (no recorded orderly shutdown); the matrix's STOP
screen (`stop-1E-usbaudio-w2k-win-acms.png`) is from one of them, and
the others are read as the same from the trials above, not proved.

For the matrix: on 2000 the restart prompt after a `usbmidi` install is
expected (once per boot in which KS/WDM audio is loaded); a harness that
answers it should restart cold rather than count it as a failure.

## 6. What can be done

| Option | What | Fixes | Risk / cost |
|---|---|---|---|
| A. Change the model | none needed: the model is the specification's and the real device's shape | - | - |
| B. A class line in the 2000 INF | `usbmidi`'s 2000 INF also names `USB\Class_01&SubClass_01&Prot_00` (the compatible id the function carries; an MS-interface id `USB\Class_01&SubClass_03` is never on an AC+MS function, section 2) | every unlisted MIDI-only device on 2000 | the same id is on every USB speaker, microphone and headset (AC + AS): it is a better match than `wdma_usb.inf`'s bare `USB\CLASS_01`, and on 2000 a signature does not outweigh that (the guests' `setupapi.log`: the unsigned INF's driver date ignored, its line still selected), so `usbmidi` takes the audio function and, finding no MIDIStreaming interface, leaves it at Code 10 with no sound. Rejected before (usbmidi.md 4.2) for this reason; nothing here changes that |
| C. Document; grow the device list | release notes: on 2000, install usbmidi before the first plug; an unlisted class-compliant MIDI-only device (AudioControl + MIDIStreaming, no other driver for it) may stop 2000 at its first plug under Windows' own driver (Windows 2000 has no USB MIDI driver). Add known class-compliant MIDI-only products to the 2000 device list (usbmidi.md 4.2 already plans the list from a table). Optionally document how to add a device's own id to the INF before its first plug on 2000 (the id read on another system), the route that worked in section 4 | listed devices, and any device whose id is added before its first plug | an unlisted AC+MS device plugged in first may still stop 2000; a list needs the products' ids (facts, no driver needed); a hand-edited INF is for experienced users |
| D. A 2000 co-installer that reads the function | as `uac2`'s `UACCI1.DLL` (uac2.md 16.4, a MEDIA class co-installer that marks `usbaudio`'s node bad for a UAC 2.0 function), but on 2000 only: for a function with compatible id `USB\Class_01&SubClass_01&Prot_00` whose own interface collection holds a MIDIStreaming interface and no AudioStreaming interface, mark `usbaudio`'s node `DNF_BAD_DRIVER` and let `usbmidi`'s node win (a class node that this co-installer marks bad on every function that is not MIDI-only) | every unlisted MIDI-only device, speakers untouched | the compatible ids cannot tell the two apart, so the co-installer must read the configuration descriptor from user mode on 2000: the hub's `IOCTL_USB_GET_DESCRIPTOR_FROM_NODE_CONNECTION` reads the physical device's, so the design must map the function's node through its composite parent to the hub and port, find the function's own interface collection (another function in the same configuration may be audio), and say what happens when the read fails (leave the device as Windows would have it); xHCI98's hub must answer that IOCTL; whether all this works at install time on 2000 is unverified; a design record, review and legs on both stacks; a new user-mode file on 2000 |

**Recommended: C now, D as the owner's decision.** C costs a note and a
list and makes no listed device worse; D is the only option that serves
an unlisted device without risking speakers, and it is new design work
(the descriptor read from user mode on 2000 is unverified on both
stacks). B trades a crash on MIDI devices for silence on every USB audio
device and is not recommended.

Draft text for the release notes (option C; the owner rephrases):

> Windows 2000 has no USB MIDI driver of its own. A class-compliant MIDI
> keyboard or interface that also has an audio control interface (most
> do) goes to Windows' audio driver, which can stop Windows. Install
> usbmidi before you plug in the device: for such a device usbmidi takes
> over only if it lists it. Do not plug such a device into Windows 2000
> if usbmidi does not list it and it has no driver of its own.

(In the record's terms: an AudioControl + MIDIStreaming function that no
installed INF names by its id.)

So the material inspected ties no id to a class-compliant AC+MS

general: a maker publishes a Windows driver for a device mode that is
not class compliant, and a class-compliant MIDI-only product usually has
no driver, or an optional one shipped as an installer. The 2000 INF keeps its one listed device,
the UM-ONE mk2 in its TAB (class-compliant) mode, whose id this project
read from the real device. No id was added.

Sources that would serve, each needing the owner's or the coordinator's
leave: the configuration descriptor read from a real device (as
`testdata/umtab`; the owner's own MIDI devices); the INF text inside a
maker's self-extracting installer, read with an archive tool and nothing
run; or published descriptor listings of real devices.

## 8. A device added by hand on 2000 (owner, 2026-11-07)

The owner chose, instead of a maker list, to let users add their own
device to `usbmidi`'s 2000 INF (README, "Installing", `usbmidi` on
2000). The how-to's route, run on each stack:

- **Guest:** a fresh overlay of the matrix's 2000 base (`win`: Windows'
  UHCI; `xh`: xHCI98 `3990e17d`), Driver Signing policy Ignore as in
  those bases (so the signature question of the how-to's step 4 did not
  come up).
- **The edit:** the released `free/audio/usbmidi/w2k/` folder copied to
  `C:\USBMIDI`, its `usbmidi.inf` given one line after the UM-ONE line,
  as the how-to shows: `%Manual%=UM,USB\VID_FFFF&PID_1234&MI_00`, an id
  no INF lists. `DevicePath` set to `%SystemRoot%\inf;C:\USBMIDI` (a
  REG_EXPAND_SZ value, written here by a `.REG` file rather than by
  `regedt32`), and `AutoReboot` 0; then a shutdown and a cold start
  (this board's rule for any restart), all before the first plug.
- **The device:** `midiemu.py` `acms` with `--pid 1234` (`FFFF:1234`),
  Full Speed: on Windows' UHCI and on xHCI98.
- **Three plugs**, each followed by MIDITEST `list` and `0 0` and the
  `Enum\USB` export, and an unplug.

| Stack | Plug 1 (first plug, install) | Plug 2 | Plug 3 | Bound |
|---|---|---|---|---|
| Windows' UHCI (`bh-win`) | `usbmidi` installed from `C:\USBMIDI`, no restart asked; 355/355 PASS | 355/355 PASS | 355/355 PASS | `USB\Vid_ffff&Pid_1234&Mi_00` `usbmidi` (parent `usbhub`) |
| xHCI98 (`bh-xh`) | the same; 355/355 PASS | 355/355 PASS | 355/355 PASS | `USB\VID_FFFF&PID_1234&MI_00` `usbmidi` |

No stop on either stack; `usbaudio.sys` never took the function. The
`&MI_00` form the how-to asks for is the function id on both stacks
