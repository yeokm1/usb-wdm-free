# rtl815x with a real RTL8157, 2026-11-06/07

xHCI98 task: the owner reports users finding `rtl815x` slow and the
adapter perhaps running hot. A real RTL8157 (chip id `1030`, USB
`0BDA:8157` rev 3000) was tested on development host A, passed through
to QEMU guests. Its cable ran straight into a 10GbE port of the host
(link-local addresses, no switch). Every number below is from guests
under TCG emulation and is relative: it is not a real machine's speed.

## Rig

- The adapter was bound to WinUSB on the host and given to a guest by
  QEMU `usb-host` (hostbus/hostaddr read at each attach) on the
  `qemu-xhci` port. Captures were made with `usb-host`'s `pcap=` option
  and decoded with `src/net/rtl815x/rtlpcap.py`.
- Two emulators:
  - The usb4-emu fork build `cb36497` ("stock").
  - A test build of the same QEMU 11.1.2 source with two changes to
    `hw/usb/host-libusb.c`: the Windows libusb poll at 0.25 ms instead of
    10 ms, a request only bringing the poll forward, and bulk endpoints
    pipelined. This is a test tool only and is not kept in any
    repository.
- Guests: q35 bases, each on a fresh overlay.
  - XP SP3 and 98 SE under xHCI98 3.4.1.0 as released (`INSTALL.BAT`,
    exit 3).
  - Windows 10 22H2 x64 under Windows' own xHCI driver.
- Traffic: `NETPERF.EXE` (new, `src/net/cdcnet/netperf.c`) in the
  guest as a TCP server. `netperf.py` on the host connects out, so the
  host's inbound firewall plays no part; the stream is a fixed pattern
  checked on both sides.
- Pings were sent from the host at 1472, 4000 and 8000 bytes.

## The passthrough path

The stock emulator polls libusb every 10 ms (virtual clock, re-armed by
each new request). It never pipelines bulk transfers: one transfer per
endpoint is in flight, about 85 a second. Any driver is then capped near
17-20 Mb/s per direction.

| Driver, guest, stock rig | out (guest to host) | in (host to guest) |
|---|---|---|
| Realtek 10.68.20, Windows 10 x64 | 17.2 Mb/s | 17.6 Mb/s |
| rtl815x 0.2.1.0, XP | 6.0 Mb/s | 19.2 Mb/s |
| rtl815x 0.2.1.0, XP, both directions at once, 11 min | 2.07 Mb/s | 15.2 Mb/s |

rtl815x's outbound figure is the lower one for two reasons:

- Its bulk-OUT transfers are small: 53% carry one frame, at most 10
  frames (15354 bytes). Its bulk-IN transfers are aggregated to 32 KB.
- With both directions at once, the outbound pipe also carries the ACKs
  for the inbound stream.

The Windows 10 inbox has no driver for the RTL8157 (Code 28).
`rtl815x` cannot run on Windows 8 and later (no NDIS 5), and Realtek
ships no XP or 7 driver for this chip. So no same-OS comparison exists.

## Reliability (xHCI98 3.4.1.0)

| Leg | Before | After the changes |
|---|---|---|
| XP: link | 5000 Mb/s full duplex | the same |
| XP: ping 1472/4000/8000, 10 each | 10/10 each | 10/10 each |
| XP: TCP both ways 11 min | 1.43 GB, 0 mismatched bytes | (see Speed) |
| XP: unplug idle, replug | pass | pass |
| XP: unplug under TCP both ways | **hang** (below) | pass, 3 + 3 cycles ("0 of 9" and "0 of 13 transfers still outstanding after the abort"); `f446180`: pass, 3 cycles ("0 of 13") |
| XP: TCP both ways 11 min | 1.43 GB (stock rig) | `16333c0` with 32 KiB transmit: 2.31 GB out at 27.9 Mb/s, 4.92 GB in at 59.6 Mb/s, 0 mismatched; but 3191 sends failed for a full queue (below) |
| XP: TCP both ways 11 min, `f446180` | - | 4.58 GB out at 55.3 Mb/s, 5.45 GB in at 66.0 Mb/s, 0 mismatched, 0 failed sends (queue peak 283) |
| XP: Device Manager disable/enable | - | pass; the host's port goes Disconnected while disabled (PHY down) |
| 98 SE: link, pings | 5000, 10/10 each | the same |
| 98 SE: TCP out | **0.01-7 Mb/s, queue corrupt, fatal exception 0E** | ran at 37-70 Mb/s, but still stalls and faults (below) |
| 98 SE: TCP in | stalls after 12-100 MB, once 17512 corrupt bytes | still stalls |
| 98 SE: unplug under ping, replug | - | pass (halt, image reloaded, 5/5) |
| 98 SE: TCP both ways 10 min | - | 0E at `0028:C1924CA3` after 38 s |

**XP unplug under traffic.** xHCI98 holds a departed device's transfers
instead of failing them. Nine IRPs stayed outstanding and 40 sends sat in
the transmit slots. TCP/IP never unbound, so `MiniportHalt` never ran:
- the adapter stayed in Device Manager;
- a replug never loaded;
- shutdown hung.

Fixed in the shared core (ethernet.md section 4.7).

**98 SE sends.** The core's queue showed a null head with a tail pointing
into the 98 TCP/IP's memory. Fixed by two changes (ethernet.md section
6.4.2), both needed: without either, 98 SE failed at once.
- The send status is set to PENDING.
- The core takes the kernel spin lock.

**A full send queue failed sends.** Under sustained TCP on XP, the
core's queue limit of 64 frames was reached and `MiniportSendPackets`
failed the excess with `NDIS_STATUS_FAILURE`: 3191 sends in the 11-minute
run, each a loss for TCP. A deserialized miniport must keep every valid
send, so the queue no longer has a limit (ethernet.md section 6.4.2).

**98 SE, still open.** Every build so far stalls or faults under
sustained TCP: fatal exceptions 0E at `0028:C19243C3`, `C1924CB3` and
`C1924CC3`, and once "in VXD MSTCP(01) + 00004F5A".
- The driver's receive pool stays whole (64 free, 0 out) when it
  happens, and every indicated packet is returned.
- Neither a larger pool nor 4 KB transfers changed it.
- A control with another fast NIC on 98 SE could not be set up: 98 SE
  has no driver for QEMU's RTL8139.
- Followed up in `2026-11-07-98se-tcp.md`: the stalls followed the context of
  the driver's receive indications and send completions on 98 SE, which
  are now made from an NDIS timer there (ethernet.md section 4.4).

## Speed (test emulator)

With the 0.25 ms poll and pipelining, the stock rig's cap is gone and
the guest CPU under TCG is the limit (QEMU at 1.0-1.5 host CPUs). The
numbers are relative: each row is one build on the same XP boot, 4 runs
of 20 s per direction, interleaved.

| Build | out (guest to host), Mb/s | in (host to guest), Mb/s | guest CPU in |
|---|---|---|---|
| A+B only (removal, send status) | 28.5, 23.3, 24.4, 30.1 (mean 26.6) | 52.9, 55.9, 64.2, 59.6 (58.2) | 65-68% |
| + batched receive (S3), 8 bulk-IN (S1), PHY down | 28.3, 32.1, 43.3, 39.6 (35.8) | 74.9, 84.2, 84.1, 81.3 (81.1) | 60-61% |
| + 32 KiB transmit (S2, held for the owner, not in this line of commits) | 32.9, 29.6, 28.9, 27.5 (29.7) | 82.7, 76.8, 67.4, 66.9 (73.5) | 61-63% |
A second boot compared the queue fix. Each build ran 4 runs
of 20 s per direction, interleaved.

| Build | out, Mb/s | in, Mb/s | failed sends per 80 s | frames copied (RESOURCES) |
|---|---|---|---|---|
| `16333c0` (before the queue fix) | 27.1, 36.2, 30.3, 30.0 (30.9) | 71.4, 73.9, 66.6, 64.5 (69.1) | 147, 184 | - |
| the queue fix, before the D3 and recovery guards in `f446180` | 29.7, 30.5, 24.0, 28.5 (28.2) | 74.8, 72.0, 65.2, 64.6 (69.2) | 0, 0 (queue peak 190) | 1714, 2015 |
| the same with 128 receive packets (experiment) | 26.4, 26.8, 27.2, 27.0 (26.8) | 77.7, 72.0, 68.5, 69.1 (71.8) | 0, 0 | 452, 1350 |

- The queue fix removes every failed send. In 20 s runs of one
  direction it changes neither direction's throughput. In the 11-minute
  run of both directions at once, outbound went from 27.9 to 55.3 Mb/s
  (different boots, and the earlier build also had 32 KiB transmit).
- 128 receive packets cut the copied frames by a third to three
  quarters, but throughput stayed within the spread, so it was not
  adopted.

- An earlier boot gave S3 alone +20% inbound over A+B: 61.3 and 61.8
  against 47.7 and 52.6.
- S1 at 5 and at 8 measured within the spread of each other.
- S2 shows no gain on this rig; it is held for the owner on its own
  commit, off this line.
- 98 SE, after B: one run at 69.5 Mb/s out; other runs 9-38 Mb/s
  before the stall described above.
- Realtek 10.68.20 on Windows 10 x64, same rig: 244 Mb/s out, 339 in, at
  100% guest CPU. That is not a comparison of drivers: it is a different
  OS and TCP stack, with LSO and checksum offload.
  - Its bulk-IN: up to 5 x 32 KiB in flight.
  - Its bulk-OUT: up to 3 x 32848 bytes.
  - rtl815x before: bulk-IN 4 x 32 KiB, bulk-OUT 4 x at most 10 frames.

Data buffers per adapter (nonpaged on NT, page-locked on 98 SE):
- RX 8 transfers (4 before) of 32 KiB, or 16 KiB on the RTL8152 and on
  the RTL8153 below SuperSpeed;
- TX 4 x 16 KiB;
- 64 x 1536 bytes of receive packet storage.

Those data buffers come to 416 KiB with 32 KiB receive buffers (288 KiB before), and 288 KiB
with 16 KiB ones (224 KiB before). Adapter state, control and interrupt
buffers, IRPs and the packet and buffer descriptors come on top.

## Heat-related settings

Final register writes from usbmon captures: rtl815x on XP, and Realtek
10.68.20 on Windows 10, whose PHY access goes through its own USB
`0xd630`/`0xd634` window.

| Setting | rtl815x (= Linux) | Realtek 10.68.20 default |
|---|---|---|
| EEE: MAC `0xe040` bits 0-1, PHY `0xa432` bit 4, advertised `0xa5d0`/`0xa6d4` | on; 100M, 1G, 2.5G, 5G | off; none |
| ALDPS, PHY `0xa430` bit 2 | on | off |
| EEE clock division, `0xa430` bit 15 | on | off |
| 10M clock division, `0xa442` bit 11 | on | off |
| MAC clock slow-down, `0xe0ca` bit 15 | on | off (bit 14 set instead) |
| Chip U1/U2 while linked, USB `0xcfd8` bit 0 | off | off |
| UPS and power cut | off | off |
| PHY at disable | was left up (link kept at 5G); now powered down | powered down (BMCR bit 11) |
| Interrupt pipe (bInterval 11 = 128 ms) | 7.8 completions/s under xHCI98 | 124.5/s under Windows' xHCI |
| Link poll by control read | every 2 s | about every 5-10 s |

Realtek's INF defaults for the RTL8157 agree: `*EEE` 0,
`EEEMaxSupportSpeed` 1000, `EnableGreenEthernet` 0, `AdvancedEEE` 0,
`EnableExtraPowerSaving` 0, `*SelectiveSuspend` 0. Its buffer settings
are `PendingReceives` 10 x `ReceiveBufferLen` 32 and `PendingTransmits`
3 x `TransmitBufferLen` 37.

xHCI98 never enables U1/U2 (`xhci_enum.c`). For the 8157 the chip side
is off while the link is up, under Linux and Realtek too, so this makes
no difference here.
