# uac1 0.1.0.1 on Windows 98 SE, 2026-11-07

xHCI98 Phase 47: the legs of `uac1` 0.1.0.1, the USB Audio Class 1.0
driver for Windows 98 SE built from the driver core `uac2` shares
([design 26](../design/uac2.md)), and the gates the owner set for its
binding by class on 98 SE (26.10): G1, an unplug while playing on a real
device; G2, the first plug of a boot on 98 SE's own USB 1.1 stack; G3,
the layouts `uac1` does not run. With them, `usbmidi` beside `uac1`,
`uac2`'s regression legs on the new shared build, and XP, where `uac1`
must not bind.

These are development legs in QEMU (TCG), not "Tested".

**Outcome.** G1 failed, as `uac2`'s control did; G2 matches Windows'
own driver; G3 passed; `usbmidi` works beside `uac1`; `uac1` does not
bind on XP; `uac2` is unchanged by the shared build. The owner ruled
(2026-11-07): `uac1` ships in 0.1.9 as an option, by class as built,
with Windows' `usbaudio` the default; the unplug and first-plug
behaviours are known issues (design 26.11).

## Harness notes

- **First plug of a boot (36.41).** On 98 SE the first audio arrival
  after a cold start wedges the guest about half the time, with
  `uac2` and Windows' own `usbaudio` too ([known issue](../status.md)).
  A leg resets, cold starts and plugs again, and records the wedge
  apart (WEDGE); it is not a result of the driver under test.
- **A stuck stream holds COM1.** A test whose buffers never return keeps
  its window and COM1. Legs from 17:00 send Ctrl+C twice and Alt+F4
  before asking the guest whether it answers; earlier legs' "guest does
  not answer" after a stuck recording can mean COM1 was held, not a
  freeze (the screenshot's taskbar clock tells them apart).
- **"No problem code"** lists the Problem values of every device of the
  base, not only the one under test: not usable; G3 rests on the null
  start's stage value (`Uac2M0Stage` 0x40/0x41).

## usbmidi beside uac1

Base `w98k`, legs `uac1-w98-xh-coex1` and `-coex2`: `uac1` on the
simulated `headset` (root port 1), then `usbmidi` on `midiemu.py`'s
`acms` (root port 2), listed by hardware id in its test INF. MIDITEST is
a 355-message loopback through the model's echo.

| Step | coex1 | coex2 |
|---|---|---|
| headset install, play 3 s | PASS | PASS |
| MIDI install beside it; MIDITEST | PASS (355/355) | PASS |
| play beside MIDI | PASS | PASS |
| audio unplugged; MIDITEST | PASS | PASS |
| audio replugged, play | PASS | PASS |
| MIDITEST after the audio replug | FAIL (WinMM error 4 on the old port numbers) | PASS, ports read again |

When the audio device comes back, WinMM numbers its MIDI outputs anew:
before, output 0 was the loopback and output 1 Windows' software synth
(which `uac1`'s INF, as `uac2`'s, offers through the audio device); after
the replug the synth was output 0 and the loopback output 1. coex1 opened
the old numbers; coex2 read the list again and passed. A program that
keeps a MIDI port number across an audio device's arrival can open the
wrong port; `usbmidi`'s ports themselves keep working beside `uac1`.
The same leg with `uac2` on the simulated `hs24` (`uac2-w98-xh-coexu2`)
renumbered the outputs the same way after the audio replug, and passed
on the numbers read again: the effect is the audio devnode's software
synth entry, shared by both drivers, not `uac1`'s.

never match. Leg `uac1x-xp-xh-11071800` (XP SP3 x86 under xHCI98

`uac1` does not bind on XP.

`uac2` on XP SP3 x86 with the new shared build (`36cd9aa7`), the mxnt
kit's legs (first plug, play, record; the first profile also replugged
and restarted), set beside the same profiles of the build before the move

|---|---|---|---|
| `x4full` | PASS, replug, restart | PASS; replug play 1/8; restart PASS | first plug FAIL then PASS / PASS |
| `hs24` | PASS | PASS | PASS / PASS |
| `fs` | play 0/8, record PASS; rerun: PASS, replug, restart | play 0/8 (Full Speed on UHCI), record PASS | PASS / FAIL |

## The final image

`dd0ff364`, on bases `w98k` (xHCI98) and `w98p` (98 SE's own UHCI, a clean
install with the final INF):

| Leg | Result |
|---|---|
| `nor2`, `w98k` | `play2`: install, list, play 48 and 44.1 kHz, the mixer ramp, record 48 kHz PASS (two first-plug wedges before, 36.41) |
| `fz5`, `w98k` | `headset`: the same steps PASS (one wedge before); `logi`: not run (dropped at wrap-up; the replay passed on the earlier images) |
| `fz6`, `w98p` | `headset`: Setup's two non-KS prompts, play and record 48 kHz PASS |

G3 was run again (`fz3`: `pcm8` and `midi:acms`, null start 0x40, no audio
device, unplug clean: PASS) on an image that differed only by the rule
withdrawn below; neither layout carries an alternate either way.

Three changes were tried after `ccc649c9`, each for a finding of the
final review on a layout no device read has, and withdrawn. Images with
the first never started playback of the `play2` layout on 98 SE (no
alternate selected, 0 of 8 buffers; legs `fina`, `fz1`, `fz4`), where
the same code without it played (`nor2`) and `ccc649c9` played in the
same rig (`ctla`, `ctlb`); the other two went with it, untested on their
own. Each issue is open in the shipped code, as it is in `uac2`'s:

| Change withdrawn | The issue it addressed | In the shipped code |
|---|---|---|
| One direction per AudioStreaming interface | a playback and a capture alternate on the same AS interface: starting one direction selects another alternate of the interface under the other's running stream | open: no guard; `uac2` has none either |
| Each format's rates from its own alternates, only rates one of them carries | the terminal's list holds 16 rates; rates past them, or a later format's own, are not offered | open: such a rate or format is not offered |
| The pin's data ranges taken format by format in turn | 32 data ranges for all formats: a later format past them is not offered to Windows | open: such a format is not offered |

`uac2wdm.sys` built from this tree is the same as `w47-rel019`
`b9e2222`'s build: x64 byte-identical, x86 identical but for the order
of the six adjustor thunks.
