# `ax88179` with EEE on and off: a real AX88179 through QEMU, 98 SE, 2026-11-09

Design [ethernet.md](../design/ethernet.md) section 12.3 (owner,
2026-11-09: `*EEE` on by default, ASIX's 7 INF default; a real AX88179
with EEE on owed). The owner attached a real AX88179 (`0B95:1790`, revision
`0100`, WinUSB on development host A) for this check; its cable went to
one of the host's own 10GbE ports ("Ethernet 2", whose driver showed
Energy-Efficient Ethernet Enabled, EEE Max Support Speed 1.0 Gbps Full
Duplex, Green Ethernet Enabled, Advanced EEE Disabled, read only). The
adapter was passed through to the guest with QEMU's `usb-host`; nothing
on the host was changed (its binding, firewall and addresses stay as they
were). The host's own network stack was the link partner, so this is a
real chip and a real PHY link, in an emulated machine.

## Rig and build

The 9x matrix's harness (`E:\xhci98-vm\p48\wdmb\kit`): QEMU `cb36497`
(usb4-emu fork), TCG, one vCPU, the `w98x` base (98 SE, xHCI98 3.4.2.0),
the AX88179 on qemu-xhci at SuperSpeed. `ax179f.sys` trace build
`5d42b292...` (branch `w48-wdmb`, the Advanced-tab code), `AX179F98.INF`
of the same tree (`*EEE` 1, `*SpeedDuplex` 0, `*FlowControl` 3 written at
install). Host commands: read-only `Get-NetAdapter*`, `ping.exe`, and,
by the owner's exception for this leg, `iperf` 2.0.8 (`575691cf...`) as a
client only (outbound, bound to the host port's address); the server ran
in the guest. Every host `iperf` process is in the kit's `pids.txt`.

## Results

| Step | Result |
|---|---|
| Install (wizard, `DevicePath`), cold start | the driver trace: `setting *EEE = 1`; `initialized: b95:1790 chip 179, super speed USB`; `link 1, 1000 Mb/s full duplex`; the host port Up at 1 Gbps |
| Guest address | 169.254.30.78 (98 SE's own APIPA; no DHCP on the link); host port 169.254.197.91 |
| EEE on: host `ping` 50 x 32 bytes | 50/50, 2-25 ms |
| EEE on: host `ping` 500 x 1472 bytes (soak) | 500/500, 2-43 ms, average 9 ms |
| EEE on: host `ping` 50 x 8000 bytes (fragmented) | 50/50, 60-248 ms |
| EEE on: `iperf -c <guest> -B <host port> -t 30` (host to guest) | 14.0 MB in 30.2 s, 3.89 Mbit/s (10 s intervals 4.61, 3.04, 4.09) |
| EEE on: the same with `-P 4` | no result within 90 s (98 SE's `iperf` server took the first connection only, it seems); the client was stopped |
| EEE on: guest `netstat -e` after | received 15093958 bytes, 10075 unicast; sent 115502 bytes; discards 0/0; errors 0 received, 1 sent (the 1 was there before the traffic) |
| EEE off (`*EEE` 0 written as the tab writes it, then a cold start and a plug) | trace `setting *EEE = 0`; link 1000 full |
| EEE off: `iperf` host to guest, 30 s | 15.3 MB in 30.2 s, 4.23 Mbit/s |
| EEE off: `-P 4` | as with EEE on, no result |
| EEE off: guest `netstat -e` after (counted from that boot) | received 16443598 bytes, 10975 unicast; sent 116150 bytes; discards 0/0; errors 0 received, 1 sent |
| Removal at each halt | `halted: tx 2101/4 rx 10100` and `tx 2113/4 rx 11000` (the 4 sends failed are the ones in flight at the removal) |
| A link drop and back (QMP `device_del` and `device_add` within one boot) | first leg (`real179-w98-xh-a`, EEE on): the driver halted and started again (`link 1, 1000 Mb/s`), but the guest then answered no Start > Run (screen black, the session stopped); second time (`iperf179`, EEE off): the guest answered and the driver linked again |

- The throughput is the emulated 98 SE's (TCG, one vCPU), the same order
  as the simulated chips' TCP legs (2 to 4 Mbit/s): it says the data path
  carried sustained TCP with EEE on and off, not what the chip can do.
- EEE's low-power idle (LPI) is not observable from the guest, and
  `ax88179` reads neither the PHY's EEE advertisement back nor the
  partner's EEE ability (the driver writes the advertisement only). What
  was negotiated is not shown here; that the link and sustained TCP
  behaved the same with EEE on and off is (the pings ran with EEE on
  only).
- Not run (needing an inbound connection to the host, not allowed): the
  guest-to-host direction (`iperf -r`, `-d`, a guest client), and pings
  from the guest (the host's firewall drops them).

**Reading:** with `*EEE` on (ASIX's 7 default) the real AX88179 linked at
1000 full against an EEE-capable partner and carried 500 pings and
sustained TCP without loss or a receive error. With EEE off it linked the
same and carried sustained TCP at the same rate with the same counters;
the ping soak was not repeated with EEE off. The guest that stopped
answering after a hot replug (EEE on) did so with the driver's trace
showing a completed restart; the replug with EEE off came back. Its cause,
and whether EEE has a part in it, are not known: open.
