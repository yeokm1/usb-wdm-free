# uvc98 at Full Speed under a UHCI driver on 98 SE: the cause and the fix, 2026-11-09

The open item "`uvc98` on 98 SE: ... Full Speed under 98 SE's own UHCI"
([open items](open-items.md)): with `M1CAP` `06e30623` the third frame
of every Full Speed run came back empty under 98 SE's own UHCI driver and
under NUSB's UHCI companion, while xHCI98 passed the same profile. This
record reads the cause with a trace build, and runs the fix, design
[uvc.md](../design/uvc.md) section 5.4a (commit `f9f6aed`), on the stacks
of the [9x matrix](2026-11-07-matrix-9x.md). Development legs in QEMU
(TCG) with the simulator, not a release and not "Tested".

## The cause (leg `uvcfs-w98-own-t1`, 0.1.9 trace build, 98 SE's own UHCI)

Four runs, all FAIL as in the matrix: READ 1 and 2 good, READ 3 empty
(`data=0`, `drops=1`). The trace after READ 3:

| Counter | Value |
|---|---|
| URBs completed | 50 (`0x32`) |
| whole-URB failures | 8 |
| first failure | NTSTATUS `C000009C`, URB status `C0000A00` (`USBD_STATUS_BAD_START_FRAME`) |
| stream | stopped by the driver (`UVU_STOP`, the pipe aborted) |

The test tool writes each 38 KB frame to the floppy between reads; the
guest stalls longer than the 48 ms the three queued 16-packet URBs cover.
Every URB resubmitted with `USBD_START_ISO_TRANSFER_ASAP` after that came
back at once with `USBD_STATUS_BAD_START_FRAME`, and section 5.4's rule
(8 whole-transfer failures in a row end the stream) ended it. The
simulator saw the guest stop polling the endpoint and never start again
(`stop_iso_stream` 0.255 s after the start, as in the matrix): the
stream was over in the guest, not in QEMU. Under xHCI98 and EHCI the same
stall did not end the stream.

## The fix (design 5.4a)

A transfer the stack refuses for its start frame is a lost interval and
marks a resync; once every slot is back and the start path has filled
them, every slot is submitted at an explicit start frame (current frame +
8 + k x 16), and ASAP after that; 4 resyncs with no good transfer between
them end the stream. Host checks in `isotest` (`2486355 checks, 0
failures`); the other host tests of the package pass as at `3f41d8c`
(`flowtest` and `m1test` fail there and here alike: `flowtest` links no
`FLOWTEST.EXE` on this host, `m1test` fails its check at line 139).

Trial `uvcfs-w98-own-t2` (the draft's trace build, the same stack): 4 of
4 runs PASS. After the stall the trace read one resync after 3 refused
URBs, then 32 good URBs (the explicit ones, then ASAP) and READ 3 good.

The High Speed FAILs under NUSB are not the fix's. Two trace legs on the
same stack and profile (`uvc11-hs`, full cycle) told them apart:

- `uvc98-w98-nusb-t4`, the fix with a per-transfer trace (`bc316843`:
  `f9f6aed` plus trace lines for every failed or refused transfer and the
  resync's frames; not committed): in every run no resync, no refused and
  no failed transfer; the frames were dropped for packets that came back
  with an error status (`USB_PKT_FAILED` 0x1D0 to 0xD39 a run, frames
  dropped as bad).
- `uvc98-w98-nusb-t0`, 0.1.9's trace build (the release's code): the
  same, READ 1 empty with packet errors (`USB_PKT_FAILED` 0x31D, 0x810).

Under xHCI98 at Full Speed the first captures after the install met
guest stalls: the guest's clock stood still for minutes while the
harness waited. A trace leg (`uvc98-w98-xh-t5`, the trace build above)
read no resync and no refused or failed transfer in any run; inside the
guest its first capture passed (three frames, `PASS` on COM1), too late
for the harness, with READ 2 and 3 skipping 3 and 9 frames, the guest
starved; its replug and restart runs passed. In `r3` the first capture's
READ 3 timed out inside the guest during such a stall. The control
`uvc98-w98-xh-c2` (0.1.9) passed its first two captures and its restart
run, and lost its replug run the same way (no end marker within the
harness's wait). The new code does not
run on xHCI98 (it never refuses an ASAP transfer: it schedules one after
the last queued transfer), and 0.1.9 lost a run the same way, so the
loaded host is the suspected cause; the Full Speed cell under xHCI98 is to
be run again on a quieter host.

The matrix's NUSB High Speed cells passed with 0.1.9 on a lighter host
([9x matrix](2026-11-07-matrix-9x.md)); development host A ran at about
94% CPU during these legs, other work included, which is the suspected
cause of the packet errors; it is not isolated here. The High Speed cells
under NUSB are to be run again on a quieter host.
