# MTP M0: binding and NTKERN readings on 98 SE and ME, 2026-11-16

M0 of [mtp.md](../design/mtp.md) (sections 5.6 and 12): how 98 SE and ME
bind a still image (MTP/PTP) device, and how NTKERN and each USB stack
carry the handle contract the driver will rely on. All of it was read
with the M0 probe driver `MTPPRB.SYS` and its program `MTPPROBE.EXE`
(`src/image/usbmtp/probe/`, not shipped) in headless QEMU guests, against
QEMU's `usb-mtp` and this repository's simulator `mtpemu.py` (every
string of which says SIMULATED). Emulated only: no real phone or camera
was used. Development readings, not a release and not "Tested".

98 SE ran twice, once with the device on NUSB 3.3's EHCI driver and once
on xHCI98 3.5.0.0, as `AGENTS.md` asks (the owner restated it on
2026-11-16). ME ran on xHCI98 3.5.0.0 only: ME has no USB 2.0 stack, and
the owner decided on 2026-11-16 that ME is released on its xHCI98 half
alone, its USB 2.0 half recorded as not tested ([mtp.md](../design/mtp.md)
11.5).

## Rig

**Emulator.** QEMU 11.1.0 from the release tarball `qemu-11.1.0.tar.xz`
(SHA-256 `6ee1d1a61f68212476b27108c26da5f449dc09b626d42f8279ba0dc2e08fa858`,
the archive of [2026-10-21-qemu-iso.md](2026-10-21-qemu-iso.md)), built
with MSYS2 MINGW64 (`--target-list=x86_64-softmmu --enable-usb-redir`,
`--disable-werror`) with three patches applied in this order:

| Patch | What | SHA-256 |
|---|---|---|
| [qemu-mtp-win32.patch](qemu-mtp-win32.patch) | `usb-mtp` built and run on a Windows host | `b31d38e5dffbc7ed288797bc5508c6b996eded418a6c24641ee740afadb99577` |
| [qemu-nosymlink.patch](qemu-nosymlink.patch) | no symlink install tree on a Windows host | `26b17ca26f6a55cb837e5c67b27bf232b38370dd3621342c739605cff57c193c` |
| [qemu-smm-tlb.patch](qemu-smm-tlb.patch) | the TLB flushed on SMM entry and RSM (the usb4-emu fork's commit `5748fdd`) | `e17980c4ebe3bbebc8fec7d842b97b946efb893914c1e6c4886cab14729b2d54` |

The patches reproduce the build tree: the four files they touch, taken
from the tarball and patched in that order, are byte-identical to the
build tree's, and a full-tree comparison with a fresh extraction differs
only in those four files and in build by-products. The executable
reports `QEMU emulator version 11.1.0`, SHA-256
`39612c933f8b707a3a1a37c4a35d255e7cec96d2f6a6e450926937ff31faf65f`.

**Why the third patch.** Upstream 11.1.0 (this build before the patch,
and a packaged 11.1.0, `v11.1.0-12130-ge470268ff4`) hangs 98 SE on q35 at
its boot logo with the CPU at `SMM=1, EIP=00008000, CS=a000` at every
sample. With `smm=off` the boot went further and stopped at "While
initializing device IOS: An I/O subsystem driver failed to load". The
usb4-emu fork build of the q35 base reached the desktop with the same
command line; its commit `5748fdd` explains the hang (an SMI taken in
real mode keeps a TLB entry of the VGA window over SMBASE `A0000h`). With
the patch the q35 base reaches the desktop.

**Guests.** Headless, TCG, one vCPU, `-action reboot=shutdown` (cold
starts only), port E9h and COM1 to files, the probe files on a read-only
FAT drive (D:). Every run on a fresh overlay; every QEMU's pid and
command line in the kit's `pids.txt`.

  `75ec5d806ba9dd5a53763dd0e950935b54d6b9d27bf0d43b8f96f497557abca4`),

**Devices.** `usb-mtp` (`46F4:0004`, one interface `06/01/01`, a host
folder, read-only) and `mtpemu.py` at commit `80ff1c6` over `usb-redir`:
`android` (`FFFF:0060`, class 00 composite: interface 0 `06/01/01`,
interface 1 `FF/42/01`), `androidff` (`FFFF:0061`, interface 0
`FF/FF/00`), `camera` (`FFFF:0062`, one interface `06/01/01`). Plugged
and unplugged with the monitor's `device_add` and `device_del`.

**Probe builds.** `MTPPRB.SYS` and `MTPPROBE.EXE` built with the
repository's MSVC 6.0 (`drvbuild.ps1`, `build.cmd`); the driver binds by
the test INF `MTPPRB.INF`. Each run's binaries:

| Runs | Commit | `MTPPRB.SYS` | `MTPPROBE.EXE` |
|---|---|---|---|
| 98 SE NUSB EHCI, first set (`c`) | `3602d3a` | `0d6a58ee...42e9` | `961f1574...bbe` |
| 98 SE xHCI98 3.5.0.0, first set (`d`) | `3602d3a`, program `f5faf12` | `0d6a58ee...42e9` | `177d5932...5c08` |

Every event the driver sees is a line `prb <ms> <event> <values>` on port
E9h, written synchronously; the times come from the tick count (10 to 55
ms steps), so latencies are coarse and include the logging's own cost.
Before every stop the program confirms, through an observer handle, that
the request is pending in the stack.

| `camera` | the same picture, `USB\VID_FFFF&PID_0062` | the same | not plugged |
| `android` | 98 SE's composite parent from `USB.INF` ("USB Composite Device", `USB\COMPOSITE`, 98 SE's `USBHUB.SYS`) after a wizard; children `USB\VID_FFFF&PID_0060&MI_00` (`06/01/01`) and `MI_01` (`FF/42/01`), both described by the product string; `MI_01` is enumerated first and `MI_00` only after `MI_01`'s wizard closes | xHCI98's own parent, `USB\XHCI98_COMPOSITE&VID_FFFF&PID_0060` ("xHCI98 USB Composite Device"), installed silently; the same `MI_xx` hardware ids, described by the interface strings ("MTP", "ADB Interface") | as 98 SE under xHCI98 |

The `MI_xx` hardware ids are the same under every parent, so the test
INF's ids bound the probe under both of 98 SE's stacks and on ME. Under
both parents the child's configuration descriptor holds one interface
(`bNumInterfaces` 1; pipes `81` bulk 512, `01` bulk 512, `82` interrupt

bound silently.

## NTKERN readings

"Same tick" below means the stop and the retirement fell in one tick.

| Reading | 98 SE, NUSB EHCI | 98 SE, xHCI98 3.5.0.0 | ME, xHCI98 3.5.0.0 |
|---|---|---|---|
| Win32 view of each status (`IOCTL_PRB_STATUS`, `Information` 3) | `SUCCESS` true, 3 bytes; `CANCELLED` 995; `IO_TIMEOUT` 121; `DELETE_PENDING` 5; `SHARING_VIOLATION` 32; `ACCESS_DENIED` 5; `INVALID_PARAMETER` 87; `DEVICE_BUSY` (`80000011h`) 170 with 3 bytes reported; `DEVICE_NOT_CONNECTED` 1167; `UNSUCCESSFUL` 31 | the same | the same |
| `IoCancelIrp` of a pending bulk IN, interrupt IN, class request (`67h` held by `ep0_hang`) | retired in the same tick or the next; IRP `C0000120h`, URB `C0010000h`; Win32 995, 0 bytes | the same; URB `00010000h` | the same as xHCI98 on 98 SE |
| `URB_FUNCTION_ABORT_PIPE` of a pending bulk IN, interrupt IN | retired, IRP `C0000120h`; the abort IRP succeeded | the same, URB `00010000h` | the same |
| Get Device Status and `RESET_PIPE` against `usb-mtp` | both completed at once (success, 0 bytes): nothing to cancel | the same | the same |
| `CloseHandle` of a handle with a `ReadFile` pending on another thread | blocked until the read ended (86 s, until it was cancelled from another process); no cleanup or close reached the driver meanwhile | the same (52 s) | the same (51 s) |
| `ExitProcess`, `TerminateProcess` with a read and an interrupt read pending (both seen pending in one observation) | NTKERN called the cancel routine of each IRP (interrupt read first), then cleanup and close of every handle about 0.1 s later | the same | the same (bulk read first) |
| A `ReadFile` on a second handle of the same process while a read is pending | reached the driver at once (refused busy, Win32 170) | the same | the same |
| `DeviceIoControl` on another handle while a read is pending | every call observed got through (state reads, stops, a pending interrupt read) | the same | the same |
| A `ReadFile` from a second process while a read is pending | held until the first read ended (seen while the first process sat in a blocked `CloseHandle`) | the same | held until the first process's pending read ended, with no `CloseHandle` involved; its IOCTLs got through |
| Unplug with a read pending | the stack completed the read (`C000009Dh`, URB `C0007000h`, Win32 1167) 0.3 to 0.4 s before REMOVE; a read issued in that gap was admitted and REMOVE's cancel retired it after 219 ms (URB `C0007000h`, its length field still the requested 512, 0 bytes copied); one `SET_POWER` arrived after the power gate had closed and was completed `STATUS_DELETE_PENDING` | the read stayed pending until REMOVE; the driver's cancel retired it (Win32 5); no power IRP | as 98 SE under xHCI98 |
| IRPs on handles kept open after REMOVE | IOCTLs, reads, cleanup and close all arrived after `IoDeleteDevice` (the probe before the zombie route); counters through a kept handle; a new open failed with 2 | the same | the same, but with the zombie route: they reached the retained object, not a deleted one |
| Device object memory | not seen in these runs | after a device was deleted with no handle open, the next device's `AddDevice` got the same address (that an IRP of a handle still open would then reach the new device is an inference; it was not observed); the probe then took that device's IRPs as late and the camera's START failed (problem 10); fixed in `a6a3010`, and the camera started on the rerun | not seen in these runs |
| Zombie route (handles A, B, O kept across an unplug and a plug) | same device replugged: the zombie kept with 3 handles, the new device a different object; old handles' read and state refused (Win32 5), counters answered; 0 IRPs of old handles reached the new device; the zombie deleted at its last close | another device (`camera`) plugged: the same, 0 reached the new device | same device replugged: the same, 0 reached the new device |

Both URB statuses on cancel are by design: xHCI98 uses the value the
Windows 2000 DDK's `usbdi.h` gives `USBD_STATUS_CANCELED`, which lies in
that header's success class; later headers, and NUSB's stack, use
`C0010000h` (xHCI98's source was checked: the value is deliberate there). Clients
decide by the IRP status ([mtp.md](../design/mtp.md) 5.4).

All other cancels and aborts were taken with the request confirmed
pending first. After all runs the driver's counters balanced (creates,
cleanups and closes) and no action was dropped; no guest crashed in a
probe run. The late removals after an End Task are described below.

**Late REMOVE after an End Task.** On 98 SE under xHCI98, the first unplug after an
End Task (run "f", with all four kinds pending) reached the driver about 9.7 minutes
late, and a device plugged meanwhile was not enumerated until then; on ME a later
unplug (nothing pending) about 3.2 minutes late. A matrix on fresh overlays, each
unplug with nothing pending, pinned it down:

| Case | Before the unplug | 98 SE, xHCI98 | ME, xHCI98 | 98 SE, NUSB EHCI |
|---|---|---|---|---|
| T1 | a held bulk OUT cancelled | about 1 s | not run | not run |
| T2 | a held bulk OUT aborted | about 1 s | not run | not run |
| T3 | a held class request cancelled | about 1 s | not run | not run |
| T4 | an ordinary read cancelled | about 1 s | not run | not run |
| T5 | T1 and T3 | about 1 s | not run | not run |
| T6 | the late run's history without End Task | about 1 s | not run | not run |
| T7 | a read and the wait pending, then End Task | none within 60 s; 154 s | none within 60 s; 156 s | none within 60 s; 155 s |

In every late case REMOVE arrived with the guest's next input or activity (in T7, the
typing of the `XHCITR /snapshot` step). It is not unique to xHCI98: it was seen
under both of 98 SE's stacks and on ME. Its mechanism was not established. Meanwhile a cancel
still retired a pending request at once, and a new request failed at once with the
device gone (`C000009Dh`, URB `C0007000h`).

**Binding.** 98 SE's Have Disk (a `split` simulator, `FFFF:0063` MI_00, whose ids
match none of the INF's models) listed all five models of `MTPPRB.INF` with no
warning; a pick closed the wizard, the function's node went away and no driver loaded;
on the next plug the function came back as new hardware with no driver. ME's Have
Disk was not read. ME's own driver search found no driver for `usb-mtp` (`06/01/01`)
(first set).

## What the readings decided

[mtp.md](../design/mtp.md) 5.4 and 5.6 take these up: the device object
is kept as a zombie until the last close, with the open count in
`slot.c` (`SA_FREE_READY`) and a model scenario for it; decisions by the
IRP status; the library treats both removal shapes as the device gone,
cancels its own calls before closing a handle, and runs in one process
with a control handle beside the I/O handle (calls on one handle are
serialised); it never waits for REMOVE, since an unplug after an End
Task may be reported minutes late; `IoDeleteDevice` is the driver's last
act on its removal path; no model is offered for picking by hand.

## Not run

- ME's USB 2.0 half: not tested (no USB 2.0 stack for ME; owner,
  2026-11-16).
- Deferred past M0 ([mtp.md](../design/mtp.md) 12): 98 SE's and ME's
  UHCI stacks (no commitment), zero-length transfers and short and
  zero-length reads' byte counts (5.6 item 2), the `locked` and `single`
  profiles (`split` was used only for the Have Disk reading), a pipe
  reset's cancel, ME's Have Disk, ME's WIA beside our driver.
- The probe build with the device-object fix of `a6a3010` alone was not
  run; its successor `2086262` was. The isolation cases on ME and on
  NUSB's EHCI were run only where the tables say.
- Real phones and cameras: the owner's bench.
