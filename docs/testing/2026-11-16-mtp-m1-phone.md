# MTP M1: first readings from a real phone on 98 SE and ME, 2026-11-16

A first, read-only reading of `USBMTP.SYS` against a real device: a
Fairphone 3 in its MTP ("File transfer") mode, passed through to a
headless QEMU guest running Windows 98 SE with xHCI98 3.5.0.0, then to
two more guests (98 SE on the USB 2.0 stack, ME on xHCI98), and once in
its PTP mode on 98 SE with xHCI98. One phone,
one run on each. A development reading, not a release
and not "Tested". Nothing was sent to, deleted from or changed on the
phone: every operation below only reads.

## Rig

**Emulator.** A QEMU 11.1.2 build with `usb-host` (the usb4-emu fork's
build, which carries the TLB flush on SMM entry of
[2026-11-16-mtp-m0.md](2026-11-16-mtp-m0.md)); the executable's SHA-256 is
`da60139fae18537468fc77df630ef2a25824696f029c898580a8f0ee32ce0c93`.
Machine `pc`, TCG, `-cpu pentium3,-apic`, 256 MB, a `qemu-xhci`
controller. On the Windows host the phone was bound to WinUSB so that
libusb could open it, and attached with
`device_add usb-host,vendorid=0x18d1,productid=0x4ee1` on the xHCI
controller. The emulator reported it at 480 Mb/s.

**Guest.** Windows 98 SE with xHCI98 3.5.0.0, a fresh overlay of the
image the M1 load runs use. No USB 2.0 stack in this guest.

**Files.**

| File | What | SHA-256 |
|---|---|---|
| `USBMTP.SYS` | trace build | `c82caa91da1f3c5e1db96eb6dfdbf174d9ee30c28e96415df024b2bf729b7c10` |
| `MTPTEST.EXE` | with the read-only `storage` test | `0e77a4758de178c96fbf747d3822b75de63952cf9a40e72de4536455eb179468` |
| `MTPPROBE.EXE` | `/pnp` only | `9a623adf44bd98247c6015a72dd4af9b5d3fce38dfb7f807cdefa29cae478b5d` |
| `USBMTP.INF` | as built | `2e634b4e8681635755c44f92f22df38c3ff77908b2b085c4bcab4f25d750bb70` |

**A scratch INF, not the tracked one.** The driver was installed from a
copy of `USBMTP.INF` with one line added under `[Models]`:
`%Device%=UsbMtp,USB\VID_18D1&PID_4EE1`. The reason is the first reading
below. That copy is not in the repository.

## Readings

**How 98 SE sees the phone** (`MTPPROBE /pnp`, before any driver): one
device node, no interface nodes.

- hardware ids `USB\VID_18D1&PID_4EE1&REV_0409`, `USB\VID_18D1&PID_4EE1`
- compatible ids `USB\CLASS_FF&SUBCLASS_FF&PROT_00`,
  `USB\CLASS_FF&SUBCLASS_FF`, `USB\CLASS_FF`
- description `FP3`, parent the xHCI98 root hub, problem 1 (no driver)

So this phone in MTP mode is a single vendor-class interface, and the
tracked INF, which matches only `USB\Class_06&SubClass_01&Prot_01`, does
not match it. The Add New Hardware Wizard opened for "FP3" and found no
driver until it was pointed at the scratch INF.

**Install and start.** The wizard found "MTP or PTP device (wdm-free)" in
the scratch INF and finished. The trace shows the descriptor walk
accepting the configuration and the start succeeding:

- `cfgwalk 00000000 FF010027`: the walk's result 0 (accepted); then the
  node's interface number FFh (none: a whole device, not an `&MI_nn`
  node), one interface in the configuration (`bNumInterfaces` 1) and a
  `wTotalLength` of 0027h, 39 bytes: the configuration, the interface
  and its three endpoint descriptors, nothing else (no class-specific or
  other records).
- `start 00000000 00FF0200`: the start's status 0 (`STATUS_SUCCESS`);
  then the owned interface 0, its class FFh and the bulk IN packet size
  0200h (512).

**`MTPTEST info`.** Interface 1.0, 44 bytes. VID 18D1, PID 4EE1,
bcdDevice 0409; interface 0, class FF/FF/00; maximum packet 512 in, 512
out, 28 interrupt; speed 2 (high speed); endpoints 81 in, 01 out, 82
interrupt. Strings 1 to 3 read: "Fairphone", "FP3" and the serial number
(not recorded here).

**`MTPTEST storage`.** Every response was 2001h (OK).

- OpenSession.
- GetDeviceInfo: 355 bytes, all 355 parsed. Standard version 100, vendor
  extension id 00000006, extension string
  "microsoft.com: 1.0; android.com: 1.0;", functional mode 0000; 31
  operations (1001 to 100D, 1010, 1014 to 1017, 1019 to 101B, 9801 to
  9805, 95C1 to 95C5), 6 events (4002 to 4007), 6 device properties, no
  capture formats, 28 playback formats.
- GetStorageIDs: two storages, 00010001 and 00020001.
- GetStorageInfo 00010001: type 0003, filesystem 0002, access 0000,
  48,091 MiB, "Internal shared storage". GetObjectHandles of its root: 14
  handles.
- GetStorageInfo 00020001: type 0004, filesystem 0002, access 0000,
  61,471 MiB, "SD card". GetObjectHandles of its root: 14 handles.
- CloseSession.

Each data phase arrived in one read; each response was a 12-byte
container of its own.

**`MTPTEST session`.** The same results as on the simulators: a second
claim refused (error 32), a bind with a wrong epoch refused (error 5),
GetDeviceInfo, Get Device Status 2001h, a wait for an event timing out
(error 121; 504 ms for a 500 ms wait), a read left pending for 1.5 s and
then ended by ABORT (error 995), and a new claim after the close with the
next epoch.

**Removal.** With no handle open, detaching the phone from the guest gave
`remove`, `remove-deletes`, `deleting` and `unload` in the trace.

## The same reading on two more configurations

Later the same day, with the same phone, files and scratch INF, each on a
fresh overlay and with the same emulator build, the phone still in its MTP
mode. Read-only as before; one run each.

**98 SE on the USB 2.0 stack (NUSB 3.3's EHCI driver).** The phone was
attached to the guest's `usb-ehci` controller. The wizard opened for
"FP3" and installed from the scratch INF; `cfgwalk` and `start` as above.
`MTPPROBE /pnp` after the install: the same compatible ids, parent
`USB\ROOT_HUB20`, problem 0. `MTPTEST info`: the same values (FF/FF/00,
512/512/28, speed 2, endpoints 81/01/82, three strings). `MTPTEST
storage`: every response 2001h, 355 of 355 bytes parsed, the same two
storages, 14 root handles each. `MTPTEST session`: the same results (the
500 ms wait took 506 ms, the aborted read 1506 ms). Removal with no
handle open: `remove`, `remove-deletes`, `deleting`, `unload`. On this
stack the cancelled URBs carried `C0010000`, where under xHCI98 3.5.0.0
they carried `00010000`; the IRP status was `C0000120` on both.

**ME on xHCI98 3.5.0.0.** ME's wizard, pointed at the scratch INF by
"Specify the location of the driver", installed the driver; `cfgwalk`
and `start` as above. `MTPPROBE /pnp`: parent the xHCI98 root hub,
problem 0. `MTPTEST info`, `storage` and `session`: the same values and
results as on 98 SE (505 ms, 1505 ms). Removal with no handle open: the
same four trace lines.

## The same phone in PTP mode

Later the same day, the same phone switched to its PTP mode, on 98 SE with xHCI98 3.5.0.0 only, a fresh
overlay of the same image, the same emulator build and files, and this
time **the tracked `USBMTP.INF` as built** (`2e634b4e...0bb70`, at the
root of D:), not the scratch INF. Read-only as before; one run.

- **Ids.** The phone presented `18D1:4EE5`: hardware ids
  `USB\VID_18D1&PID_4EE5&REV_0409`, `USB\VID_18D1&PID_4EE5`; compatible
  ids `USB\CLASS_06&SUBCLASS_01&PROT_01`, `USB\CLASS_06&SUBCLASS_01`,
  `USB\CLASS_06`. The wizard opened for "FP3", found "MTP or PTP device
  (wdm-free)" in `D:\USBMTP.INF` and finished, so the tracked INF's class
  line matched it. `MTPPROBE /pnp` after the install: one device node,
  class `UsbMtpDevices`, maker "usb-wdm-free", parent the xHCI98 root
  hub, problem 0.
- **Start.** `cfgwalk 00000000 FF010027` (accepted; a whole device of
  one interface, 39 bytes) and `start 00000000 00060200` (interface 0,
  class 06, bulk IN 512).
- **`MTPTEST info`.** Interface 1.0, generation 1, VID 18D1, PID 4EE5,
  bcdDevice 0409; interface 0, class 06/01/01; maximum packet 512 in, 512
  out, 28 interrupt; speed 2; endpoints 81 in, 01 out, 82 interrupt.
  Strings 1 to 3 read: "Fairphone", "FP3" and the serial number (not
  recorded here).
- **`MTPTEST storage`.** Every response 2001h. GetDeviceInfo: 279 bytes,
  all parsed; vendor extension id 00000000 and an empty extension string
  (MTP mode: 00000006 and the Microsoft and Android strings); the same 31
  operations, 6 events, 6 device properties and 28 playback formats as in
  MTP mode, no capture formats. The same two storages, 00010001
  ("Internal shared storage", 48,091 MiB) and 00020001 ("SD card",
  61,471 MiB); GetObjectHandles of each root: 2 handles (14 in MTP mode).
  Each data phase in one read; each response a 12-byte container of its
  own.
- **`MTPTEST session`.** The same results as in MTP mode: a second claim
  refused (32), the bind and timeout refusals (5), GetDeviceInfo, Get
  Device Status 4 bytes 2001h, the waits timing out (121; the 500 ms wait
  505 ms), a pending read ended by `ABORT` (995 after 1,505 ms), a new
  claim after the close with the next epoch.
- **Removal** with no handle open: `remove`, `remove-deletes`, `deleting`
  and `unload`.

## What this does and does not show

It shows the driver starting on a real Android device at high speed on
98 SE under xHCI98 and under the USB 2.0 stack, and on ME under xHCI98,
and the session, device information and storage operations returning
the same well-formed answers from it on all three. In PTP mode the same
phone is bound by the tracked INF's class line, with no added line, and
answers the same read-only operations on 98 SE under xHCI98.

Not run: any operation that transfers an object or writes to the device;
the device removed with a handle open; a standby with the phone
attached; PTP mode under the USB 2.0 stack and on ME; the phone with USB
debugging on (a composite device). How
the shipped INF should match phones in MTP mode is open
([mtp.md](../design/mtp.md) 3.2, "Vendor class `FF`: never by class").
