# The Ethernet options with a real RTL8157 under xHCI98, XP SP3 and 98 SE, 2026-11-17

Guest legs for the options of design [ethernet.md](../design/ethernet.md)
sections 4.10.8 and 4.10.9 (`*FlowControl`, `*SpeedDuplex`, `*EEE`,
`EnableGreenEthernet`, `AdvancedEEE`, `NetworkAddress`, the receive
checksum keywords) against a **real** Realtek RTL8157 (USB `0BDA:8157`,
`bcdDevice` 3000, chip version `1030`) passed through to QEMU guests. The
earlier legs of these options ([netopts-legs](2026-11-17-netopts-legs.md))
ran against the simulator; this record is about what the real chip showed
that the simulator could not, and where the two differed. It is not a
stall-recovery leg and not a performance measurement. One driver defect
was found (forced 10 and 100 Mb/s, below); its fix came after these legs
and has run on the simulator and the host model only (last section).

## XP SP3, xHCI98 3.5.0.0

### Install and identification

The Found New Hardware wizard (no Windows Update, automatic) listed two
matches of the same version 0.2.3.0: the released INF in `C:\WINDOWS\inf`
and `A:\RTLXP7.INF`; the floppy's was chosen (unsigned prompt answered
Continue Anyway). Device Manager: "Realtek RTL8157 USB 5G Ethernet
(wdm-free) #4", "This device is working properly" (no problem code). The
trace:

| Line | Value |
|---|---|
| `device bda:8157 rev 3000, 3 configurations: probe 0` | three configurations; configuration 0 (value 1), interface 0 selected |
| `chip start: 0, version 1030` | the RTL8157 path (`K_1030`), 363 to 365 requests per start |
| `buffers: rx 8 x 32768, tx 4 x 32768 (64 frames); offload 77` | 32 KiB receive buffers (the SuperSpeed size) |
| `initialized: bda:8157 chip 1030, super speed USB` | |
| `link 1, 5000 Mb/s full duplex, rx 32768` | the partner port linked at 5 Gb/s |

The descriptor format is not named by any trace line; the driver picks
it from the chip version (1030), and with it every received transfer
parsed: no `rx drop` line, and `0 malformed transfers, 0 dropped frames,
0 with an FCS` at every stop, on both systems.

The connection's Status dialog read **Speed 705.0 Mbps** while the
driver reported 5000 Mb/s. 705.0 Mb/s is 5,000,000,000 b/s modulo 2^32:
the driver's `OID_GEN_LINK_SPEED` is 50,000,000 (units of 100 b/s), and
XP's dialog converts it to b/s in 32 bits. This is XP's display; the
simulator legs (1 Gb/s) could not show it. "Limited or no connectivity"
until the static address was set (no DHCP server on the partner).

The Advanced tab (Device Manager or the connection's Configure): nine
entries, in the tab's order, with the values after install:

| Entry | Default shown | Choices |
|---|---|---|
| Advanced EEE | Off | Off, On |
| Energy-Efficient Ethernet (EEE) | Off | Off, On |
| Flow control | Enabled (negotiated) | Enabled (negotiated), Off, Transmit only |
| Green Ethernet | Off | Off, On |
| IPv4 checksum offload | On, transmit | Off, On transmit, Receive enabled, Transmit and receive enabled |

### Flow control against the real partner

Each value set with `NETSET` and the adapter restarted (`devcon
restart`). The trace gives only `setting *FlowControl = n`; the
advertisement written (PHY `0xa408`, MII register 4) and the chip's
resolved directions (`MR_LINK` `0xe908`, bits 0x40 transmit and 0x20
receive pause) come from the capture:

| Value | Advertisement written | `MR_LINK` at link up | Resolved |
|---|---|---|---|
| 3 | 0x1DE1 (PAUSE + ASM_DIR) | 0x10E3 | both directions |
| 0 | 0x11E1 (neither) | 0x1083 | none |
| 1 | 0x19E1 (ASM_DIR alone) | 0x10C3 | transmit only |
| 3 again | 0x1DE1 | 0x10E3 | both |

The partner's advertisement cannot be changed and is not read by the
driver. Of the four partner combinations of IEEE 802.3 Table 28B-3, only
PAUSE + ASM_DIR gives "both" at value 3 **and** "transmit only" at
value 1, so that is the partner's; the three cells this exercises
(column "PAUSE + ASM_DIR" of the simulator record's table) agree with the
table and with the simulator's model. The same three results were seen
again on the second boot and on 98 SE.

### Speed and duplex

| Value | Written | Result (trace and `MR_LINK`) |
|---|---|---|
| 6 (1 Gb/s) | ANAR 0x1C01, GIG control 0x0200, autonegotiation restart | 1000 full, both pause directions |
| 2500 | ANAR 0x1C01, GIG 0x0000 | 2500 full, both |
| 5000 | ANAR 0x1C01 | 5000 full, both |
| 4 (100 full) | BMCR **0xA100** (reset + 100 + full) | **5000 full**, both |
| 3 (100 half) | BMCR **0xA000** | **5000 full** |
| 2 (10 full) | BMCR **0x8100** | **5000 full** |
| 1 (10 half) | BMCR **0x8000** | **5000 full** |
| 0 (automatic) | ANAR 0x1DE1, GIG 0x0200, multi-gig 0x0181 | 5000 full, both |

**Defect (forced 10 and 100 Mb/s on the RTL8157).** For values 1 to 4
the driver's `Negotiate` (`rtlchip.c`) wrote the forced speed and duplex
in the same BMCR write as the reset bit (`MIICTL_RESET`). The real PHY
read BMCR back as **0x1040** (autonegotiation enabled, no forced bits)
30 to 40 ms later, at the driver's first poll of the reset bit: the
reset had returned the register to its defaults, autonegotiation ran
with the multi-gigabit advertisement still set, and the link came up at
5000 full each time. The trace reported `link 1, 5000 Mb/s full duplex`
after `setting *SpeedDuplex = 4` (and 3, 2, 1), so the tab's four 10/100
choices had no effect on this chip. The simulator dropped the reset bit
and kept the forced bits (`rtlemu.py` `phy_written`), so its legs had
shown 100 full and 100 half. The forced path also returned before
writing the advertisement, so the 0x1C01 left by the forced 1 Gb/s run
stayed in the PHY through these four runs; value 0 wrote 0x1DE1 again.

### EEE, Green Ethernet, Advanced EEE, Network Address

| Setting | What the capture shows | Link |
|---|---|---|
| `*EEE` 1 | MAC `0xe040` bits 0-1 set, PHY `0xa432` 0x0811, EEE advertisement `0xa5d0` 0x0006 (1000T, 100TX), `0xa6d4` 0x0003 (2.5G, 5G) | 5000 full |
| `*EEE` 0 | `0xe040` bits cleared, `0xa432` 0x0801, `0xa5d0` and `0xa6d4` 0 | 5000 full |
| `EnableGreenEthernet` 1 / 0 | PHY SRAM `0x8011` 0xD337 / 0x5337 (bit 15); 0x5337 is what the chip held when first read | 5000 full |
| `AdvancedEEE` 1 / 0 | no register write differs: EEE+ is set only at a 10 Mb/s link (`H_EEE_PLUS`), which the defect above made unreachable here | 5000 full |
| `NetworkAddress` set to a locally administered address (02-00-C0-xx-xx-xx), then deleted | `address: NetworkAddress`, initialized with that address; after deletion the chip's own (Realtek's 00-E0-4C prefix) | 5000 full |

Whether the partner accepted EEE (LPI) is not read by the driver; the
trace showed the setting read and the link returning each time. No
`settings this chip cannot apply` line in any run.

## Traffic (partner 169.254.197.91/16, guest 169.254.197.200/16)

The partner side was only read and used as it was. The partner started
everything: `ping` from the partner's address to the guest, and
`netperf.py` bound to the partner's address, connecting to `NETPERF.EXE`
in the guest. A file copy over a share was not run (it would have needed
SMB1 on the partner side for XP and 98 SE); the copies are NETPERF's
fixed-pattern streams, checked byte for byte on the receiving side. Each
stream ran 20 s by the requesting side's clock.

| System, setting | Partner to guest ping | Guest to partner ping | Partner to guest stream | Guest to partner stream |
|---|---|---|---|---|
| XP, checksum 1 (default), flow 3 | 20/20 | 0/20 (see below) | 43.8 MB, 0 mismatched | 49.7 MB, 0 mismatched |
| XP, checksum 3 | 10/10 | - | 41.6 MB, 0 | 38.4 MB, 0 |
| XP, checksum 0 | 10/10 | - | 40.1 MB, 0 | 43.1 MB, 0 |
| XP, checksum 1 | 10/10 | - | 42.6 MB, 0 | 47.1 MB, 0 |
| XP, flow 0 (none resolved) | 10/10 | - | 42.2 MB, 0 | 41.5 MB, 0 |
| XP, flow 1 (transmit only) | 10/10 | - | 41.7 MB, 0 | 42.8 MB, 0 |
| XP, flow 3 (both) | 10/10 | - | 42.0 MB, 0 | 46.5 MB, 0 |
| 98 SE, flow 1 | 10/10 | 0/10 | 14.2 MB, 0 | 18.5 MB, 0 |
| 98 SE, flow 3 | 10/10 | - | 10.8 MB, 0 | 36.2 MB, 0 (the guest's clock ran slow that boot: 62 s by the partner side's) |
| 98 SE, flow 0 | 10/10 | - | 13.4 MB, 0 | 18.6 MB, 0 |

- The guest's pings to the partner got no reply on either system: the
  partner side's firewall drops inbound echo on that port, and it was not
  changed. Running them needs that port to allow inbound ICMPv4 echo.
- Receive checksums with the real chip's verdicts (XP, value 3): the
  driver's counter `rx: 24576 ok ... 24569 checked` during the streams;
  at value 0 and 1, `0 checked`. No stream byte mismatched with the
  verdicts claimed. Which 7 frames were not checked was not looked at.
- Counters: XP `netstat -e` after the last runs: 0 discards, 0 errors
  either way; every XP stop traced `halted: tx n/0`. 98 SE: `netstat -e`
  Sent Errors **5**, and the trace's `tx .../5` in every boot with
  TCP/IP bound (`halted: tx 25/1` on the first restart). The core counts
  as errors the sends it refuses while the link is down (`SendPackets`,
  `Connected` false), and 98's TCP/IP sends right after the driver
  initializes, before the link comes up some seconds later; the 5 were
  not attributed further. No pause-frame counter is exposed by the driver.
- Before the address was given, XP's TCP/IP had already sent its DHCP and
  related frames onto the partner port (status dialog: 5,626 bytes sent).

## Where the real chip differed from the simulator

1. **Forced 10/100 Mb/s**: the real PHY's reset cleared the forced bits
   written with it (BMCR read 0x1040 after 0xA100); the link stayed
   autonegotiated at 5000 full. The simulator kept the forced bits. The
   driver defect above.
2. **State kept across restarts and guests**: the chip is not
   power-cycled between driver starts or between guests. ANAR 0x1C01 from
   a forced 1 Gb/s run stayed until value 0; on 98 SE's first plug
   `MR_LINK` read 0x10E3 (up, 5 Gb/s, both pause) before the driver had
   written anything, left from the XP guest. The simulator started from
   its reset values at every plug.
3. **ANAR as first read**: 0x11E1 (no pause bits) on the real chip; the
   simulator's power-on value was 0x1DE1. With value 3 the driver writes
   0x1DE1 either way, so this changed nothing the driver did, except at
   forced speeds, where it left ANAR alone.
4. **`MR_LINK`'s high word** read 0x0402 (dword `0x040210E3`); the
   simulator's real-chip profile gives 0x0009. Bit 7 of the low word was
   set in every read, as the simulator models; 0x2000 appeared in early
   reads (`0x2280`, `0x2200`) before the link. Neither bit is named in
   `rtlchip.h`; the driver does not use them.
5. **Link speed**: 5000 Mb/s against the real partner (simulator legs:
   1000 on High Speed), which exposed XP's 32-bit Speed display (705.0
   Mbps).
6. **Pause**: only the partner's PAUSE + ASM_DIR column could be
   exercised (3 of 12 cells); they matched the table. Pause frames
   themselves were not observed (no counter).
7. **Advanced EEE**: no effect at 5 Gb/s on the real chip (EEE+ only at
   10 Mb/s, unreachable because of 1). The simulator legs did not test
   it either.
8. **Receive checksum verdicts**: the chip's own, on real TCP streams
   (24569 of 24576 frames claimed checked, no corrupt byte delivered);
   the simulator's verdicts were its model. Malformed or bad-checksum
   frames were not sent toward the real chip (no tool on the partner side
   for it); not run.
9. **Link up after an autonegotiation restart**: about 3.5 to 4.5 s in
   the capture's clock through this passthrough path (not a chip
   measurement).
10. **98 SE transmit errors at start** (5 per boot, above); the simulator
    records do not mention transmit errors on 98 SE. Not attributed.

- 98 SE under the current xHCI98 release (only a 3.1.0.0 base was used).

- The partner's other pause advertisements (not changeable).

## After these legs: the fix, on the simulator and the host model only

Design [ethernet.md](../design/ethernet.md) 4.10.4, "`rtl815x`'s forced
sequence"; code `e69e740`. For values 1 to 4 `Negotiate` now writes the
reset bit alone, polls until BMCR reads it clear (up to 50 reads, each
after a requested 20 ms sleep, plus the latency of each), then writes
the speed and duplex bits alone (IEEE 802.3 22.2.4.1.1), and advertises
only the forced ability (no 1000 Mb/s, no multi-gigabit speed). A reset
that has not cleared by then fails the start with no forced write
(`68c758e`; the simulator's `--reset-stuck`, `0ca2bb9`). The same code
serves every chip of the package;
only the RTL8157 has shown the defect, and only on the real adapter
above.

The simulator was changed after these legs to behave as the real chip
did: a BMCR reset returns the register to its default and drops the bits
written with it, its bit reads set once and then clears, and a write
before that is not taken (`3ad31d9`); `--keep-chip` keeps the chip's
registers from one connection to the next (`ccaeee9`); the RTL8157
profile's advertisement starts at 0x11E1 (`4b2992d`). Items 4 to 10 of
the list above are unchanged in the simulator.

Host tests (no guest, no adapter), at `4b2992d`:

| Test | The chip core before the fix (`63ea5ee`) | With the fix |
|---|---|---|
| `rtltest` (forced 1 to 4 on every chip: the reset written alone, then the forced bits alone; the advertisement) | FAIL at the first forced check | PASS |
| `rtlsimtest.py`, the forced cases (8153 10 full, 8152 100 half, 8157 10 half, 8157 100 full without pause) | 4 FAIL: the links autonegotiated (8157: 5000 full) | PASS |
| `rtlsimtest.py`, one kept RTL8157 run through 6, 2500, 5000, 4, 3, 2, 1, 0 (the order above) | 4 FAIL: 4, 3, 2 and 1 linked at 5000 full with ANAR 0x1C01 and 5G left from the earlier runs, as on the real adapter | PASS |

The fix has not run on the real adapter. A re-run of the forced values
there is owed (design 4.10.4; [open-items](open-items.md)).
