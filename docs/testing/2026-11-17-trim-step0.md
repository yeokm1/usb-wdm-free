# Step 0 of the Advanced-tab trimming: the registry routines on 98 SE, ME and XP, and the install clean-up, 2026-11-17

Design [ethernet.md](../design/ethernet.md) section 4.10.8, "Step 0, before
any trimming code": a disposable test build that proves, on each system,
that the trimming's registry routines load and behave, which key the
driver reaches, and what an install section's `DelReg` does, before any
trimming code is written. Every leg ran against the simulator
(`rtlemu.py`, an RTL8157 at High Speed unless stated); no physical
adapter was used. No trimming code exists; nothing here changes the
released driver.

## The test build (scratch only)

Kept out of the tree, every release folder and every INF of the package:
a copy of `src/net/rtl815x` at `2952348` in a scratch folder, built with
the package's `build.cmd ndis5 trace` plus two changes made only there:

- `trimprb.c` (new) and a call at the end of `Initialize`, after
  `NetUsbOpen` and `Ready` (`NET_STEP0`), as the design places the
  trimming job. The probe runs on a system thread of its own
  (`PsCreateSystemThread`, waited for) and traces every result to the
  debug console. Imports added, and only these, the trimming's set:
  `IoOpenDeviceRegistryKey`, `ZwOpenKey`, `ZwCreateKey`,
  `ZwQueryValueKey`, `ZwSetValueKey`, `ZwEnumerateKey`, `ZwDeleteKey`,
  `RtlDeleteRegistryValue` (`ZwClose` was already imported). The import
  gate passed with them added to the scratch copy's
  `imports-ndis5.txt`. `rtl815x.sys` `4b57509c...`.
- What it does at each start: opens the driver key with
  `IoOpenDeviceRegistryKey(PDO, PLUGPLAY_REGKEY_DRIVER)`; reads
  `TrimProbe` through NDIS (`NdisReadConfiguration`) and through that
  handle and compares; reads `Ndi\params\TrimProbe\ParamDesc`; writes
  `TrimProbeBack` (a value made from the system time) through the handle,
  and after the probe reads it back through NDIS; writes a whole entry
  `Ndi\params\TrimProbeW` ("Driver-written entry <same text>") through the
  handle; lists `Ndi\params\TrimProbeList` (its values, its `enum`, its
  subkeys) and the root values of the experiment.
- The handle rule, by instrumentation only: on `Step0\TrimHandle` (outside
  `Ndi`), ten calibrations (open, `ZwClose`, open again: is the handle
  value reused?), then twenty `RtlDeleteRegistryValue(RTL_REGISTRY_HANDLE)`
  calls each on a handle opened for it alone, which the probe never uses
  again on any system; the next `ZwOpenKey`'s handle value is compared
  with it (equal: the value was freed and handed out again, consistent
  with the routine having closed the handle; unequal proves nothing, as an
  allocator need not hand a freed value out at once).
- Twenty cycles: create `Ndi\params\TrimScratch` with `ParamDesc`, `type`,
  `default`, `Optional` and `enum` with three values, read every value
  back, then delete values first and leaf first (the three `enum` values,
  `enum` with `ZwDeleteKey`, the four values, the key), reading back after
  each deletion; each `RtlDeleteRegistryValue` on a handle of its own,
  closed by the probe on NT and never touched on 98 SE and ME (the system
  told apart by `IoIsWdmVersionAvailable(1, 0x10)`); then ten more opens
  and closes of `Ndi\params`.

INFs (scratch): the tip's built INFs with every install section's
`AddReg` extended by `Probe` (root `TrimProbe` "tp-7Q3k9ZrX" and an edit
entry `Ndi\params\TrimProbe` "Step 0 probe tp-7Q3k9ZrX") and one of: A,
`TrimProbeList` with four choices, default 2, a stray value `TrimStray`
and root `TrimProbeList` 2 with no-clobber; B, `DelReg` of
`HKR,Ndi\params\TrimProbeList` (key form, no value name, no flags) before
the `AddReg`, and the entry written back with two choices ("Choice zero
B", "Choice one B"), default 1, root 1 with no-clobber, a newer
`DriverVer`; C (98 SE only, a control), B without the `DelReg`. Device
names read "(step 0 test)".

## Rig

QEMU 11.1.0 (stock), TCG, headless; throwaway overlays of the installed
bases; the simulator over `usb-redir`. 98 SE: NUSB 3.3's EHCI. ME: ME's
own UHCI, Full Speed. XP SP3: Windows' own EHCI. Files from a virtual
floppy; dialogs answered from screenshots; on XP the updates by
`devcon update` (the Microsoft tool, in the throwaway guest only) and the
registry read with `reg query`; on 98 SE the updates through Device
Manager's Update Driver wizard (Have Disk) and the registry read with
`regedit /e`; root values with `NETSET.EXE`.

## Results: the routines, the handle rule, the key

| System | Load with the new imports | Handle rule (calibration; after `RtlDeleteRegistryValue`) | 20 cycles | Key mapping |
|---|---|---|---|---|
| 98 SE | loaded, every start (fresh install; four more starts on two overlays) | value reused after `ZwClose` 10/10; after the routine 20/20 reused, consistent with the documented rule (98/Me close it) | 180 deletions asked, 180 succeeded, 0 faults; own opens and closes after 10/10 | `TrimProbe` through NDIS and through the handle the same; `TrimProbeBack` written through the handle read back the same through NDIS; the driver-written `TrimProbeW` listed on the Network adapter's Advanced tab |
| ME | loaded | 10/10; 20/20 reused, consistent with the documented rule | 180/180, 0 faults; 10/10 | NDIS and handle the same both ways; ME's Advanced page not opened |
| XP SP3 | loaded, every start (install, three updates, a reboot) | 10/10; 0/20 reused: consistent with the documented rule (2000 and later leave it open), not a proof that it stayed open | 180/180, 0 faults (handles closed by the probe); 10/10 | the same both ways; "Driver-written entry ..." listed on Device Manager's Advanced tab |

The reuse figures are consistent with the documented rule (Learn: 98/Me
close the handle, 2000 and later leave it open) and corroborate it under
the probe's conditions; they were observed without using a handle after
the routine. Non-reuse on XP does not by itself prove the handle stayed
open. A design relies on the documented contract, never on comparing
handle values at run time.

What passed is the **load, delete and key-access subgate** on 98 SE, ME
and XP: every import resolves (so the separate 98 SE/ME build without
them is not needed for that reason), deletion behaved, and the key is the
one NDIS and the property page read. Installer completeness, an
interrupted install and recovery have **not** passed on any system.

## Results: the install clean-up (`DelReg`)

**XP SP3.** The first install found B (the wizard's automatic search;
the higher `DriverVer`), then A, then B again:

| Step | `Ndi\params\TrimProbeList` | Root `TrimProbeList` |
|---|---|---|
| B (first install) | B's text, `enum` 0, 1 | 1 |
| update to A | A's text, `TrimStray`, `enum` 0 to 3 | 1 (kept) |
| root set to 3 (`NETSET`), update to B | B's text; `TrimStray`, `enum\2`, `enum\3` gone | 3 (kept) |
| update to A; the adapter's sheet open on the Advanced tab with an edit pending ("Choice one"); update to B | B's text, the dropped values gone, no deferral seen; the open sheet still showed A's name and choices | 3 |
| then OK on the sheet (XP's sheet has OK and Cancel, no Apply) | unchanged (B) | 1 (the pending edit); the adapter restarted |
| update to A, sheet open with an edit pending, update to B, Cancel | B | 1 (kept) |
| reboot | B | 1 |

So on XP the key form removed the whole subtree and ran before the
`AddReg` (the entry exists with B's content only), and the root value
was kept by every update, written only by the sheet's OK. (Whether XP's
installer keeps an entry no INF writes was not shown: each update
restarted the adapter, and the probe writes `TrimProbeW` again at every
start.)

**98 SE.** On one overlay (A installed by the Add New Hardware wizard):

| Step | `Ndi\params\TrimProbeList` | Root `TrimProbeList` |
|---|---|---|
| A installed | A's | 2 |
| root set to 3 on the Advanced tab (OK, OK, restart declined), update to B | B's; `TrimStray`, `enum\2`, `enum\3` gone | **1** (B's default) |
| root set to 0, update to B again (same INF) | B's | 0 (kept) |
| update to A | A's (and an unnamed value `@`="2" in the entry's key) | **2** (A's default) |

The control, on a second overlay: A installed, then updated to C (no
`DelReg`): `TrimStray`, `enum\2` and `enum\3` were gone as with B, and so
was the driver-written `Ndi\params\TrimProbeW`, which no INF writes; the
root value went from 2 to 1 (C's default) despite the no-clobber flag,
and every parameter key gained an unnamed value equal to its current
value. **In these tested 98 SE update paths** (Device Manager's Update
Driver wizard, Have Disk; three updates to a different INF and one to the
same INF, with this scratch package) **the whole entry was replaced, with
or without `DelReg`**: the control shows `DelReg` was not needed for the
replacement observed, so its own effect is not shown on 98 SE; it does
not establish what every network-installer path does or exclude an
interaction with this package. In the same paths an update to a
different INF reset the root value tested to the new INF's default; the
same INF installed again kept it.

With the sheet open on 98 SE: the Network properties' adapter sheet
open on the Advanced tab with an edit pending ("Choice three"), an update
through Device Manager (the wizard took the installed model, so it
reinstalled A) ended with "Windows was unable to install the Realtek
RTL8157 USB 5G Ethernet (step 0 test) device"; the adapter halted, and
afterwards no `Net` key carried its name (`NETSET`, `regedit /e` found
none). OK on the sheet, then OK on Network, restarted Windows (the
restart question answered Yes by the keystroke); after the restart the
device enumerated but no driver loaded and no wizard came. Cancel was
not reached on 98 SE. The cause is not attributed: it happened with a
scratch driver that writes registry metadata at every start, on an
overlay whose setup had earlier been disturbed by stray keystrokes; a
clean control with an unmodified package is owed.

**2000, ME (the experiment; ME's Advanced page and update behaviour are
untested), Vista, 7:** not run. The 2000 base has no
USB stack files (toolchain.md, "Test guests"); that rig was not set up.
On ME the automatic search installed B first and the update steps were
not run.

## What this means for the design

- The load, delete and key-access subgate: passed on 98 SE, ME and XP;
  the handle figures consistent with the documented rule; 2000 not run.
  Installer completeness, interruption and recovery: not passed.
- The key: the device-object handle reaches the key whose `Ndi\params`
  the property page reads, and NDIS reads the same values (98 SE, ME
  reads, XP).
- The clean-up: shown on XP. In the tested 98 SE update paths the entry
  was replaced whole whether or not `DelReg` was there, what the driver
  had written there was discarded, and the root value tested was reset on
  an update to another INF; one update made with the property sheet open
  failed and left the adapter without its driver key (cause not
  attributed). ME inherits none of these 98 SE conclusions.

Evidence (logs, screenshots, the scratch build): `E:\usb-wdm-free\netopts\w3`
(`logs\e9-*.log` the traces, `logs\sim-*.jsonl` the simulator, `shots\`,
`step0\` the test build, `STATE.md` the order of events).
