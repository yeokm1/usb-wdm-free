# The forced speeds again, 2000's options and XP's checksums under xHCI98, with simulated chips, 2026-11-17 and 18

Guest legs owed by [netopts-legs](2026-11-17-netopts-legs.md),
[advanced-tab](2026-11-09-advanced-tab.md) and
[open-items](open-items.md) for `rtl815x`'s Advanced tab options (design
[ethernet.md](../design/ethernet.md) 4.10.4 and 4.10.9):

1. the forced-speed rows those records mark as superseded (observed
   against a simulator whose PHY reset kept the bits written with it),
   run again with the fixed driver (`e69e740`, `68c758e`) against the
   corrected simulator (`3ad31d9`, `ccaeee9`, `4b2992d`), on XP SP3 and
   98 SE, with the simulated RTL8157 and RTL8156B;
2. Windows 2000's leg of the options (flow control, checksums, speed and
   duplex), with the Advanced tab in Device Manager;
3. XP SP3's receive checksums with xHCI98 as the host controller.

Every leg ran against the simulator (`rtlemu.py`); no physical adapter
was used and none is claimed. This is simulator evidence: the registers
are the model's, and what it shows is the driver's writes and the
systems' handling on top of that model. The real chip's behaviour with
the fixed driver is not shown here.

## 1. Forced speeds with the fixed driver

The order: Automatic, a forced 1 Gb/s run (6), the multi-gigabit values
where the chip has them, 4, 3, 2, 1, and back to Automatic (0), on one
kept chip. "ANAR" is the advertisement (register 4), "1000" register 9
(1000BASE-T control); every forced value also carries the trace's
`setting *SpeedDuplex = <v>` and `link 1, <speed> <duplex>`.

**RTL8157, XP SP3, Windows' EHCI (High Speed), and 98 SE, NUSB 3.3's
EHCI (High Speed): the same registers on both.**

| 6 | 1000 full | 0x1040 | 0x1C01 | 0x0200 | both | 4/4 |
| 4 | 100 full | 0x2100 | 0x1D01 | 0x0000 | none | 4/4 |
| 3 | 100 half | 0x2000 | 0x1C81 | 0x0000 | none | 4/4 |
| 2 | 10 full | 0x0100 | 0x1C41 | 0x0000 | none | 4/4 |

Every case PASS. At each forced value 1 to 4 the control register held
the forced speed and duplex with autonegotiation off, the link came up
at that speed and duplex, and the advertisement held only the forced
ability and the pause bits (`*FlowControl` 3), with register 9 (and
7.32) cleared (design 4.10.4); with autonegotiation off there was no
pause either way. After the forced runs Automatic wrote every field
back (0x1DE1 or 0x0DE1, 0x0200, and 0x0080 at SuperSpeed), on the kept
chip. The RTL8157's bit 0x1000 in the advertisement is the simulator's
power-on value for that chip (as the real RTL8157 read), kept by the
driver's masked updates.

On both 98 SE guests the first run of value 2 on the RTL8156B wrote
2500 instead: 98 SE's Run box completed "...SpeedDuplex 2" from the
earlier "...SpeedDuplex 2500" in its history. Those two cases are void
(they read as 2500 does); value 2 was run again with a trailing space,
then value 0, and the table shows those runs. The RTL8157 runs on 98 SE
had no 2500 before them; on XP the Run box did not complete the value
(the trace read 2).

The rows these replace: netopts-legs' forced 100 full and half on XP
SP3 and 98 SE (RTL8157), and advanced-tab's `*SpeedDuplex` 4 on 98 SE
under xHCI98 and NUSB's EHCI and on XP (RTL8156B). Here every value 1 to
4 ran on each, and the RTL8156B under xHCI98 ran under xHCI98 3.5.0.0
(advanced-tab's ran under 3.4.2.0).

### 98 SE, host-to-guest stream at each forced value (side measurement)

On the 98 SE guest under NUSB's EHCI, the simulated RTL8157 with
`--udp` bridged to a QEMU user-mode network, `NETPERF.EXE` in the guest
and `netperf.py ... recv` (host to guest, 20 s) through a forwarded
port, the value changed and the adapter restarted between runs:

| Value | Link | Host to guest |
|---|---|---|
| 0 | 1000 full | 23.48 Mb/s |
| 4 | 100 full | 26.02 Mb/s |
| 3 | 100 half | 24.25 Mb/s |
| 2 | 10 full | 24.34 Mb/s |
| 1 | 10 half | 25.07 Mb/s |
| 0 | 1000 full | 29.51 Mb/s |

No mismatched byte in any run. The simulator does not limit the rate
to the link speed or model the wire, so these rates are the emulated
machine's and say nothing about the chip; what they show is that with
the simulator no forced value slowed the 98 SE driver's receive path.

## 2. Windows 2000 SP4: the options (simulated RTL8157, 2000's EHCI)

Installed by the Found New Hardware wizard from the floppy
(`RTL815X.INF`, the unsigned-driver question answered Yes); the driver
started at once: `task offload: tx 3 rx 0`, 1000 full.

**The Advanced tab** (Device Manager, the adapter's Properties): nine
entries, "Advanced EEE", "Energy-Efficient Ethernet (EEE)", "Flow
control", "Green Ethernet", "IPv4 checksum offload", "Network Address",
"Speed and duplex", "TCP checksum offload (IPv4)", "UDP checksum offload
(IPv4)". Flow control offers "Enabled (negotiated)", "Off", "Transmit
only"; Speed and duplex "1 Gb/s full duplex", "10 Mb/s full duplex",
"10 Mb/s half duplex", "100 Mb/s full duplex", "100 Mb/s half duplex",
"2.5 Gb/s full duplex", "5 Gb/s full duplex", "Automatic" (2000 lists
them sorted); TCP checksum offload "Off", "On, transmit" (current),
"Receive enabled", "Transmit and receive enabled".

| Step | Result |
|---|---|
| Flow control: "Transmit only" chosen in the tab, OK | 2000 restarted the adapter at once (halt, a new `DriverEntry`); `setting *FlowControl = 1`; ANAR 0x19E1; transmit only. PASS |
| Speed and duplex: "100 Mb/s full duplex" chosen in the tab, OK | restarted at once; `setting *SpeedDuplex = 4`; BMCR 0x2100, 100 full. PASS |
| The sheet reopened | Speed and duplex shows "100 Mb/s full duplex". PASS |
| "Automatic" chosen in the tab, OK | 1000 full |

(While choosing Flow control, an arrow key in the open Speed list moved
it to "1 Gb/s full duplex"; it was set back to "Automatic" before that
OK, as the trace's `= 0` confirms.)

**Values written with `NETSET.EXE`, the adapter replugged:**

| Keyword, value | Result |
|---|---|
| `*FlowControl` 0 | ANAR 0x11E1; no pause. PASS |
| `*FlowControl` 2 | `= 2: not offered, default 3`; 0x1DE1; both. PASS |
| `*FlowControl` 3 | 0x1DE1; both. PASS |
| The three checksum keywords 0 | `keywords leave 0`; no `task offload` line (no set). PASS |
| 1 | `keywords leave 7`; `task offload: tx 3 rx 0`. PASS |
| 2 | `keywords leave 70`; `tx 0 rx 3`. PASS |
| 3 | `tx 3 rx 3`. PASS |
| `*SpeedDuplex` 6, 2500, 5000, 4, 3, 2, 1, 0 | as the RTL8157 table above: 6 1000 full ANAR 0x1C01; 2500 and 5000 taken as 0 at High Speed (traced), 1000 full; 4 to 1 forced, BMCR 0x2100, 0x2000, 0x0100, 0x0000, the link at that speed and duplex, no pause; 0 1000 full, 0x1DE1, 0x0200. Each with a ping 4/4. PASS |

2000 SP4's TCP/IP enabled IPv4 and TCP, never UDP, either way (bits 1
and 2), as XP SP3 does.

**Crafted frames** (the checksum-trace build copied over
`system32\drivers\rtl815x.sys` with the adapter unplugged; the simulator
bridged to the probe harness `cspeer.py` and a QEMU user-mode network,
as netopts-legs; 2000 has no firewall): the 14 cases of netopts-legs at
values 3, 2 and 1, 42 of 42 PASS. At 3 and 2 the claims were those of
netopts-legs' table (a good TCP checksum claimed as IPv4 and TCP, a bad
one IPv4 only, UDP IPv4 only, fragments and UDP checksum 0 IPv4 only,
a bad IPv4 header checksum and the malformed lengths nothing); at 1
(receive not enabled) nothing was claimed and the stack checked every
frame itself, with the same answers.
